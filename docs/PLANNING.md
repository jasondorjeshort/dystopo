# Planning

## Purpose
A topographic map and backcountry navigation system. Reference apps: BackCountry Navigator, Gaia GPS, CalTopo (app + web).
Android first. Designed to grow into a full-stack system: a sync server, then desktop and iOS clients.

**Where decisions and facts live (since T84, 2026-10-12).** This file keeps the design detail, the measurements and the dated log. Decisions are recorded as ADRs in [`design/decisions/`](design/decisions/README.md): the Hatchery alignment and why this file stays whole (0020), the git guard (0021), [Units](#units-decided-2026-10-10) (0022), no Wi-Fi gates (0023), publishing and the beta path (0024), the [Design goals](#design-goals-set-2026-10-10-one-data-path-online-and-offline-precaching-long-routes-sharing-on-a-trip) (0025), the coordinator's own hands (0026), T75's area manifest (0027) and T77's long-distance router (0028); a new decision gets an ADR and the section here points at it. ## Hard requirements
- **Offline-first.** Everything works with no connection; going online only adds things (sync, fresh tiles, sharing).
- **Distributed communication.** All modules (phone, server, future desktop and iOS clients) exchange data through one well-defined sync protocol. The server is a peer that is always on, not the single source of truth.
- **Don't preclude:** local map generation, a full OSM map with routing, iOS/desktop clients.
- **Agent-operable.** AI agents do most or all of the coding and debugging. Every feature must be buildable, runnable, observable, and testable from a command line with no human at the device. See [Agent-driven development](#agent-driven-development).

## Differentiating features
The core problem: each reference app has features the others lack. The goal is the union, without their weaknesses.

| App | Strength to keep | Gap to fix |
|---|---|---|
| CalTopo | Generates its own maps from national elevation data (NED/3DEP) + OSM. Strong planning tools on the web. | US-only. Its maps can't be used in other navigation apps or tools. |
| BackCountry Navigator | Very easy offline map downloads. Long-time daily driver. | Very dated interface. Limited, stale map sources (no OSM). Missing simple features. |
| Gaia GPS | _TBD_ | _TBD_ |

### Product principles that follow
1. **Global coverage.** Use the best available data for each region: global baselines (Copernicus GLO-30 DEM, OSM) layered with higher-resolution national sources where they exist (USGS 3DEP, and similar datasets in other countries).
2. **Our maps are open and portable.** Anything we generate can be exported or served in standard formats (PMTiles, MBTiles, XYZ/TileJSON URLs, GPX/KML/GeoJSON) so other apps and tools can use it. Interoperability is a feature, not an afterthought.
3. **Offline downloads as easy as BackCountry Navigator.** Pick an area and zoom range, see the size estimate, download, done.
4. **Many map sources, kept fresh.** A pluggable map-source catalog: built-in sources, user-added XYZ/WMS/WMTS sources, and regularly regenerated OSM-based maps.
5. **Modern UI.**
6. **The user controls how the map is drawn.** Contour interval, units, shading, slope-angle thresholds, which layers show, and **label/text size** are settings. Most map apps draw text far too small on average phone screens. Default to larger, readable labels, scaled to screen size and density, with a user text-scale setting.

## Architecture goal: rapid feature growth, small footprint where it counts
We expect features to multiply quickly. Total code complexity can grow large, but **the Android app must stay small in CPU, memory, battery, and APK size.**

- **Small core, feature modules.** The Android app has a lean core (map display, location, tracks, offline storage, sync). Features are separate Gradle modules behind well-defined interfaces, so adding one doesn't bloat or destabilize the rest. Rarely used ones can become Play Feature Delivery on-demand modules.
- **Heavy lifting goes where resources are.** Bulk processing (OSM tile builds, large DEM processing, global datasets) runs on the server or desktop. The phone does only what has to happen locally or offline.
- **Different budgets per module.** Server and desktop modules can trade footprint for features. Android modules can't.
- **Budgets are enforced, not hoped for.** APK size, cold-start time, steady-state memory, and battery cost of GPS tracking are measured in automated checks (Macrobenchmark, APK size checks, memory stats from the debug server). A regression fails the build, so agents see it immediately.
- **Lazy by default.** Load data, map sources, and features only when used. Stream tiles from disk instead of holding them in memory.

## Proposed architecture

### Code sharing: Kotlin Multiplatform (KMP)
- One `shared` module holds the domain model, sync engine, storage, and geo math. It compiles for Android, JVM (server + desktop), and iOS.
- Platform modules: `androidApp` (Jetpack Compose), `server` (Ktor), later `desktopApp` and `iosApp`.
- **Constraint:** code in `shared` must be pure Kotlin. Java libraries (JTS, GraphHopper, Planetiler…) work on Android, server, and desktop, but **not iOS**. Wherever we use one, it goes behind an interface in `shared` with JVM-only implementations.

### Map rendering: MapLibre Native (proposed)
- Open source, with Android/iOS SDKs and a web counterpart (MapLibre GL JS) for a CalTopo-style site.
- Renders vector tiles, raster tiles, hillshade from DEM, and 3D terrain.
- Alternative: Mapsforge, which is pure Java and fully offline but Android/desktop only, with weaker styling. Not proposed.

### Map data formats
- Offline packs: **PMTiles** (single file, works over HTTP range requests and from local disk). MBTiles as a fallback.
- Vectors: Mapbox Vector Tiles (MVT). Elevation: terrain-RGB / Terrarium DEM tiles.
- User data import/export: GPX, KML/KMZ, GeoJSON.

### Raw data + on-device rendering vs downloaded tiles
Rough estimates for one 1°×1° cell (~9,000 km² at 40°N), to be measured in phase 0:

| What's stored offline | Size per 1°×1° | Device CPU when viewing | Restylable on device? |
|---|---|---|---|
| Raster topo tiles to z16 (CalTopo/BCN style) | ~1.5–2.5 GB | Almost none (decode images) | No |
| Raster topo tiles to z15 | ~0.4–0.6 GB | Almost none | No |
| OSM vector tiles (PMTiles) | ~20–100 MB | GPU rendering, low CPU | Yes |
| DEM, 30 m (Copernicus GLO-30), compressed | ~15–30 MB | See below | Yes |
| DEM, 10 m (USGS 3DEP 1/3″), compressed | ~100–250 MB | See below | Yes |
| DEM, 1 m lidar | Several GB | See below | Yes; small areas only |
| Raw OSM extract (.osm.pbf) | Similar to vector tiles | **Not renderable directly**: needs preprocessing that is heavy in RAM | n/a |

**Elevation: generate on the fly. Feasible and cheap.**
- Hillshade and slope shading: a small per-pixel kernel. MapLibre already does hillshade on the GPU from DEM tiles. Effectively free.
- Contours: marching squares per tile, ~1–10 ms per 256–512 px tile on one phone core, parallel across cores. maplibre-contour does this in browsers today.
- Memory: a 512×512 16-bit DEM tile is 512 KB. A 50-tile LRU cache is ~25 MB.
- Generated contour tiles are cached on disk, so CPU is spent once per area, not on every pan.
- The DEM needs zoomed-out overview levels (a pyramid) so low-zoom contours stay smooth and fast.
- **Product win:** contour interval, units (ft/m), shading, and slope-angle thresholds become user settings rather than baked into images.

**OSM: download vector tiles, don't process raw OSM on the phone.**
- Raw OSM has no spatial index. Turning it into something renderable means resolving every node location, which takes lots of RAM and minutes to hours. Fine on desktop/server (Planetiler), impractical on a phone beyond a county-sized area.
- Vector tiles are already "data rendered on device": MapLibre styles them on the GPU at view time. OsmAnd, Organic Maps, and Mapsforge-based apps have used this model on phones for over a decade.
- Possible later experiment: on-device conversion of small raw extracts.

**How offline navigation apps do it.** OsmAnd (`.obf`), Organic Maps (`.mwm`), MapFactor Navigator, and Mapsforge-based apps all use the same model: a server converts OSM once into **one compact file per country/state**, and the phone renders and routes from it. Each file holds:
- Vector geometry with a spatial index and pre-simplified versions for zoomed-out views.
- A **routing graph** (roads/paths as a network with costs) for on-device route finding.
- A search index (place names, addresses).
"Very simple map" apps draw only a subset (roads, water, places) with minimal styling, which keeps files small and rendering cheap.

**Our equivalent: region packs.**
- One pack per country/state (matching standard extract boundaries, e.g. Geofabrik), built by Planetiler + routing tools on desktop/server/peers.
- A pack contains: OSM vector tiles (PMTiles), a routing graph (format depends on BRouter vs GraphHopper), a search index, and the DEM pyramid. Each part is optional and separately versioned.
- **Two ways to download:** whole region (simple, like Navigator) or a drawn area (like BackCountry Navigator). Area downloads are cut from region packs; PMTiles supports extracting a bounding box by HTTP range requests.
- Map detail is a style choice, not a data choice: the same pack can be drawn as a simple navigation map or a detailed topo map.

**Decision (proposed): hybrid.**
- Offline packs contain **DEM (as a pyramid) + OSM vector tiles + overlays**, not rendered rasters.
- Hillshade, slope shading, and contours are generated on device and cached.
- The same packs are what peers share: small, content-addressable, and style-independent.
- Raster exports (PNG/MBTiles/XYZ for other apps) are rendered from these on desktop/server, or on device on request.

### Elevation compositing: seamless multi-source DEM (key differentiator)
Source quality varies hugely: USGS 3DEP (1 m lidar in much of the US, 10 m everywhere in the US) is far better than global sources (Copernicus/SRTM, ~30 m). Some other countries have national lidar too (e.g. Switzerland, Austria, Norway, UK, NZ). **No existing app moves smoothly between sources.** That's a core feature to build.

What "smooth" requires:
- **A source catalog.** Each source has a coverage footprint (polygon or tile mask; 3DEP 1 m is patchy), resolution, accuracy, capture date, vertical datum, and license/attribution.
- **Best available per location.** For any area and zoom, use the highest-ranked source that covers each cell. Don't fetch 1 m data for a zoom-10 view.
- **Common vertical datum.** Sources use different datums (US NAVD88, EGM96, EGM2008, ellipsoid heights). Unconverted, they disagree by metres and leave a step at every boundary. Convert everything to one datum before blending.
- **Feathered seams.** Near a coverage edge, blend the two sources over a transition band (weight by distance to the edge) so there's no cliff or kink in the hillshade or contours.
- **Void filling.** Holes in a high-resolution source (water, data gaps) are filled from the next source down.
- **Provenance.** Output records which sources contributed, for attribution and so the app can show where high-resolution data exists.
- **Where it runs.** Compositing runs on the server/desktop when building region packs, so phones get one seamless DEM pyramid. The same `shared` code can composite on device when a user has downloaded raw sources.

Status: built in `devtool` as of 2026-10-09 (details in the Phase 0 log). Sources: `copernicus` (GLO-30, global), `3dep` (USGS 10 m), `3dep-1m` (USGS lidar, found through the TNM API), and `best`, which layers them with feathered edges in a common EGM2008 datum. `terrarium` (Mapzen's frozen 2017 mosaic) is kept only for comparison. Still missing: the source catalog with coverage footprints and dates, provenance in outputs, and per-tile compositing with halos.

### Offline-first data and sync
- Local SQLite (SQLDelight, KMP-compatible) is the source of truth on every device.
- Every entity (waypoint, track, route, map, folder, share) has a UUID and is never identified by a server-assigned ID.
- Changes are recorded as an **operation log** with hybrid logical clock (HLC) timestamps. Peers exchange the ops they're missing. Conflicts resolve per field (last-writer-wins, plus CRDT types where merging matters, e.g. track point lists).
- Transport is pluggable: HTTPS/WebSocket to the server first, possibly device-to-device later (Wi-Fi Direct / Bluetooth / LAN) with the same protocol.
- Wire format: versioned, so old clients keep working. Built as a hand-written compact binary format (no serialization dependency in `shared`); see [Sync](#sync-as-built-t44-t51).
- Candidates considered instead of building our own: Automerge (a Rust core behind JNI bindings, a native library per platform, whole-document CRDT history: more than per-field last-writer-wins on a handful of entity types needs), Electric/PowerSync-style sync (server-authoritative database replication, against "the server is just a peer"), Couchbase Lite (its own document store and server stack). The op log below is under 2,000 lines of pure Kotlin with a simulator that checks it; revisit if collaborative editing of long texts ever matters.

### Peer-to-peer (long-term goal)
Ideally modules talk directly with no central server, BitTorrent-style. Not built early, but these choices keep it possible:
- **Identity is a keypair, not a server account.** Each device/user has a public key; ops are signed. A server can vouch for keys but isn't required.
- **Content-addressed data.** Tile packs and large files are identified by hash and split into chunks, so any peer can serve any chunk and the receiver verifies it. This is the BitTorrent/IPFS model.
- **The op log is already peer-friendly.** UUIDs + HLC timestamps + "send me the ops I'm missing" works the same between two phones as between a phone and a server.
- **Transport stays pluggable.** Start with direct HTTP/WebSocket to a known peer. Later: LAN discovery (mDNS), a DHT for finding peers, relays for NAT traversal. Evaluate jvm-libp2p (MIT/Apache) before building our own.
- **The server is just an always-on peer** that also seeds content and can act as a relay.

### Sync (as built, T44, T51)
Code: `shared/.../sync/` (pure Kotlin, every platform; the HTTP peer logic, paging included, is `SyncServer` there), the stores in `shared/.../store/`, the server peer's HTTP adapter in `serverlib/.../devtool/SyncRoutes.kt` (since T52; used by `devtool serve` and the `server` module, which can put `/sync*` behind a bearer token), the JVM tools in `devtool/.../SyncCommand.kt`, the phone in `androidApp/.../sync/` and `SyncRoutes.kt`.

**Model.** All user data (tracks, waypoints, routes, settings) is an append-only **operation log**; the tables the app reads (`track`, `track_point`, `waypoint` in `tracks.db`) are a **materialised view** of it, updated in the same SQLite transaction as the operation. Operations are small and typed: `PutTrack`/`PutWaypoint`/`PutRoute`/`PutSetting` (create, or replace all fields: an import, a re-import after a delete), `SetField` (one field: rename, description), `AppendPoints` (points added to one numbered segment of a track; a recorded fix is one append of one point), `Delete` (a tombstone). Every operation carries a **hybrid logical clock** timestamp (wall ms, counter, device id): totally ordered, with the receive rule (a replica that merged an operation stamps everything afterwards later than it, even when its own clock is behind). Device ids are random UUIDs created with the database on first open and kept in `sync_meta` (one per install). Local-only state is not synced: which track this device is recording, `updatedAt`, the stats cache.

**Merge rules** (`Materializer`: the state of an entity is a pure function of the set of its operations, so arrival order, duplicates and the replica computing it do not matter):
- *Tombstones:* the newest `Delete` hides every operation on the entity older than it. An entity exists when a `Put` newer than its newest delete exists, so a delete wins over every change it could have seen, and a re-import of the same file (same ids) after a delete brings the track back as imported. Operations older than a tombstone are dropped from the log when it arrives (compaction rule 1), and are dropped on arrival afterwards.
- *Fields:* last writer wins per field by HLC. Two concurrent renames resolve to the greater HLC on every replica (later wall clock, else counter, else device id).
- *Track points:* the union of all live appends, ordered by (segment number, HLC of the append, position in it). A device's own appends are in its HLC order, so a recording keeps its order, and two devices appending to one track interleave the same way everywhere. Two appends with the same segment and identical points (64-bit FNV-1a content digest), such as the same GPX imported on two devices, count once.
- *Waypoints* belong to a track (fixed at their put) or to none; a waypoint whose track does not exist is hidden (added on one device while the track was deleted on another). Waypoints of a track are listed in the order of their first put.
- *Routes* (T60, `model/RoutePlan.kt`): no new operation types. A planned route is a `PutRoute` (name and the other GPX fields, no points) followed in the same transaction by two `SetField`s: `path` (the travel mode, the via points and every leg's geometry and kind, trail, straight or fixed, in one versioned base64url value: deltas in 1e-7 degrees and centimetres, about 8 bytes a point) and `waypoints` (the route's waypoints, exact). Both are last writer wins like any field. Via points and legs live in one value on purpose: two concurrent drags must never leave one device's via points with the other's legs; a rename and a drag on two devices both survive (separate fields), two drags resolve to the later one, a concurrent waypoint add on two devices keeps the later list (reported as edited on two devices). A put resets `path` and `waypoints` (a put replaces every field); a pre-T60 put with points, or a `path` that does not decode (a newer format), materialises as one fixed leg from the put's points, the same way everywhere. Older builds ignore the unknown fields. Coordinates are quantised when the path is made, so a decoded path equals what was encoded and a GPX written from it is byte-identical on every replica. Each edit writes the whole path again (a 300-point Paradise route is about 2.5 kB per drag); superseded values stay in the log like any field write.

**Clocks (T51).** *Skew guard:* a received HLC more than one day ahead of local physical time (`HlcClock.MAX_AHEAD_MS`) is merged (every replica must hold the same set to converge) but not observed: the receive rule skips it, so one device with a clock far ahead no longer drags every replica's clock to its future, and an absurd timestamp cannot exhaust the counter. Each replica counts such operations (`SkewLog`: count, largest lead, last device; persisted in `sync_meta` `skew`, shown as `clockSkew` in `/sync/status` and on the phone's sync screen). *Entity-level receive rule:* a local change to an entity is stamped after every operation this replica holds on that entity, even one past the guard (up to `MAX_SEEN_AHEAD_MS`, 30 days), because the user saw that state: a rename after seeing a far-future rename still wins, and a re-import after a far-future delete is not dead on arrival. The cost: a device that edits something a fast device touched follows that device's clock from then on (in `sync-sim` with a peer two days ahead and heavy shared editing, the two honest peers end the run about two days ahead; with no shared edits they stay at their own time). Further ahead than 30 days, a local change to such an entity can lose to it until real time catches up (an insert then fails with a clear error). A full counter moves the wall on by 1 ms instead of failing. A replica reopened after a crash restarts its clock from its own vector entry and the other entries within the guard (`SqlTrackStore` used to take the newest operation of any device).

**Runs (T51).** A recorded fix extends this device's previous single-device append (same track, same segment) instead of adding an operation, while that append is the newest operation on the track, has not shipped (no bundle or page was built since; `opsSince`/`page` mark this device's operations up to then as shipped, in memory, so a restart starts a new run), and holds fewer than 64 points; the grown append replaces it (new HLC, same transaction, old row deleted). No other replica ever held the replaced operation, so this is invisible to the merge. A recording now costs about 33 bytes per fix plus one header per run instead of 76 bytes per fix (100 fixes: 3 operations instead of 101).

**Edited on two devices (T51).** When a merge brings a field write whose current value on this replica came from another device and differs, `Conflicts` reports it: as *concurrent* when the bundle's sender did not hold the current write (the merge point, the first replica that has both, finds these), and as *overwritten here* when the current value was this device's own (so the device whose value lost always learns of it, concurrent or not). Operations carry no causal history beyond their HLC, so concurrency is a lower bound. Merge results are unchanged. The phone keeps the last 100 (`files/sync/conflicts.json`) and shows "edited on 2 devices" on the track in the list; a tap says which value was kept and dismisses it.

**App settings (T51).** The user's units (only a choice the user made, not a region seed), text scale and map options (`MapOptions.KEYS`) are setting operations `app.units`, `app.textScale`, `app.map.<key>`, last writer wins per key. `SettingsSync.publish` writes the keys a settings change set (one line in `SettingsRoutes.apply`, which the sheet and `POST /settings` share); after a sync that merged something, `SettingsSync.pull` applies synced values that differ through the same validation and apply path (a value this build rejects is skipped and reported) without publishing them again. Device-local settings stay local: server, warm-up, cache caps, decoder, sync peer and token.

**Protocol.** Each replica keeps a **version vector**: per device, the newest operation of that device it holds. Sync with a peer is pull, merge, push: `pull(since = my vector)` returns a **bundle** (the peer's operations after my vector, the vector they were selected against (`base`), and the peer's vector); I merge it, then push the operations the peer's vector lacks. A device's operations always reach a replica as a prefix in HLC order: a bundle's operations of device D are taken only when `base[D]` is at or below what the receiver holds of D, otherwise D is skipped for that bundle (a gap; a later sync fills it). Replays, duplicates and reordering are harmless.

**Pages (T51).** A first sync of a big log no longer needs one request. `SyncReplica.page(since, maxOps, maxBytes)` returns the oldest operations after `since` (at most `maxOps`, about `maxBytes` raw, always at least one) as a bundle whose vector is the *continuation vector* (per device, the newest operation in the page, or the whole entry when the page holds the rest of that device) with a `more` flag. The receiver merges it like any bundle and pulls again from its new vector; the last page carries the peer's full vector. Since every page is a valid bundle under the gap rule, a sync cut off after any page loses nothing. `Sync.exchange(..., pageOps)` pulls pages until `more` is clear, then pushes pages of what the peer lacks; `SqlTrackStore.page` reads at most `maxOps` rows per device, not the log. Defaults: 2,000 operations and 1 MiB per page. Measured on this machine with a 50,001-operation log (fifty 1,000-fix tracks written one operation per fix, as T44 recorded them; `devtool sync gen`): push to the server peer in 26 pages, 1.34 MB gzipped in all; a fresh replica pulls it in 26 pages of about 52 kB gzipped in 10.4 to 11.1 s, against 9.3 s for one 1.34 MB bundle (page 10,000: 6 pages, 10.8 s); the replicas' digests match and their tables match their logs; a repeat sync is one 73-byte page in 52 ms.

**Format** (version 1, and version 2 for pages; `OpCodec`, `Bundle`): LEB128 varints (signed ones zigzag), doubles as 8 bytes little-endian (exact, so a GPX survives a sync byte for byte), strings as length + UTF-8 (nullable ones length + 1, 0 for null), ids as a tag byte (1 + 16 bytes for a canonical lowercase UUID, 0 + string otherwise, 2 for none). An operation is its HLC (wall, counter, device), a type byte (1 put, 2 set, 3 append, 4 delete), a kind byte (1 track, 2 waypoint, 3 route, 4 setting), the id, then the type's fields; a recorded fix is 76 bytes. A bundle is `DSYNC`, a version byte, the sender id, base vector, vector, count, then each operation as length + bytes; gzipped on the wire and in files. A page with more to follow is version 2: a flags varint (bit 0: more) after the vector; every other bundle is still written as version 1, byte for byte, so older builds read files and unpaged replies. HLC text (the database key, vectors in URLs): `<wall, 12 hex>.<counter, 6 hex>.<device>`, which sorts like the HLC. Any malformed input (truncated, corrupt, random bytes, a broken gzip stream, a bad HLC text or vector) throws only `SyncFormatException` (T51; a truncation sweep at every length and 9,000 random inputs and byte flips in the tests).

**Transports** (`SyncTransport`): HTTP against any `SyncServer`: `POST /sync/pull?since=<comma-separated HLC texts>` returns a gzipped bundle, `POST /sync/push` takes one and answers JSON with the merge counts and the vector, `GET /sync/status`. The devtool server (`serve`, both modes) is the always-on peer, its replica in `out/sync/peer.db` (`DYSTOPO_SYNC_DB`). A `.dsync` **file**: syncing with it merges what it holds and rewrites it with everything this replica holds, so one file passed between devices (adb, USB, a shared folder) keeps them in step; `devtool sync export --since <vector>` writes an incremental one. Phone: "Sync now" and "Sync status" in the tracks list (the `peer` setting, else the online server), `POST /sync?with=<url|file>[&page=N]`, `GET /sync/status`, `POST /sync/settings?peer=&token=`, `GET|DELETE /sync/conflicts`, `POST /sync/ui?open=1`, `POST /sync/field` (debug). The sync status sheet shows the peer, the last sync (what moved, pages, bytes, or the error; kept across restarts), the operations the peer did not have at the last sync plus everything since (`pendingFor` the stored peer vector), the fields edited on two devices, and what the clock guard saw. HTTP requests carry `Authorization: Bearer <token>` when a sync token is set (the `server` module's gate). Pull requests take `&limit=N&maxBytes=B` (capped at 100,000 operations and 64 MiB; without `limit`, the whole bundle as before). JVM: `devtool sync status|with|export|import|import-gpx|rename|gpx|gen --db <file>` (`with --page N --token T`).

**Encryption (T72).** Two transports between phones carry the log end to end encrypted, and the server relays without reading: the LAN link of T54 and a relay on the server (`/sync/relay`) for phones that are not on the same network. Code: `shared/.../sync/crypto/` (pure Kotlin, no dependency) and `shared/.../sync/EncryptedBundle.kt`.
- *Cipher:* ChaCha20-Poly1305 as in RFC 8439 (`ChaCha20Poly1305`, `Poly1305` in 26-bit limbs with a mask-selected final reduction), checked against RFC 8439's vectors (2.3.2, 2.4.2, 2.5.2, 2.6.2, 2.8.2, A.3 #1 and #5 to #11, A.5) and, on the JVM, against the JDK's `ChaCha20-Poly1305` cipher and a BigInteger Poly1305 on random inputs at every block boundary. HMAC-SHA256 and HKDF (RFC 4231 and RFC 5869 vectors) over the shared `Sha256`.
- *Share code:* 16 characters of Crockford base32 (`0-9 A-Z` without `I L O U`; `I`/`L` read as 1, `O` as 0, case, spaces and dashes ignored), 80 random bits from `SecureRandom`, shown as `7K3M-QW2D-9XHP-T4CA`. The LAN link and the relay use the same kind of code; it replaces T54's 6 digits (below, why).
- *Keys:* per message, `HKDF-SHA256(salt = 16 random bytes, IKM = the canonical code in ASCII, info = "dystopo seal v1 <purpose>", 44 bytes)`, the first 32 the key and the last 12 the nonce. The salt is the per-message (per-session) nonce and travels in the clear; a fresh one per message means no key and nonce pair repeats. The purpose (`relay bundle`, `lan request`, `lan response`) separates keys, so a frame of one kind never opens as another.
- *Frame* (`EncryptedBundle`, `DSEAL`): `"DSEAL" | version 1 | purpose | salt (16) | ciphertext | tag (16)`, 39 bytes over the plaintext; the associated data is the 23-byte header plus an optional context (a LAN reply binds the salt of its request). Any failure is one exception type with `authFailed` (wrong code or changed bytes, indistinguishable) or not (not a frame).
- *LAN link:* the listener answers only `POST /share/sealed`, whose body is a sealed `method | path?query | body` and whose answer is a sealed `status | content type | body` (`SealedLink`); hello, pull, push and status travel inside. The code never crosses the network. Wrong code: 403 and a failure (five rotate the code); a frame whose salt this session already served: 409; the T54 plain routes (`/share/hello?code=`, `/sync/pull?code=`, ...): 426, without looking at the request. A T72 client talking to an older phone gets a 404 on `/share/sealed` and says so; it never falls back to plain HTTP.
- *Relay:* a phone posts its whole log (`Sync.pack`, then sealed) to `POST /sync/relay?slot=&side=` and gets back the other sides' blobs (`RelayProtocol`, `RelayTransport`, a `SyncTransport` that behaves like a `.dsync` file kept on the server). The slot is `HKDF-SHA256(salt = "dystopo relay slot v1", IKM = code, info = "slot", 16 bytes)` in hex, the side a random 8-byte id per session; the server keeps one blob per side, at most 4 sides per slot, in memory, for 15 minutes after its last write, and never merges. Each phone polls every 5 s while its blob is alive and syncs again when a newer blob appears, so two phones converge in whichever order they act, without being online at the same moment. The server endpoint is open (no bearer token: it only holds ciphertext under unguessable slots); limits and config in docs/SERVER.md, The relay.

**Threat model (T72).**
- *What the relay server learns:* the slot (a one-way function of the code), the random side ids, the client addresses, blob sizes and timing (when each phone posts and polls), and that two addresses share a slot. Not the code, not any track, name, point, setting or device id, not the number of operations beyond what the size suggests. A blob opens with the code only: the relay tests (`RelayTest`, `EncryptedBundleTest`) store real bundles and check that other codes, including codes one character off, fail authentication and that no track name appears in the stored bytes.
- *What a LAN eavesdropper learns:* the addresses and port, the NSD announcement (`Dystopo <model> <first 4 characters of the device id>`, as in T54), and sizes and timing of `POST /share/sealed` requests; the inner paths, vectors and data are encrypted.
- *Why 80 bits:* anyone holding one encrypted message (the relay operator, someone recording Wi-Fi traffic) can test codes offline, as fast as HKDF and one Poly1305 run: on the order of a million codes a second per CPU core, far more on a GPU. T54's 6 digits (10^6 codes) would fall in about a second, so a 6-digit code would protect against nobody who records traffic; rate limits cannot help against an offline attack. 80 bits (1.2 x 10^24 codes) is out of reach for any attacker, so no key stretching is needed. The cost is typing 16 characters instead of 6 when the QR code or a link cannot be used.
- *Online guessing* is also bounded: on the LAN, five wrong codes replace the code on the screen, and the listener exists only while the Share screen is open; on the relay, a wrong code is not even detectable (it is another slot), each address gets 120 requests a minute (429 beyond), and a blob lives 15 minutes.
- *Active attackers* can drop, delay and replay but not forge or modify (Poly1305 tags). A replayed LAN request is refused (409; the code changes whenever the screen reopens, so a recorded session cannot be replayed into the next one); a replayed or stale relay blob is harmless (merging old operations again changes nothing). A malicious relay can refuse service or withhold blobs.
- *Whoever has the code is the other phone:* it can read the whole log and add to it, as in T54. The LAN code is new each time the Share screen opens; a relay code is new with each "New code". A `dystopo://share` link only fills in the fields: the user taps Sync or Join, since a link naming someone else's address and code would hand them the log.
- *Not provided:* forward secrecy (someone who records traffic and later learns the code can read it; a PAKE such as CPace or SPAKE2 would fix that and also allow short codes, at the cost of elliptic-curve arithmetic we do not have yet); authentication of devices beyond the shared code (per-device keys are the peer-to-peer plan); hiding metadata (sizes, timing, addresses). Running the relay behind HTTPS (docs/SERVER.md) hides the slot ids and sizes from the network path; the content is protected either way.

**Migration.** `2.sqm` (schema 3) adds `sync_op`, `sync_vector`, `sync_meta` and `waypoint.created_hlc`; existing rows stay as they are, and the first open seeds the log from them (one put per track and waypoint, one append per segment, stamped by the new device id), keeping every id. `TrackDbMigrationTest` checks that a version-2 file with tracks, a recording flag, segments and waypoints keeps them, seeds once, and syncs to a fresh store with identical GPX. `3.sqm` (schema 4, T60) adds the `route` table, a materialised view of route operations like `track` (fields, the encoded path and waypoints, the first put's HLC for list order, and the summary numbers: distance, ascent, descent, hike-model time, via and waypoint counts, metres off trail); the first open after it fills the table from the log once (`sync_meta` `routes`). The test builds a version-3 file whose log holds a pre-T60 route and a planned one and checks the rows equal the log.

**Verification.** `devtool sync-sim --peers 3 --ops 2000 --seed 42 --partitions 5 --reorder [--seeds 20] [--store sql]`: in-process peers make weighted random changes (recording, new segments, imports including the same file on two peers, racing renames, waypoints, deletes and re-imports, routes, settings) while syncing over a simulated network with latency, 5 % loss, duplicates, reordering (latencies spread so messages overtake each other), gossip relays of other peers' bundles (which exercise the gap rule) and partition episodes; then the partitions heal and syncing continues until every vector and state agree. A run converges when all peers have the same state digest and vector, equal to a fresh replica merged from the union of all operations; with `--store sql` the peers are `SqlTrackStore`s and each one's tables must also equal its log rematerialised. Runs are deterministic from the seed (the report's `replay` line reruns a failure), and SQLite and in-memory peers produce identical runs (`SqlSyncTest` asserts it). T51 adds `--skew-days D` (or `--big-skew-ms`: the last peer's clock D days ahead, negative behind), `--crashes N` (peer 1 crash-restarts N times during the change phase: down 30 s, messages to it and its in-flight syncs lost, back from its durable state: the same SQLite database reopened by a new store, or the in-memory log reloaded) and `--page N` (pulls in pages, the receiver asking for the next at once). 20 seeds (42 to 61) with `--skew-days 2 --crashes 3` converge with memory and with SQLite peers (identical runs), as do `--skew-days -2 --crashes 3` and `--skew-days 2 --crashes 3 --page 50`; the guard merged about 1,200 to 2,700 far-ahead operations per run without observing them.

**Limits.**
- Tombstones are kept for 180 days (`compact`); a replica offline longer than that can resurrect something deleted in the meantime with its stale operations.
- A device whose clock runs far ahead still wins every concurrent field edit until real time catches up, and devices that edit what it touched follow its clock (bounded at 30 days ahead); the guard only stops clocks moving on receipt alone. Detecting the skew at sync time (compare the peer's reported time and warn) would help; not built.
- Conflict detection is a lower bound for concurrency (no per-operation causal history); a later edit on another device that replaced this device's value is reported too, which is what the note says.
- No signatures: the `server` module's bearer token gates `/sync*`, but anyone with it (or who can reach `devtool serve` on 127.0.0.1) can read and write the log. Keys per device and signed operations are the [peer-to-peer](#peer-to-peer-long-term-goal) plan. The phone-to-phone transports (LAN link, relay) are encrypted under the share code since T72, but the code is a shared secret, not a device identity, and there is no forward secrecy (Threat model above).
- Route waypoints are one list field, not entities: concurrent waypoint edits on two devices keep one device's list. Superseded `path` values are never compacted.
- Concurrent appends from two devices to the same segment interleave by HLC; a recording is expected to come from one device.

### Peer sources on a trip (T78, as built 2026-10-12)

One phone that holds the sources serves the others on the same network (Design goals, principle 6). Everything rides on the T72 sealed link, so the T72 threat model applies unchanged: whoever lacks the share code sees one `POST /share/sealed` per request, with sizes and timing, and nothing else.

- **Publishing.** While the Share screen is open, the share listener also answers the peer-source routes (`share/PeerServe.kt`), only inside a sealed frame (plain requests for `/peer/...` are 426, like the sync routes): `/peer/catalog` is the phone's pack catalog in the server's `/catalog` format (`PackCatalog`, a SHA-256 per archive, file URLs `/peer/file/<file>`, plus `publisher`: the phone's name and device-id prefix); `/peer/areas` and `/peer/areas/<id>` are its T75 areas and their manifests (a pack-backed box as `pack` items with this link's URLs and hashes); `/peer/file/<file>?from=&len=&sha=` is up to 4 MiB of an archive per reply (409 when `sha` is no longer the archive's hash); `/dem` and `/osm` tiles come from its packs, then its online tile cache (corridors it downloaded), never fetched or generated for a peer. The archive hashes are computed once when sharing starts (about 1.1 s for the 227 MB Rainier pair on the emulator) and recorded like a catalog download's. Every request names its sender (`by=`, and `POST /peer/hello` with its name); the Share screen lists "Maps sent from this phone" per phone with bytes, archives and tiles (`serving` in `GET /share/status`).
- **Finding a peer.** A peer is added with its address and code (Share screen: "Use its maps"; `POST /share/peers/add`), or by discovery: the phone keeps the codes it has used (`POST /share/peers/code`, the trip's code) and tries each once on every phone NSD resolves, skipping its own announcement; a phone that has the code sees a new phone's catalog within about 0.1 s of NSD reporting it. Codes are tried once per phone and address, so a wrong code costs the other phone one failure of the five that replace its code.
- **Using it.** A peer with a catalog becomes a source of the online fetcher (`peer://<host:port>`, `share/PeerHttpGet` over the sealed link), tried **before** the server or the phone's own source readers over the network, with its own cache key and per-source counters (`sources[].fetched/bytes` in `GET /online`). Packs download through the same `PackDownloader` as from a server (`PackCatalogClient.downloadFrom`): the downloader's connection became an interface (`RangeConn`), and `share/PeerFiles` answers it with an HTTP-like 206 over sealed 4 MiB pieces, four in flight, so the plan, the resume from the part file and the SHA-256 check are the same code; a file that changed on the other phone fails as a hash mismatch with nothing installed. A peer's area downloads as its pack (recorded as a pinned area) or, for a corridor, through `AreaDownload` with the peer as a fetcher source. The job records `server: peer://...` and `via: peer <name>`.
- **Not built, designed.** *Bluetooth LE* carries only discovery and pairing: an advertisement with a service UUID and a 16-byte rotating token (HMAC of the share code and a 10-minute time slot, so only phones with the code recognise it and a passer-by cannot track the phone across slots), and a GATT read that returns the LAN address and port (or a Wi-Fi Direct group's credentials) sealed under the code; the bulk transfer then runs over the LAN or a Wi-Fi Direct group exactly as above, because BLE moves tens of kB/s and a pack is hundreds of MB. Signed catalogs (per-device keys, the peer-to-peer plan) so a phone can vouch for packs it relays.
- **Kept across restarts (T90).** A peer is written to `files/share/peers.json` (`share/PeerStore.kt`: address, code, name, device, NSD name, last seen and its last catalog and areas; plus the known codes, at most four, and the address overrides). At launch the map screen loads it: each kept peer is listed at once (`state` `saved`, its packs from the kept catalog) and tried in the background (at once, then 15 s doubling to 5 min) and whenever discovery resolves a phone at its address or under its NSD name; it becomes a fetcher source again only once it answers. One that does not answer stays listed as `unreachable` with "last seen" until forgotten (Forget on the Share screen, `DELETE /share/peers`). A kept code that no longer opens the link (the other phone's Share screen was reopened) stops the retries (`codeChanged`), because each wrong try spends one of that phone's five failures; a code is dropped from the known list when its peer answers with a new one. The address and code are the whole sealed-link state: each frame's key comes from the code and the frame's own salt. T96 (`share/PeerCodes.kt`): a refused code is never sent to that phone again by any path and the refusal is kept in the file, a kept peer's phone gets only its own code from before, any other phone at most one code from before per app start, Forget retires the peer's code, and a burst of requests sends one first when its code has not answered for a second and the rest only after its answer; measured on two emulators, a relaunch with four known codes and a cold map view right after the sharer reopened its screen each cost the sharer one failure (T90's verifier saw five, T96's seven, each with a new code).
- **Whole replies (T90).** The share port has its own listener (`share/ShareListener.kt`) instead of a second loopback-server instance: after a reply it waits for the client to close first (the client reads Content-Length bytes, then closes; the listener gives up after 30 s plus the body's time at 100 B/s, T96: at most 2 min, with at most 32 sockets waiting on one thread), and a reply that makes no write progress for 60 s is closed by a watchdog (the write deadline), so a dead peer does not hold a worker. Cause and measurements below.
- **Limits.** The sharing phone's Share screen must stay open (the code dies with it, and a kept peer needs the new code after it reopens). The phone serves only what it holds; it does not fetch or render for a peer. No forward secrecy (as T72).

### Routing (as built, T45, T49, T60, T68, T73, T76, T77, T89)
Our own router in `shared/.../routing/` (pure Kotlin, so phone, server and devtool share it; BRouter and GraphHopper were the alternatives, JVM-only and far larger than a trail network needs). Long distance (T77) sits behind the same interface: a drive overlay over the graph tiles, and the server as a remote router for the phone (below).

- **Graph.** `RoutingGraphBuilder` reads the `transportation` lines of a vector pack at its deepest zoom (capped at 14; both schemas hold every line there), clips each line to its tile, snaps vertices within 1 m, adds junctions where lines cross (not bridges and tunnels), splits at junctions and samples the pack's DEM every 25 m for each edge's ascent and descent. Every line therefore ends at a z14 tile border, which is what lets graphs of different packs meet. Rainier (3.4 MB outdoors pack): 4,675 nodes, 5,098 edges, 2,072 km, built in 0.7 s on the desktop.
- **Graph tiles (T76, principle 5).** `GraphTiler` cuts the pack's graph into tiles at z11 (`GraphTiler.ZOOM`): an edge crossing a tile border is split there and the cut becomes a node written into both tiles at the same microdegrees; its parts share the edge's length, ascent and descent by length, so they keep its average grade and cost exactly what it did. Pack graphs have no cuts at z11 (their edges already end at z14 borders). Measured on Rainier (whole graph 3.45 MB in memory with its adjacency and nearest-edge indexes): z10 is 9 tiles and Paradise to Panorama Point reads 2.2 MB of them; z11 is 20 tiles and the route reads 2 tiles, 0.61 MB; z12 is 56 tiles and 0.35 MB but longer routes cross many more borders. z11 it is.
- **File (`<vector archive>-graph.idx`, `DYSG` version 4 since T73).** A header (source archive, both pack fingerprints, source zoom, tile zoom, and since version 4 a capability byte: drive) with a tile directory (x, y, length, node and edge counts), then one body per tile (nodes, edges with class, surface, SAC, flags, length, ascent, descent, geometry and names), each with its own FNV-1a checksum; `GraphTileFile` documents the layout. Readers open the header through ranged reads and load tiles on demand. Version 2 (one graph per pack, T45 to T68) and version 3 (T76, before the drive data) are refused with a message saying so and rebuilt: that is the migration. Version 4 adds a speed-limit byte per edge after the names of each tile body; the T73 bits ride in the existing flags byte. The file is 1 % larger than version 2 (Rainier 400,760 bytes against 398,245). Version 5 (T89) marks bridges and tunnels in each edge's attribute byte and adds per node a level byte and the two component labels (below); version 4 files are refused and rebuilt the same way.
- **Loading.** `TiledGraph` looks a tile up in every pack's file; `GraphTileCache` keeps decoded tiles (with their derived indexes) under one byte cap, least recently used dropped first (32 MB default on the phone and the server). A node within 2 m of a z14 border (the deeper of source and tile zoom) is a boundary node: the router looks for its twin, a node at the same place, in the pieces of the tiles around it. In one file twins match exactly; between two packs (lines clipped separately) within 2 m. Overlapping packs simply give parallel copies of the same network joined at every z14 border, so no pack has to win a tile.
- **Router.** `Router` is an interface: `route(from, to, mode, snap)` and `nearest(point, radius)`; `TileRouter` implements it with bidirectional A* (average potentials, so both searches stay consistent and the result is optimal for the cost model; direction-aware costs, so the backward search prices each edge in travel order), and `Router(graph)` routes on one in-memory graph. A remote router or a hierarchy for long routes (T77) is another implementation; directed edges (T73 one-ways) fit the same search through the edge flags and the per-mode `CostModel`. Separate networks fail as soon as either search runs out of nodes. Each result reports `memory`: tiles read, their bytes, and the search's own arrays.
- **Where it runs.** The phone (`RoutePlanner`) opens or builds the graph file of every pack with a vector archive (the primary only goes first), and plans over the packs whose box is within 5 km of the route's ends; `RouteEditor` (trips) takes the same `Router`. The server (`RouteRoutes.kt`) does the same for the packs in `out/` near the route's points. `devtool route` reads and writes the same file.
- **Numbers (T76).** Paradise to Panorama Point on the Rainier pack is unchanged: 2,953.3 m, +416.4 m, cost 6,284.5, 223 points from the router (`devtool route`), 2,953.3 m, +401.6 m, 1:16 in the trip summary on the server, as T68 logged; the search settles 55 nodes instead of 227. With Rainier cut into a south and a north pack at the z14 border at 46.8000° N (`pmtiles extract`), the same route crosses from one pack into the other with the same points (224 then; 223 since T89, below); the trip climb is +404.6 m instead of +401.6 m because each half's DEM ends at the border (samples within a pixel of it fall back to the nearest one). Memory for the route, the same on the phone (API 35 emulator, `GET /route/status` `lastRoute`) and the server: 2 graph tiles, 0.61 MB, plus 57 KB of search state, against 3.45 MB for the whole graph held before T76; across the two halves 3 tiles, 0.61 MB. On the phone the Rainier graph file builds in 2.6 s (the halves in 0.8 s and 1.3 s), and the route plans in about 2 s including that first tile load.
- **Drive mode (T73).** A third `TravelMode`, `drive`, for getting to a trailhead and between trailheads inside the packs; the app says plainly that it is not a road navigator (`Router.DRIVE_NOTICE`, shown on the route card, the trip card and the browser trip card). The outdoors profile (version 2) carries `oneway` (1 or -1; roundabouts and motorways implied), `motor_access` (`no`, `private`, `destination`, from `motorcar` > `motor_vehicle` > `vehicle` > `access`) and `maxspeed` (km/h) on roads and tracks from z12, and road `name`/`ref` at z14 so a drive route names its roads; `dystopo:profile_version` says `2`. The graph keeps trunks and motorways (hike and bike cost them infinite, and they join only other roads where lines cross without a shared vertex, so trail edges are not split), one-way and motor bits in the edge flags relative to the edge's from-to direction (a line drawn twice in opposite directions is two-way), and the speed byte. Edges are directed for drive only: the cost model's `allows(edge, forward)` refuses a one-way the wrong way, and the bidirectional A* already prices each step in travel order, so the backward search needs nothing else. Cost is travel time as metres at 130 km/h (`length x 130 / speed`, tagged `maxspeed` clamped to 5..130, else motorway 105, trunk 85, primary 75, secondary 65, tertiary 55, minor 40, service 20, track 15 km/h; unpaved 1.25x), so the heuristic weight is 1. Paths, footways, cycleways, bridleways, steps and `motor_access` no/private are closed; `destination` roads are open only in the zone joined to a route's end through other destination roads (first or last leg). Drive ends snap only onto roads open to cars. The router's time is the sum of each road's time; since T89 a routed drive leg keeps that time in the trip's path (`RouteLeg.timeS`) and the trip summary adds it up, so every place shows the router's number (45 km/h only for straight and imported legs; below). A graph built from a pack without the road data (outdoors profile 1, or a schema we cannot read) has `drive = false`; drive mode near it fails with `drive_unsupported` naming the file to rebuild, and hike and bike on it are unchanged. OpenMapTiles packs count as drive-capable (their `oneway` and `access=no`; class speeds; checked on a real pack in T89, below). Hike and bike costs, snapping and results are unchanged: the fixture goldens and `devtool route` on the Rainier pack give the same numbers as main (2,953.3 m, +416.4 m, cost 6,284.5, 223 points hiking; 3,006.7 m, cost 13,997.5 cycling).
- **Drive numbers (T73).** Paradise to the Sunrise visitor centre on the rebuilt Rainier pack (`devtool route --mode drive`): 81.9 km, 1:26 by the router's speeds, via Longmire-to-Paradise Road, Stevens Canyon Road, SR 123, Mather Memorial Parkway (SR 410) and Sunrise Park Road (secondary 48.0 km, tertiary 27.7 km, primary 5.8 km, service 0.4 km), never a trail; the hike over the Wonderland Trail is far shorter and is refused. The graph grew to 8,465 nodes and 9,519 edges with 33.5 km of trunk. On the pack built before (profile 1) drive answers `drive_unsupported`.
- Out of scope for drive (stated in the app and here): turn restrictions and turn costs, conditional and seasonal closures (Stevens Canyon Road and SR 410 over Chinook Pass close in winter; the packs do not know), traffic. Long drives across packs: T77, below.
- **Long distance: the proposal (T77, written before building; T84 turns it into an ADR).** Goal: the drive from New York to Los Angeles and the ride between towns, without the phone ever holding a continental graph. The alternatives, measured on this machine on 2026-10-12:
  - *GraphHopper on the server* (9.1, Apache-2.0 core). Imported the Washington extract (365 MB PBF) with a car CH profile in 88 s, peak heap about 2 GB, 327 MB on disk, 2.73 M nodes and 3.43 M edges; warm queries 3 to 15 ms (Seattle to Yakima 229.3 km in 8 ms, Bellingham to Walla Walla 548.0 km in 14 ms, Paradise to Sunrise 81.936 km, the same as our 81,937 m). Linear scaling to the US extract (about 30 times Washington) suggests most of an hour and tens of GB of heap per import (not measured). Against it: it pulls `osmosis-osm-binary` (LGPL-3.0), which our licence rule allows only in `tilebuild`, not in the server; it is a second import of the network from the PBF, separate from the pack graphs the phone snaps to and names its roads from; it needs the whole region's PBF on the server.
  - *Valhalla* (MIT, C++), a container beside the server. Not measured: Docker is not installed here, and nothing we ship could test it. Same second-network objection.
  - *Contraction hierarchies per region pack, with an overlay for long edges.* A CH needs the whole graph to contract, and two packs' CHs do not compose: joining them takes exactly a border overlay between the packs. So the overlay is the part that matters, and it can be built on the graph tiles we already have.
  - **Decision: a partition overlay over our own graph tiles, on the server, with the server as a remote router for the phone.** The z11 graph tiles are the cells of a one-level multi-level-Dijkstra overlay (Delling et al., customizable route planning): per tile of one pack, the border nodes where a tertiary or larger road open to cars crosses the tile border, and the exact cheapest in-tile drive between each pair of them. A long drive searches the tiles within 5 km of its ends in full and every other tile through its overlay, then expands the shortcuts back into the tile's edges, so the result has the pack graph's points, names and numbers. It composes across packs the way the tiles do (cells are per pack and tile; a tile where two packs overlap or meet is searched in full), is built per tile independently (12.5 ms a cell on average on the statewide graph, about 130 ms in central Seattle) and needs no new import. The phone asks the server (`RemoteRouter` behind `FallbackRouter`) only when an end lies beyond every pack on it, keeps the answer as a trip's geometry, and the trip's corridor download (T75) is what lets it navigate offline. No GPL or LGPL, no second network.
- **Long drives as built (T77).** `DriveOverlay` (shared) builds cells on first use (an LRU of 4,096 cells on the phone, 65,536 on the server, about the contiguous US at z11), and the server warms every tile of a pack in the background once its graph is open (`GET /route/status` `driveOverlay.warm`). `TileRouter(tiles, overlay)` uses it in drive mode when the ends are 40 km or more apart; when that finds no route (a drive that can only cross a tile border on a minor road) it searches again in full. Cells are keyed by the graph file's `GraphSource`, and the base tile of a cell is decoded only to build it or to expand a shortcut the route used. Exact within cells, approximate across them: on the six Washington drives measured below every route was identical to the full search (distance, points, time); on the synthetic grid of `DriveOverlayTest`, whose even lattice of minor roads is the worst case, two of five drives cost 1 to 5 % more. Hike and bike never use it. The router now tells graph files apart by `GraphSource`, not by a piece's index, which a shared tile cache can hand to a later router whose packs are in another order (the T76 tolerant join between packs depended on that index).

On a synthetic pack of two unconnected grids the refusal settles 0 nodes instead of exhausting a grid.

### Concurrency
- Kotlin coroutines + Flow throughout.
- CPU-heavy work (DEM decoding, contour generation, tile rendering) runs on `Dispatchers.Default`, which sizes to the device's cores. Large jobs are split per tile so they parallelize. This is where multi-core and hyperthreaded CPUs pay off.
- I/O (disk, network, database) runs on `Dispatchers.IO`. GPS tracking runs in a foreground service.

Build and explore ideas first; the full system comes later.

## Agent-driven development
Agents can't tap a screen or watch a map scroll, so every feature also needs an interface an agent can drive.

### Principles
1. **Logic lives in `shared`, not the UI.** Anything in the shared module can be tested on the JVM in seconds, with no emulator. The UI layer stays thin.
2. **Every feature ships with its debug hooks and tests.** A feature isn't done until an agent can trigger it, observe the result, and check it automatically.
3. **Everything is deterministic and injectable.** Clock, GPS location, network state, file system, and random seeds are interfaces that tests can replace with fakes.
4. **Output an agent can read.** Structured JSON logs and state dumps, plus PNGs for anything visual (agents can view images).
5. **Debug tooling ships only in debug builds.** It's compiled out of release builds.

### Tooling layers
| Layer | What it is | Used for |
|---|---|---|
| JVM unit tests | `shared` module tests, run with Gradle | Geo math, DEM decoding, contour generation, sync logic, storage |
| Dev CLI (`devtool`) | JVM command-line app that calls into `shared` | Exists: `render`, `compare`, `areas`. Later: tile export, `sync-sim --peers 3`, PMTiles/GPX inspection |
| Golden-image tests | Rendered tiles and screens compared against approved PNGs | Map rendering, hillshade, contours, UI screens (Roborazzi/Paparazzi run Compose screenshots on the JVM) |
| Sync simulator | Many in-process peers over a fake network with latency, partitions, and reordering, driven by a seed | Proving offline/online convergence; any failure replays exactly from its seed |
| In-app debug server | Debug builds run a small HTTP/JSON server, reached via `adb forward` | Query state, invoke actions, inject GPS fixes and tracks, toggle offline mode, load fixtures, dump the DB, fetch logs, take screenshots, read map camera/layers |
| UI end-to-end | Maestro flows (YAML) or UI Automator, run against the emulator | Critical user journeys |
| Server debug endpoints | Same debug API on the Ktor server; local multi-peer setup via Docker Compose | Server-side state and sync inspection |

### Privacy in the repo
This is a public, open-source repo. **Nothing that reveals where the developer lives or travels is ever committed.**
- Personal test areas are defined in a gitignored local file (`*.local.*`, e.g. `devtool.local.json`). It can hold several named areas ("home", "trip") and be changed freely.
- Committed tests, fixtures, and golden images use only well-known public places. Initial defaults: **Mount Rainier, WA** (US, high-resolution USGS lidar) and **Mont Blanc / Chamonix** (non-US, Copernicus 30 m).
- Generated output, downloaded data, and caches go in gitignored directories (`out/`, `data/`, `cache/`).
- Test GPS tracks and waypoints are synthetic or come from public places. Real recorded tracks are never used as fixtures.
- The same rule applies to the app's debug tooling: logs and state dumps that may contain locations stay local.

### Command-line environment
- Gradle wrapper builds everything; no Android Studio required for agents (it's still useful for humans).
- Android SDK command-line tools + `adb` + headless emulator (`emulator -no-window`).
- Single entry points, e.g. `./gradlew check` runs everything that doesn't need a device; one script boots the emulator, installs the app, and opens the debug port.
- A `CLAUDE.md` at the repo root documents these commands and conventions for agents.

## Licensing
The project will be fully open source. Code and map content may need different licenses. Working choices: GPLv3 for apps, AGPLv3 for the server, LGPLv3 possible for `shared`; ODbL for OSM-derived vector tiles, CC BY-SA 4.0 for other content. These can be revisited later (see below).

### Hard rules
1. **Data compatibility.** Everything we produce must comply with the licenses of OSM (ODbL) and every elevation or other data source we use, including attribution.
2. **iOS compatibility.** Tiles, the sync protocol, and anything else other modules exchange must be usable by a future iPhone app. Tile formats and the wire protocol are open, documented specs, so any client can implement them regardless of the code license.
3. **Keep relicensing possible.** We can change the license later only as long as we remain the sole copyright holders. So:
   - Write our own code. Don't copy code from other projects into the repo.
   - Dependencies must be permissively licensed (MIT, BSD, Apache-2.0, EPL/EDL, etc.). **No GPL or AGPL dependencies anywhere.** Those would lock in our license choice. **LGPL is allowed only in build-side tooling** (`tilebuild`, later the server's tile pipeline) where the library stays a separate, replaceable jar; never in `shared`, the apps, or anything distributed to users. (Decided 2026-10-09 when Planetiler brought in GeoTools, LGPL-2.1: LGPL doesn't constrain the license of code that merely uses the library, so it doesn't threaten relicensing.)
   - No outside contributions until there's a contribution policy (CLA or copyright assignment).
   - An automated dependency-license check fails the build on any disallowed license. **Done (T7):** `./gradlew licenseCheck`, part of `check`; config in `gradle/licenses/`.
   - Versions already released under a license stay available under that license; relicensing applies going forward.
4. **Data source registry.** Every data source (DEM, OSM, overlays) is listed with its license, required attribution text, and allowed uses. Tile builds read attribution from this registry and write it into tile metadata.

### Code: GPL family
| Option | Effect | Fit |
|---|---|---|
| GPLv3-or-later | Anyone distributing modified apps must release their source | Default candidate for the apps |
| AGPLv3 | Also covers running modified code as a network service | Candidate for the server, so hosted forks must share changes |
| LGPLv3 | Others can use the library in closed apps; changes to the library itself must be shared | Candidate for the `shared` core if we want wide reuse |

- Use **v3**, not v2: Apache-2.0 dependencies (Planetiler, GraphHopper) are compatible with GPLv3 only.
- Expected dependencies are compatible with GPLv3: MapLibre (BSD-2), Planetiler (Apache-2.0), BRouter (MIT), GraphHopper (Apache-2.0), JTS (EPL-2.0/EDL dual license, use EDL).
- **iOS App Store vs GPL:** Apple's terms conflict with GPL distribution of code contributed by others. A sole copyright holder can grant Apple an exception or dual-license. Decide on a contribution policy (CLA or a GPL app-store exception) **before** taking outside contributions.
- F-Droid distribution works with any of these.

- **How the national 1 m sources are read (T59).** Norway: Kartverket publishes no range-readable COGs (hoydedata.no hands out zipped project blocks), but its WCS (`wcs.geonorge.no/skwms1/wcs.hoyde-dtm-nhm-25833`, coverage `nhm_dtm_topo_25833`, an ArcGIS image service) cuts any box at any resolution, so `NorwaySource` asks for fixed 256 px blocks on a UTM 33 grid at 1 to 16 m and caches each block forever; 0 is the service's fill (sea, and beyond a strip of coarser data that reaches 10 km or more into Sweden). Austria: BEV's ALS DTM tiles (`data.bev.gv.at/download/ALS/DTM/<edition>/`) are 7.7 GB Cloud-Optimized BigTIFFs on 50 km EPSG:3035 squares (not EPSG:3416 Austria Lambert), range-readable with overviews, so no whole-tile download is needed; heights are EVRF2000 Austria (EPSG:9274) from the 2022 edition on, GHA only in 2021. A whole-tile fallback was not needed for either.
- **Canada and New Zealand (T69).** Both are on the AWS open data registry and range-readable. Canada: NRCan's HRDEM mosaics (`canelevation-dem.s3.ca-central-1.amazonaws.com/hrdem-mosaic-{1,2}m/<i>_<j>-mosaic-{1,2}m-dtm.tif`, listed by the STAC API at `datacube.services.geo.ca/stac/api`) are one Cloud-Optimized BigTIFF per 500 km square of EPSG:3979 Canada Atlas Lambert (500000 px at 1 m, LZW, overviews to 512x, no-data -32767, sparse where no lidar was flown); the 1 m mosaic's tile index is about 15 MB per file, so it is read only for cells of 1 m or less, the 2 m mosaic (which also has the projects delivered at 2 m only) everywhere else. Heights are CGVD2013; PROJ's CGG2013a grid is relative to NAD83(CSRS), so the NAD83 -> WGS84 height shift is added as for the US hybrid geoids, and the grid is int32 with a GDAL scale (GeoTiff reads that now). Lidar coverage is patchy in the mountains: none at Mount Robson (Copernicus serves it), two blocks around Mount Garibaldi. 3DEP's 10 m base reaches well into southern British Columbia, so HRDEM goes over 3DEP in `best`. New Zealand: LINZ's national 1 m DEM mosaic (`nz-elevation.s3.ap-southeast-2.amazonaws.com/new-zealand/new-zealand/dem_1m/2193/<sheet>.tiff`) is one COG per NZTopo50 sheet (24 x 36 km of NZTM2000, 424 sheets), LERC-compressed (1 mm error, 10 cm in overviews), which our own `Lerc2` reader decodes; NZTM is UTM's transverse Mercator with a 2 degree longitude and 1100 km easting shift; heights are NZVD2016, converted with NZGeoid2016.
- **The phone reads the sources itself (T80).** With no Dystopo server set, the app reads the same public files the server does: the Copernicus GLO-30 COGs on AWS, USGS 3DEP 1/3" COGs and the 1 m lidar tiles through the TNM Access API, swisstopo's STAC API and COGs, Kartverket's WCS, BEV's download service, NRCan's and LINZ's COGs on AWS, the PROJ CDN geoid grids, and OpenFreeMap's public vector tiles (`tiles.openfreemap.org`, OpenMapTiles schema, ODbL data). The licences and required credits are the same rows as above; nothing is redistributed by us (each phone fetches for itself, a pack it builds stays on that phone), the map line credits what the view shows and the About screen lists every source the phone can read with its licence. Requests carry a `dystopo-android` user agent, at most 16 at once, and a phone downloads at most 300 MB per session (setting), so the public services see one person's map use, not a mirror.
- The likely result: **ODbL for vector tiles** (forced by OSM), and **CC BY-SA 4.0** (the share-alike, GPL-like content license) or CC BY 4.0 for raster tiles and non-OSM layers.
- Each tile set records its sources and attribution in its metadata, and the app shows attribution for every visible layer.

## Design goals (set 2026-10-10): one data path online and offline, precaching, long routes, sharing on a trip

The owner's longer-term goals, written down so that near-term work stays friendly to them. None of this is scheduled as a single task; the principles bind every task that touches tiles, caches, packs, routing or sharing, and the gaps are on the board (T73 to T78).

**Goals.** (1) Move between online and offline without the user noticing: whatever was fetched or built is kept, and what is likely to be needed is fetched ahead. (2) Keep what we build (contours, shade, cliffs, graphs) so nothing is rebuilt on every zoom; these caches are keyed by every setting that affects them and can be thrown away at any time. (3) On the phone, the disk the caches may use is a setting. (4) Let users say where they are going and download everything for that area or route ahead of time (what CalTopo and Backcountry Navigator call offline maps). (5) Route searches longer than one pack: rim to rim across the Grand Canyon on foot, a bike ride between two Colorado towns 40 km apart, a drive from New York to Los Angeles. (6) On a trip, one phone that holds the sources (packs, and maybe generated tiles) serves the others over the LAN or discovered Bluetooth, so a group is effectively offline together; whether to share generated tiles or regenerate locally is a question of relative cost, not principle.

**What already fits (as built through wave 11).** The phone's loopback server reads every installed pack tile by tile (`PackSet.demCandidates`/`osmCandidates`, precedence by profile, primary flag, zoom and area) and falls back to the online server only for tiles no pack covers; fetched DEM, vector and glyph tiles go into an LRU disk cache (`TileCache`, `onlineCacheMb`, default 256 MB), and contours over fetched DEM are generated on the phone and cached too. Derived caches are already keyed by what matters: contours by version, unit, tile size, interval and a DEM identity (CRC of size, mtime and PMTiles header); shade by hillshade mode, intensity, slope, night and DEM identity; cliffs by vector and DEM identity; one LRU with a user-set cap (`contourCacheMb`, default 256 MB) and garbage collection of directories whose pack no longer exists. "Download this region" builds a pack for the current view box on the server (`POST /build`, Overpass under the cap, else Geofabrik extracts on disk or downloaded on demand) and installs it with resumable, hash-verified downloads. Routes are stored as geometry (`path` field in the sync log), so navigation never depends on the router that produced them. For sharing, the phone already runs an HTTP tile server on loopback, a LAN share listener with NSD discovery and QR pairing (T54, encrypted since T72), and the pack catalog format with hashes and sidecars that the server uses; the phone could publish the same catalog.

**Principles from here on.**
1. *Everything on the phone is a cache in front of a source, and a pack is a pre-filled, pinned, immutable cache segment.* New code reads through one resolver (pack union, then disk cache, then a source) and never special-cases "the active pack". The primary pack survives only as a tie-breaker and as the camera's home; anything still keyed to it (contour warm-up, `RoutePlanner.ensure`) is a defect to remove, not a pattern to copy. A "source" is the server today; a peer phone on the LAN is another source behind the same interface (goal 6), which is why the online fetcher must not assume a single fixed server URL.
2. *Every cache key names its inputs and its version.* Settings vector plus source identity plus format version, so a change anywhere invalidates exactly what it must. Online tiles must carry the source's content version (today the online cache has no server version and no TTL, so a server DEM change is invisible until eviction); style assets must be versioned (today glyphs and sprites are never refetched if a file exists). Content hashes, not URLs, identify pack files, so the same pack from the server or from a peer is the same pack.
3. *Derived caches are never required for correctness and are always bounded.* Phone caches are bounded today; the server's `cache/live` and OpenFreeMap caches are not, and server contours and shade are not cached at all. Every store gets a cap and LRU, and one phone settings screen shows and sets the budgets (tiles, derived, packs) with what each is using. No Wi-Fi gates (owner, 2026-10-11): everything except LAN discovery works over mobile networks; data use is steered by visible limits the user can raise, never by a network-type check that silently fetches nothing. Generated tiles may be shared between phones only when the full derived key matches (same settings vector, same source identity); otherwise the receiving phone regenerates. On today's numbers (contour tile about 80 ms warm on the phone, a few KB each) regeneration usually wins over transfer; share sources first, derived tiles only where measured to help. T78 measured it (Sync › Peer sources on a trip): transfer beat regeneration only for tiles the peer already held, by at most 23 ms a tile, so derived tiles are not shared.
4. *An area of interest is a first-class object.* A box or a route corridor with a zoom range becomes a manifest (DEM, vector, glyphs, sprites, graph, search index, derived tiles optional), with progress, verification and a pinned flag that keeps it out of eviction until the user unpins it. "Download this region" is the box case of this; route corridors ("I am walking this") and "ahead of me along the route" prefetch are the next two cases. The server side is the existing `/build` plus per-area derived products. A manifest is also what one phone offers another: "I have these areas" is the catalog, and fetching an area from a peer is the same download code with a different base URL.
5. *Routing is tiled, not per pack.* The graph becomes graph tiles at a fixed zoom (built per pack as today but stored and loaded per tile, so a search spans packs and loads only what it touches), behind a `Router` interface with the current A* as one implementation. Long distance needs a hierarchy (contraction hierarchies or customizable route planning over the road classes) or a remote router behind the same interface, with the result saved as geometry plus a corridor download, so the drive from New York to Los Angeles is planned online once and navigated offline. The rim-to-rim walk and the 40 km ride fit one pack or two adjacent ones and only need the tiled graph and cross-pack stitching.
6. *Transports are pluggable and discovery is separate from transfer.* The sync layer already has file, HTTP and LAN transports with NSD discovery; pack and tile sharing uses the same shape: discover a peer (NSD now, Bluetooth LE advertising later, where the Bluetooth link carries only the discovery and pairing and the bulk transfer runs over Wi-Fi Direct or the LAN, because Bluetooth throughput is far too low for packs), verify what it offers by content hash, fetch over HTTP from the peer's loopback server made reachable on the LAN interface with the same per-session token and encryption as the share link. As built (T78): the share listener itself publishes the catalog, area manifests, archive pieces and pack tiles inside the sealed link (no second listener, no second secret), a peer is a `peer://` source of the online fetcher tried before the network, and packs come through the same resumable, hash-checked downloader; the Bluetooth LE design (discovery and pairing only) is written down there, not built.

**Gaps, on the board.** T74 cache coherence and budgets (versioned online tiles and assets, bounded server caches, cached online shade, the storage settings screen); T75 areas of interest (manifests, corridors, pinning, prefetch along a route); T76 tiled routing graph and cross-pack routes behind a `Router` interface; T77 long-distance routing (hierarchy or remote router, corridor download); T78 peer sources on a trip (phone publishes its catalog on the LAN, other phones add it as a source, measured decision on sharing derived tiles); T73 drive mode is the third travel mode and a prerequisite for the drive case.

**Areas of interest as built (T75, proposal for the ADR T84 will write).** An area is a box or a route corridor (a line and a buffer in metres) with a zoom range; its id is a hash of the geometry and zooms, not the name, so the same area asked twice or by two phones is one area. It expands to a versioned manifest (`AreaManifest`, field by field in docs/SERVER.md › Areas of interest) whose items are `pack` archives with SHA-256, `tiles` lists per route and zoom (rows `[y, x0, x1]`) with estimated sizes, bundled style assets, and products the phone makes itself (contours, trail graph, search index). A box is a region pack built through `/build` (the server answers `POST /area` with 202 while it builds, then the archives with hashes, so the phone's download is verified like a catalog download); a corridor is the DEM and vector tiles within the buffer (DEM from z6, because contour tiles sample coarser zooms than they show, and one tile of margin), fetched through the online fetcher into the tile cache and **pinned** there: the cache's eviction asks a spatial predicate (`AreaPins`) whether a key's z/x/y lies in a pinned area's cover, so DEM, vector and contour tiles of any source and any settings stay with one rule and no key lists. During navigation the next 3 km of the line (1 km segments, 300 m buffer, z12 to z15) are fetched ahead while online and pinned until navigation stops. Rejected: (a) a corridor as a pack of only its tiles, because the resolver ranks packs by their bounding box, so such a pack would shadow online tiles beside the corridor inside its box (blank vector tiles, coarse synthesized terrain even online) until the resolver checks per-tile presence; (b) a corridor as the pack of its bounding box, right for a short loop and wrong for a long drive, whose box is half a continent; (c) explicit key lists per area, which depend on the source URL and on every derived setting and grow with every contour tile; (d) per-tile sizes and hashes in the manifest, too large for long corridors and unknown to a server that renders tiles on demand (tiles are checked by type instead, packs by SHA-256); (e) a separate pinned store outside the cap, cleaner accounting but a second resolver lookup or a cache rewrite, left to T74, which owns the budgets: today pinned tiles count against `onlineCacheMb` and are skipped by eviction, so a cap below the pinned areas leaves the cache over its cap, visible in `GET /areas`. Packs stay until removed (unpinning a pack would mean moving its tiles into the LRU, which costs more than it saves).

The verifier measured the same cold Rainier z12 view at 77.5 MB in 150 requests, and split a 4 by 5 tile area by DEM zoom: z12 25.1 MB, z11 10.0 MB, z10 7.0 MB, z9 5.5 MB, so most of a view is the z8 to z11 ancestors read for contour sampling, not the hillshade's own tiles. OpenFreeMap tiles were about 4 MB of each view (low-zoom planet tiles are 0.8 MB each). Because a fresh view is 75 to 100 MB, direct reading is Wi-Fi only by default (`directOnMobileData`), and the per-session limit is a visible setting (`directSessionMb`, 300 MB) with a message on the map when it is reached. Most of the source bytes are whole COG blocks: a 3DEP 1/3" block is about 0.8 MB, a Copernicus block about 2.5 MB, and a z12 view touches dozens once the contour tiles' coarser sample zooms (z10, z11) are counted. The 15 s goal of the task was not reached on this emulator: the time is network-bound (the summed request time was 300 to 450 s over 16 connections), not CPU-bound; a phone on fast Wi-Fi should be several times faster, and with a warm source cache a render still takes about 4 s of emulator CPU, so a fresh view of a known place costs about a third of the cold time; tiles already rendered come from the online cache at once. What was done to cap it: Copernicus is skipped where a regional layer covers the whole window (same output; half the bytes of a US view), open COGs and their decoded blocks are pooled (96 files, 96 MB at most, a quarter of the heap), DEM tiles are rendered to z12 and synthesized deeper (`directMaxZoom`, 8 to 15), six renders and 16 source requests at once, map tiles never wait behind renders, a tile not ready in 8 s answers 503 and the map reloads when rendering is done (MapLibre does not retry a timed-out tile), 300 MB per session (`directSessionMb`), and the source cache (`cache/sources/`) is trimmed to 512 MB. Next steps that would cut bytes further, first one first: contour plans that sample the hillshade's own zoom when the phone renders terrain (the ancestors above are most of the bytes), then a coarser overview level for interactive phone views. T85 (2026-10-12) did both and found a third: the 4-cell halo of every contour tile read a whole ring of neighbouring DEM tiles, 14 of a z12 view's 20 renders. With direct sources a contour tile now reads the DEM at the hillshade's zoom (`ContourTileOptions.sampleAtDemZoom`; the grid is box-averaged down to the plan's, so levels and line counts match the pack: 11 Rainier tiles at z10 to z12, the same levels in every tile, 1228 lines against 1245, worst tile 9.9% fewer at z10), takes tiles the hillshade made or is making, renders a missing one only when it is in view or under a tile at the view's zoom (or MapLibre's fallback four zooms up), and leaves the out-of-view halo NaN (lines stop half a cell short of a seam nobody sees). Tiles MapLibre asks for while the camera is still moving are answered 503 once the view has settled elsewhere, and their queued renders are given up. DEM tiles below z12 read the overview for twice their cell size (it paid: a z10 view halves, a z12 view loses its z9 fallback bytes; hillshade at z10 shows no visible loss). Two older faults surfaced: MapLibre keeps a tile it got a 503 for across a reload of an identical style, so the T80 reload after rendering never reloaded anything (the reload count is now in the tile URLs; the first views before T85 showed only coarse fallback contours), and a contour 503 had to wait under MapLibre's 10 s timeout (6 s now). The 15 s target is still missed on this emulator: first contours 28 to 31 s, the time going to six concurrent 6 to 15 s renders.

## Units (decided 2026-10-10)
Feet versus metres is a **user preference, not a geographic rule**. Region only seeds the default: the browser demo picks feet inside the US and metres elsewhere the first time the page is opened and then keeps whatever the user chose (persisted); the phone seeds its default once from the home area if known (first pack opened, or first GPS fix) and never changes it on its own. Travelling keeps your units. Everything that shows an elevation or distance (contour labels and intervals, peak elevations, track stats, profiles, search results) follows the one setting. T34 shipped the by-region default; T33 (phone) and the viewer follow-up make it a persisted preference.
