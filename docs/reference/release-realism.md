# Release realism: `tools/android-ui.py` parts

Every device part drives the release build by taps alone. The sweep runs them (`.claude/skills/sweep/SKILL.md`).

## Parts

**Release realism** (T81; `tools/android-ui.py <part>`, one JSON object, numbered PNGs under `--out`: view them). Every device part except `routes` and `search` drives the release build by taps alone, as `android-firstrun.py` does (whose `Device` it loads): `features` (Rainier pack pushed; search, a long-press route kept as a trip and the Routes list, a recorded track fed by `adb emu geo fix`, GPX export, T91: a waypoint with no recording, by long-press and Waypoint here, and the long-press card's Route from here before the end press; Sync now against `--server`, the sync sheet, the Share screen's code, Settings), `upgrade --prev-apk <published APK>` (track, trip, metric units and the pack made on the old build survive `adb install -r` of the new one; the new APK needs a higher versionCode, so build it with `-PdystopoVersionCode=<git rev-list --count HEAD>` as `release.yml` does), `permissions` (location denied from the system dialog: the card says why "Download the map around me" cannot work; allowed; notifications at the first recording), `background` (record, Home, `dumpsys deviceidle force-idle`, fixes for `--bg-seconds`, back: the points arrived through doze), `network --server-config <server.json> --proxy-port <p> --server http://<LAN>:<p>` (the emulator throttled with `emu network speed/delay`; the part starts, kills by PID and restarts the standalone server mid-download, and a stall proxy in front of it holds the first `/sync` response so the kill lands mid-sync; failure shown, app alive, retry succeeds), `matrix [--font-scale 2.0] [--dark] [--label]` (contours drawn, the map chips and search box on screen and not overlapping, a route card, Settings › Sources reachable, location switched off and on with the map open), `update --prev-apk <published universal APK> --apk <this build> --new-apk <the same commit with versionCode +1> [--mock-port 9171]` (T83: the published build with the pack, a track and metric units, pointed from its first start at a mock releases API the part serves on 127.0.0.1 (10.0.2.2 to the emulator) by `update-api.txt` in its external files dir, so its own start-up check finds an older release and never depends on what GitHub publishes (T99, `previousCheckAsked`); this build installed over it, still on the mock; a lower release stays quiet, and this build's start-up check asks the mock although the previous build checked minutes before (`dailyCheckAsked`; since T99 a check recorded under another versionCode does not count, `UpdateFeed.CheckRecord`; before, v0.1.5-alpha's own check left this build not due for a day and the part stopped at `lower-quiet`); a lying `SHA256SUMS.txt` and the new APK re-signed with a throwaway key the part makes with `keytool` (T99; the debug key before, which a debug-signed build cannot refuse) are refused with the reason; the good one is offered on the map, Install is answered in the system installer by taps (T99: the part restarts the Settings app first, because a Settings process left from an earlier install of the app keeps the old uid and its "Allow from this source" switch then fails with AppOps "Cannot setMode"; the switch is tapped once, never again), and the new build runs with the track, the units and the pack; then Check for updates against the real API, read only, is quiet; the app's `DystopoUpdate` log lines from the whole part are in `updater-log.txt` under `--out` and the report's `updaterLines`), `strings --apk <apk>` (no device: dex string tables and printable runs of every other entry through `PrivacyCheck scan`; fails on a private term or local pair, reports the lenient single-value rule; T87: with no `devtool.local.json` the scan still runs and reports clean with `privateTermsConfigured` 0 and the note "0 private terms configured"), and on the debug build `routes --port <debug forward>` (`tools/routing-tour.txt`: public Rainier routes with distance within 0.1%, ascent, the named trails, and one deliberate off-network refusal; T91: a line with `pack=<name>` (the Grand Canyon lines, T89) pushes `out/<name>-outdoors.pmtiles` (and `-dem` when present; `--pack-dir` changes the folder) to the phone, reloads, plans, and deletes what it pushed; without that file the line is `skipped` with the reason, counted in `routesSkipped`, and does not fail the part) and `search --port` (`tools/search-tour.txt`: each query's top hit and kind). `--known a,b` reports filed defects without failing (none by default since T91 fixed `overlap:search/Settings`: the floating map chips follow the font scale up to 1.3, the search box ends before the Settings chip, the online indicator sits below the search column and the open track chips wrap before it; `notification-prompt` and `location-listener` were the two T81 fixed). T81 fixes found this way: Android 8 to 10 crashed whenever GPS started or was switched off, because `LocationListener` lambdas implement only `onLocationChanged` (the other three methods became default in API 30); use `tracking.locationListener {}`, and `LocationListenerTest` fails on a lambda anywhere in the app. POST_NOTIFICATIONS is asked once, at the first recording on Android 13+ (`tracking/NotificationPrompt.kt`); allowed, the running recording's notification is posted at once; refused, recording goes on without it. `android-emu.ps1` gained the matrix and network flags: `-Api <n>` (installs the image with sdkmanager when missing; images before API 30 also need `-Feature GLESDynamicVersion`, or the emulator offers only OpenGL ES 2 and MapLibre crashes in its render thread), `-Device pixel_tablet`, `-Locale de-DE` (at boot), `-FontScale`, `-Dark`, `-NetSpeed`/`-NetDelay`, and `-BootOnly` (no build, install or forward). T91, `tools/sweep.ps1`: the `first-run` part also runs `android-firstrun.py --direct` on the fresh release install (no server: Rainier and Mont Blanc from the public sources, mobile data, the phone's own download, offline; `first-run-direct.json`, screenshots in `first-run\direct\`), and the `upgrade` and `update` parts download the previous release's APK together with its `SHA256SUMS.txt` and stop unless the APK's SHA-256 matches its line; the tag, file and hash are kept in `previous.json` next to it. Both install this build over the published one, so they need the release key, which exists only in the main checkout (`machines.md`): a build signed with another key fails `install-new` with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. From a task worktree, leave them to the post-wave sweep, which runs from the main checkout where the key is, and to the `release` skill's install-from-draft step; the `update` part alone also runs with three release builds of your own signed with the debug key (no `tools/release.properties`), the previous one with a lower `-PdystopoVersionCode`, standing in for the published APK (T99).
