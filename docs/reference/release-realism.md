## The sweep's device parts (T105)

**Both units** (T139, T129's follow-up): `tools/sweep.ps1` (T147: in every sweep with a device, no longer opt-in; `-NoBothUnits` leaves it out, `-BothUnits` is still accepted; `-Only bothunits` alone) runs `android-ui.py bothunits` after the debug parts, on the sweep's emulator and a second one booted for it on the matrix pattern: AVD `<Avd>-b`, console `-MatrixEmuPort` (default `-EmuPort`+2), debug forward `-Port`+2, the same debug build and server, stopped and deleted afterwards. The peer is a standalone server on the script's own slot `-BasePort`+3 (bound to all interfaces, `http://10.0.2.2:<port>` to both emulators), started and stopped by PID. The report is `bothunits.json`, the screenshots of both phones are in `ui\bothunits\` and on the sheet, and `summary.json` has the part's carries (`a-on-to-b`, `b-off-to-a`: value and the receiving phone's `bothUnits`), the peer and the screenshots (T147: all four, both phones after each carry, from each step's `pngs`; before, the two of the receiving phones). A second emulator that does not start (`android-emu.ps1` exits non-zero: no room for a second AVD, its console port taken) makes the part a skip, not a failure: `steps.tsv` and `summary.json` `skipped` carry "skipped: the second emulator emulator-<n> (<Avd>-b) did not start" with the script's first error line.

**The sheet** (T111): `tools/sweep-summary.py` puts every PNG of a sweep on `sheet.png`, and Chrome captures at most 16,384 px of a page: the 2026-10-14 sheet was 17,383 px, so the capture repeated its top and lost the last demo tour section. A taller page now gets more thumbnail columns (6, then 7, 8, 10, 12; the world and device tour sheets 2, then 3) and, past that, is rendered at a device scale factor below 1; `summary.json` `sheetSize` has the PNG's `width` and `height` (from its header), `pageHeight` before fitting, `columns`, `bigColumns`, `scale` and `cut` (true only if the PNG still reached the limit). That sweep's outputs make a 1600 x 12,953 sheet at 7 columns with every section.

`tools/sweep.ps1` sets the debug build's server itself: `-DeviceServer live` (the default) starts its own `devtool serve --live` on `-BasePort`+2 for the debug parts (device boot, device tour, routes, search, probe) and gives the app `http://10.0.2.2:<port>`, `-DeviceServer direct` gives it none; `android-emu.ps1 -Server <url>|none` writes it into a fresh install's preferences before the first start (with `run-as`) and sets it again through `POST /settings?server=`, and `android-check.py --server` sets it before the tour. Before T105 the sweep inherited the debug build's default on an emulator, the host's 8765 (the coordinator's live viewer; the 2026-10-14 sweep's tours ran against it). `steps.tsv` names the server on the `device-boot` and `device-tour` lines, `summary.json` per tour run (`server`, `quietWaitS`, `firstViewS`). The release build has no default server: its parts run on the packs and the public sources unless they type one (first run, features, permissions, network). The release APKs are copied to `apk\` of the sweep folder once built (`apks.json`: file, bytes, SHA-256), and every release part installs those copies, because the `update` part's second build (versionCode +1) overwrites `androidApp\build\outputs\apk\release`. The device tour's first view waits until the device is quiet by its load (`android-check.py --quiet-cores 1.0`: the CPU used besides the app in two 3 s windows in a row, from `/proc/stat` and the app's `/proc/<pid>/stat`): on two fresh API 35 AVDs (four cores) the wait was 75 and 100 s, at 1.6 to 3.9 cores besides the app until it fell to 0.0 to 0.3, and the z8 view then took 16.6 and 11.0 s (`summary.json`: `quietWaitS`, `firstViewS`).

`tools/android-firstrun.py` (and `android-ui.py`, which loads it) times the map from raw frames (`screencap` without `-p`, decoded by slicing: a fraction of a second against 1 to 4 s for a PNG decoded without Pillow) by when each frame was grabbed, and a map counts as settled when it holds still (under 0.002 of the samples against the run's first frame) for 2 s, 5 s for the timed `--direct` views; those report `firstContoursS` (any contour pixels, MapLibre's coarse fallback lines included), `fullContoursS` (the first frame with half the settled frame's contour share) and `settledS`, and save only those frames as PNGs. While they wait for screen text they close another app's "isn't responding" dialog (Close app; Messages on a loaded emulator covered the first-run card once), listed in the report's `otherAppDialogsClosed`; one about Dystopo is left for the step to report. The first run's `catalogPacks` is the catalog count Test shows: the sweep's first-run server starts with an empty `out\`, so it is 0 until "Download the map around me" builds a pack there; the Rainier pair of the second install comes from the host through the file picker, not from that server.
