## The sweep's device parts (T105)

**The two packages on the sweep's emulator** (T303): the debug build is its own app (`<release id>.debug`, `android-app.md` › Two packages), so the release parts install the release beside it rather than over it; `android-release.ps1` still uninstalls an earlier release signed with another key. A crash line is matched to its own package (`android_debug.parse_crash(text, package)`, `crash_lines` in `android-ui.py`), since the release id is a prefix of the debug one.

**The owner's phone** (T303): `tools/sweep.ps1 -Phone <serial>` (opt-in; `-PhonePort`, default `-Port`+3, is the host port forwarded to the phone's debug server) runs after the emulator parts, on that serial and with the debug build only: `phone-attach` (the serial must be listed by `adb devices` as `device`, else the step fails with the reason, "refused: the phone <serial> is not attached ..." or "... attached but 'unauthorized'", and every later phone part is a skip; it reads the model, Android and the release install's facts), `phone-install` (aapt2 must read the APK as the debug id; `adb install -r -g`; a debug build signed by another PC's key is refused by name, never uninstalled; then the Rainier packs through `android-push-pack.ps1 -Package <debug id>`), `phone-tour` (`android-check.py --server none --fix 46.7864,-121.7366,1629 --no-offline --no-cards`: the fix goes by `POST /location` on the debug port after every restart, never `adb emu geo fix`; the offline and card steps are left out because they switch the phone's airplane mode, font scale, rotation and density), `phone-startup` (`android-startup.py --launches 5`, cold, over the seeded store, against no budget: the ceilings are the emulator's), `phone-diagnostics` (`python -I tools/android_debug.py get --path /diagnostics`) and `phone-release` (red when the release install was removed, replaced or updated during the run; a changed data listing, read only where `su` works, is a note). With `-Only`, the phone parts are filtered only when `-Only` names one of them (`-Only phone-tour -Phone <serial>` runs the attach step and the tour). Outputs in `phone\` of the sweep folder (attach, tour and its sheet, startup, diagnostics, release JSON); `summary.json` gets a `phone` section (the device's model and Android, never its serial; the tour's views and memory; the launches' medians and slowest stages; the diagnostics' heap and memory; the release install unchanged or not) and the sheet a Phone table and the phone's tour sheet. Safety as code: the phone parts' programs run with `DYSTOPO_PHONE_GUARD=<serial>`, under which `tools/android_debug.py` refuses any adb call to that serial that installs, uninstalls, runs `pm clear` or names the release package or its data (`PhoneGuardRefused`); the sweep's own calls go through `Phone-Adb` (and T304's strict reads, `Phone-Read`), the same rule, with only the release's reads (`pm list packages`, `dumpsys package`) let through. The debug app stays on the phone for the next run. What the owner does once: developer options on, USB debugging on (or wireless debugging, paired with `adb pair`), the PC's key accepted at the prompt; no mock location app is needed, since the fixes are the debug build's own `POST /location`.

**The phone parts over wireless debugging** (T304; the first run on the owner's phone lost its link for about five minutes, and every phone part then spent one 60 s adb timeout). A wirelessly attached phone stays `device` in `adb devices` while its link stalls, so `phone-attach` also runs the probe, `adb -s <serial> shell echo ok` within 15 s; when it does not answer, `adb -s <serial> reconnect` once and the probe again; still no answer refuses the run ("listed but does not answer a command"). The release install's facts are only compared when they were read: a failed or timed-out read (`pm list packages`, `dumpsys package`) is retried twice, each retry only after the probe passed, and otherwise `phone-attach` fails with "could not read the release install before the run" (nothing is installed) or `phone-release` with "could not re-read the release install ... (not a change)"; `release.json` then has `unreadable` and the sheet's Phone table says "could not re-read", never "CHANGED". After a phone part that did not pass, the probe (with its one reconnect) runs; when the phone does not answer, the later phone parts are skips with "adb stopped answering (after <part>: ...)", and `phone-release` probes once without a reconnect before it tries to read. A phone part that exits non-zero has its error log's last line (else its output's) in its `steps.tsv` note. For a wireless run: one transport (the phone on Wi-Fi or on USB, not both), the screen on (Stay awake in the developer options), and the phone's Wi-Fi power saving off where it has one.

**Both units** (T139, T129's follow-up): `tools/sweep.ps1` (T147: in every sweep with a device, no longer opt-in; `-NoBothUnits` leaves it out, `-BothUnits` is still accepted; `-Only bothunits` alone) runs `android-ui.py bothunits` after the debug parts, on the sweep's emulator and a second one booted for it on the matrix pattern: AVD `<Avd>-b`, console `-MatrixEmuPort` (default `-EmuPort`+2), debug forward `-Port`+2, the same debug build and server, stopped and deleted afterwards. The peer is a standalone server on the script's own slot `-BasePort`+3 (bound to all interfaces, `http://10.0.2.2:<port>` to both emulators), started and stopped by PID. The report is `bothunits.json`, the screenshots of both phones are in `ui\bothunits\` and on the sheet, and `summary.json` has the part's carries (`a-on-to-b`, `b-off-to-a`: value and the receiving phone's `bothUnits`), the peer and the screenshots (T147: all four, both phones after each carry, from each step's `pngs`; before, the two of the receiving phones). A second emulator that does not start (`android-emu.ps1` exits non-zero: no room for a second AVD, its console port taken) makes the part a skip, not a failure: `steps.tsv` and `summary.json` `skipped` carry "skipped: the second emulator emulator-<n> (<Avd>-b) did not start" with the script's first error line.

**Diagnostics and the release key** (T154, T143's follow-up): the sweep's `diagnostics` part runs `android-ui.py diagnostics` on its own release build after `recenter` (report `diagnostics.json`, screenshots in `ui\diagnostics\` and on the sheet; `summary.json` has the steps, `heapsize`, the row's `now` lines and `lastAfterForceStop`); T305: it opens the row's own "Technical details" fold, the heading above the row's "How much memory" line, since a failed update check gives the Updates row a fold of the same name). That build is signed with the release key, so `diagnostics`, `upgrade` and `update` run as a user's phone would: in the main checkout Gradle signs it (`tools\release.keystore` and `tools\release.properties`, gitignored); a task worktree has no key, builds with the debug key, and the sweep re-signs each copy in `apk\` (and the `update` part's second build) with `tools\sign-release.ps1` (T293: `-Apk <apk> [-Out <apk>]`; it reads the main checkout's key where it lives through the SDK's `apksigner`, prints one JSON object with the certificate's SHA-256, `47:31:38:10...`, and nothing of the key; exit 2 when the main checkout has no key either, and the copy keeps the debug key). `apks.json` is written after the re-signing, its `signedBy` names `gradle`, the script with the certificate's prefix, or `debug key`. Never copy the key's files into a worktree: the permission rule denies agents reading them, and a copy outlives the worktree's use. `-Out` is a folder relative to the checkout (`out\sweep-<date>` by default); an absolute path or one outside the checkout is refused at the start.

**The sheet** (T111): `tools/sweep-summary.py` puts every PNG of a sweep on `sheet.png`, and Chrome captures at most 16,384 px of a page: the 2026-10-14 sheet was 17,383 px, so the capture repeated its top and lost the last demo tour section. That sweep's outputs make a 1600 x 12,953 sheet at 7 columns with every section.

**The before-and-after sheet** (T259): `python -I tools/sweep-diff.py <previous sweep folder> <this one> [--first <screen names>]`, run by `tools/sweep.ps1 -Prev <folder> [-First <names>]` after the summary (`-SummaryOnly -Out <existing folder> -Prev <folder>` runs only the summary and the diff). T288: the diff is a step of its own, `diff` in `steps.tsv` (its exit code, seconds and note; a `diff` line of an earlier run is dropped before the summary, so a rerun replaces it), and its exit code joins the sweep's. Each `--first` name is matched against every frame of both folders: one that matches no frame at all is printed, the sheet is still written, and the diff exits 1 with `changes.firstMissing` and `diff` under `failed` (`ok` false) in `summary.json`, so the sweep is red and holds a release until the name is corrected or a step opens that screen; a rerun with the right names (`-SummaryOnly`, or `sweep-diff.py` alone, which rewrites a `diff` line already in `steps.tsv`) clears it. A name that matches only unchanged frames (alike, timing or removed) is listed in `firstUnchanged`; new frames a name matches (a wave's own new step, with no namesake before) come first among the added, marked, and are listed in `firstAdded`; the exit is 0 for both. It pairs every PNG by its path relative to the folder, then the leftovers by the name without the step number (a step added or dropped renumbers a part's later shots: `ui/upgrade/04-create-data.png` pairs with `03-create-data.png`); composites (`sheet.png`, `*-sheet.png`, `tour/contact-sheet.png`, `changes*.png`) and the servers' sprites under `out/` and `server-out/` are skipped. No Pillow on this machine, so the comparison runs in Playwright's Chromium canvas: both images at 270 px wide with a 1 px blur, a pixel differs when a channel moved by more than 40 of 255, and a pair is changed past 0.4% (`--width`, `--pixel`, `--frac`). The status bar (the clock: the top 3% portrait, 6% landscape) of device shots (`device/`, `ui/`, `first-run/`, `release/`) is masked, and a shot named `*-first` (taken before the map settles) is listed as `timing`, never counted. Measured: the device tour's two runs of one build differ by at most 0.05% per view (0 of 11 changed in two sweeps); across the sweeps of 2026-10-23 and 2026-10-24 (a day of merges apart) 147 of 218 pairs were identical, the timing tail reached 0.13%, the smallest real change (a credit line's wording) was 0.6%; contours still landing at the screen's edges read 0.9 to 2.9% and do pass, so the sheet is read by eye. Outputs in the sweep folder: `changes.png` (the changed pairs before, after and the after with differing pixels in red, `--first`'s screens first and marked, then the new shots; fitted under the 16,384 px capture like `sheet.png`, two pairs a row, then three, four, then a scale), `changes.json` (`count`, `paired`, `changed` with each `fraction` and any `was`, `timing`, `added`, `removed`, `renumbered`, `fractions` of every pair, the thresholds), and `summary.json` `changes` (the count, the paths of both files, the previous folder; `sweep-summary.py` reads `changes.json`, so a rerun keeps it). **Where a frame is** (T295): each device frame has a sidecar `<frame>.place.json` naming the `areas.json` area that holds the viewed centre, or `outside`, with its basis: `camera` (`GET /camera`, a debug build) or `fix` (the fix or deep link the part set; it says where the phone is, not where the map looks). No coordinate is written. A camera at zoom 6 or below names the area within half a phone's width. The diff always leaves out a pair with an `outside` side, prints only "outside the public areas", and refuses a sheet with an `outside` frame on it; `--leave-out <names>` and `--leave-unknown` (a side with no sidecar, a sweep from before T295) leave out more, and without `--leave-unknown` unknown sides are kept and listed. `changes.json` gains `leftOut`, `unknown`, `leaveOutMissing` and `places`, and a summary rerun keeps them. **A red part, and the retry** (T292): `tools/sweep.ps1` runs a device part once more, after a reboot of its emulator and with a fresh ceiling, when its first run failed for the machine's sake: the outcome `emulator-gone` or `guard-stop`, or a device-class line (device offline, device not found, an adb or `/sdcard` "Permission denied", the guest's storage not ready) in its note, its logs' last 100 lines or its reports' error strings (`DEVICE_LINES` in `tools/sweep-summary.py`). A golden, test, assertion, budget or timeout failure is never retried, so a part that is red in `summary.json` failed on its own (or failed twice). `steps.tsv` keeps both runs, the first run's text files are in `retry\<part>\`, `summary.json` `retried` names the reason and the line, `parts.<part>.passedOnRetry` and the sheet's amber `ok on retry` mark a flake, and `reruns` counts every rerun per part, a `-Only` rerun into a second folder included when it passes `-RerunOf <the first folder>`.

**The route sheet** (T289): the part `route-sheet` of `tools/sweep.ps1` (no device; after `sync-sim`, ceiling 600 s) runs `python -I tools/route-diff.py run`, which plans every line of `tools/route-sheet.txt` (`<name> <pack> <mode> <from> <to> [<prefer>]`: the six public drives of `docs/reference/devtool-commands.md` under `time`, `fuel` and `quick`, the `rainier` hikes and the ride of `tools/routing-tour.txt`) with devtool `route` on the checkout's `out/` packs and keeps `route-sheet/<name>.png` (the route on its map, `--out`), `.gpx` and `.json`; the part's report is `route-sheet.json`. A line whose pack (`out/<pack>-outdoors.pmtiles`) is missing is skipped by name; without the DEM pack the route is planned with no picture (`noPicture`); a route that is not found fails the part. In a task worktree the sweep copies (never links) `montblanc-outdoors.pmtiles`, `montblanc-dem.pmtiles` and `montblanc-outdoors-graph.idx` from `-DataDir` into the worktree's `out/` when they are missing there, as it copies the Rainier packs (T299), so the `montblanc` lines run; they are never read in place, because devtool `route` writes graph and overlay files beside a pack. Without them in `-DataDir` the `montblanc` lines are skipped. With `-Prev`, `Write-Summary` first runs `route-diff.py diff <prev> <this>`, which pairs the routes by name and calls one changed when its distance moved by more than 0.1 m, its time by more than 1 s, its `fuelIndex` by more than one part in a million, its `turns` at all, or the hash of its line (the GPX's points rounded to six decimals; the route's JSON holds only a count of points, and a rebuilt graph renames edges); a field absent on both sides is equal and every other field is ignored. It writes `route-changes.png` (more pages, `route-changes-2.png` and on, past Chrome's capture limit): the changed routes first, the old and the new picture side by side, each with its own line redrawn in purple and the other sweep's line dashed in orange over it, the figures under each and the differences under the new one, the moved figures in red; then the new routes; then the names of the removed, skipped and failed. `route-changes.json` has `count`, `changed` (`why`, both sides' figures and line hash, `differences`), `new`, `removed`, `unchanged`, `skipped`, `failed`; `summary.json` has the part (`planned`, `pictures`, `skipped`) and `routeSheet` (the counts changed, new, skipped, removed, unchanged, failed, and the pages). A changed route only shows and never turns the sweep red: a wave may mean to change it. The nightly `tools/sweep.sh` does not run the part (whether its runner holds the `montblanc` pair is not known).
