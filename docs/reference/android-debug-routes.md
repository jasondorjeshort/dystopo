# Android debug routes

Debug builds only, on the debug port (`android-app.md`, Loopback token). The KDoc at the top of each `*Routes.kt` file is the full reference for its routes; this page is the map. Tracks and sync: `android-tracks-and-sync.md`; direct sources, updates and first run: `android-online.md`.

## Endpoints

Debug endpoints (debug builds only, on the debug port; `curl -H "X-Dystopo-Token: $T" http://localhost:<forwarded port>/...`). They run on their own small thread pool, so they answer while contour tiles generate:
- `GET /health`: packs, server load (`rejected` counts per reason, tile and debug pool queues), map state. `map.idle` means style loaded, MapLibre's `isFullyLoaded`, last frame complete, no tile pending at the server, no camera move and no new frame for 500 ms; `map.notIdleBecause` names the blockers (`styleLoading`, `animating`, `pendingTiles`, `notFullyLoaded`, `frameNotFullyRendered`, `rendering`, `settling`); `map.lastScreenshot` says how the last screenshot settled.
- `GET /screenshot[?wait=ms][&mode=window][&stable=0]`: PNG of the map (MapLibre snapshot). It waits for idle and then until two snapshots in a row agree, so it never returns a half-loaded map; `stable=0` skips the pixel check, `wait=0` captures at once. `mode=window` copies the map surface and draws the Compose overlays on top. **View it**, like the devtool PNGs.
- `GET /camera`; `POST "/camera?lat=46.853&lon=-121.76&zoom=12&bearing=0"` (or a JSON body). T93 (`controls/ControlRoutes.kt`): `POST /camera/recenter[?animate=ms]` does what a tap on the recentre button (the bullseye lower right) does: centres on the last fix at the current zoom and bearing, turns navigation's follow back on after a pan, and answers with the camera once it is there and `fixOffsetPx` (the fix's distance from the centre; 409 with `noFix` or `noPermission` when there is no fix). `GET /camera` adds `fixOffsetPx` and `recenter`: the button's `state`, `orientation` (NORTH_UP until the three-state button), `lastTap`, and `button` (`boundsPx`, the credit, route card, track panel and navigation card edges, and `clear`; `hiddenBecause` `tripCard` while the trip card is open).
- `GET /stats`: tiles served per source, contour generation ms (min/avg/max, recent tiles with sample/trace split, `warmup`), disk-cache hits, DEM decode cache, memory (Java heap, native heap, PSS by category), APK and pack bytes.
- `POST "/location?lat=..&lon=..&accuracy=10"`: inject a fake GPS fix (the location puck moves; device fixes stay detached until `POST /location?device=1`); `GET /location`.
- `GET /settings`; `POST "/settings?units=m&textScale=1.4&warmup=0"`: units (`ft`, `m`, or `unset`), text scale (0.5 to 3; outside is a 400), contour warm-up; `server` (the online tile server, empty for offline only; T79: plain http only to a home-network address, see First run). Cache caps: `onlineCacheMb` (fetched online tiles) and `contourCacheMb`, one LRU byte cap enforced while the app runs over every pack's contour tiles, the cliff-rewritten vector tiles (`cliffs1-<vector id>-<dem id>/`) and the hillshade/slope shade tiles (`shade1-<options>-<dem id>/`); a deleted pack's directories go with it. T74: online tiles are keyed on the server's content versions (`GET /version` there, `X-Dystopo-Version` on tiles; checked at most every 15 s on a tile request and by the probe), so a server whose DEM changed is seen at the next check and its old tiles (and the contours and shade made from them, which are cached in the online cache too) are dropped; glyphs and sprites follow the server's `/assets/manifest.json` hashes (`/online` `assetsVersion`, `assets`); the fetcher takes a list of sources (`/online` `fetcher.sources`). Map options (T47, also the Map section of the settings sheet): `hillshade` off/single/multi, `hillshadeIntensity`, `slope` on/off (CalTopo bands), `contourInterval` auto or a value from `contourIntervalChoices` (from contour zoom 11, pack and online contours alike), `contourLabels` sparse/normal/dense, `trails`, `water`, `landcover`, `pois`, `boundaries`, `night`; the default style is unchanged unless an option needs shade tiles (`/shade/{z}/{x}/{y}.png`, `/stats` `shadeGeneration`). Units are a preference (docs/PLANNING.md › Units): unset on install, seeded once from the first pack's centre or the first fix, then only the user changes them; contour tiles, the style, track stats, the profile and search results follow them. `POST /settings/ui?open=1` opens the settings sheet (also the Settings chip on the map).
- **Storage** (T74, `storage/Storage.kt`; Settings › Storage ›): `GET /storage[?walk=1]` lists every store with bytes and budget: `packs` (`files/packs/` and pushed ones), `online` (`cache/online/tiles/`, fetched tiles plus online contours and shade, `onlineCacheMb`), `derived` (`cache/contours/`: pack contours, shade, cliffs, `contourCacheMb`), `sources` (`cache/sources/`, the phone's own source reads); `walk=1` adds each directory's `files`, `apparentBytes` and `diskBytes` (compare with `adb shell du -s -k`). `POST /storage?onlineCacheMb=&contourCacheMb=` sets the budgets (the same settings), `POST /storage/clear?store=online|derived|sources` empties one, `POST /storage/ui?open=1` opens the screen.
- `POST /reload` (reopen packs after a push), `POST /cache/clear` (drop cached contour tiles).
- `GET /features` (alias `/labels`): rendered feature count per style layer in the viewport (queryRenderedFeatures) plus placed symbols per symbol layer; `GET /features/text`: pixels that change when text is hidden (0 with labels placed = labels not drawn).
- `GET /contour-labels[?minRunPx=200]`: index contours in view and which carry a placed label; unlabelled ones with their visible length and longest on-screen run (`labelledLong`/`indexLong` count lines with a run of at least `minRunPx`).
- `GET /packs`: `active` (the primary pack), `inUse` (every pack on the map with `primary`, `demRank`/`osmRank` in precedence order, `osmProfile`), `roots`, and per pack `name`, `active`, `usable`, `bytes`, `bounds`, `minZoom`/`maxZoom`, `attribution`, `dem`/`vector` (file, bytes, tileType, zooms, bounds, tiles, attribution, title, `complete`), `files`, `errors`, `inUse`; plus `downloads`, `search` (per-pack index state) and `routing` (the trail graphs: the primary pack's state at the top, every pack's under `packs`, the graph tile cache, the last route's `memory`). Precedence per tile (`PackPrecedence`): outdoors profile over plain OpenMapTiles, then the primary pack (`POST /packs/activate?name=`), then the deeper archive, then the smaller box. `DELETE /packs/{name}` removes the archives, the search index, the routing graph and (on the next collection) the pack's contour, cliff and shade tiles. `GET /attribution`: full credits plus `mapLine`, what the on-map credit line shows for the packs overlapping `viewBounds` (and the online sources when the view is online).
- **Routes** (T45, `RouteRoutes.kt`): `POST "/route?from=46.7864,-121.7366&to=46.8024,-121.7289&mode=hike"` plans over the trail graphs of every pack near its ends (T77: with a server set, an end beyond every pack on the device is planned by the server's `GET /route` instead, `memory.remote` in the route, `remote` in `GET /route/status`; keep it with `POST /routes/keep`, then `POST /areas/download?trip=<id>` fetches its corridor so navigation works offline; drives of 40 km or more use the drive overlay, `driveOverlay` in `/route/status`) (T76: each built on first use into `<vector archive>-graph.idx` next to its pack, z11 graph tiles read on demand, so a route crosses from one pack into the next; progress, tile cache and the last route's `memory` in `GET /route/status`) and shows it, fitting the camera to it; results carry `via`, the named trails in travel order (outdoors packs; plain OpenMapTiles lines have no names). `GET /route` (card state, `ui.lastFit`, `ui.layout` with the route card and track panel edges and `overlap`), `POST /route/mode?mode=bike` (answers with the replanned route; T73: `mode=drive` follows the packs' roads, one-ways and roads closed to cars, to and between trailheads, says on the card that it is not a road navigator, and on a pack built before outdoors profile 2 fails with `drive_unsupported` naming the pack to rebuild), `/route/longpress`, `/route/save`, `/route/gpx`, `/route/export`, `/route/clear` (T65: also closes the route editor, so a kept route's line goes too; the route stays stored, `closedTrip`). T65: a route has one set of numbers everywhere: the card, `route` in `POST|GET /route`, the kept route, the trip card, the Routes list and navigation all show `RouteSummary` of its points (T24's 3 m hysteresis climb, the T45 hike model); the router's graph-based climb and time are under `route.graph`. `POST /route/import/pick` opens the Routes list and the system file picker (its Import button; pick a GPX, it is imported as routes and the last one opens), `GET /route/import` has the result. Trips (planned routes, `/routes`) are documented in `trips/TripRoutes.kt`; the trip card has Go.
- **Navigation** (T61, T65; `NavRoutes.kt` documents every route): `POST /nav/start?route=current|<kept route id or prefix>|<saved route>` (or `track=`, `file=`, a GPX body), `GET /nav`, `GET /nav/status`, `POST /nav/stop`, `/nav/camera`, `/nav/heading`. Starting closes the route editor and hides the route card; the navigation line draws above the planned, kept and track lines (`layer.overlaysAbove` empty). `POST /nav/snooze?min=10|until=back|off=1` silences the off-route alert (events are still listed; `snooze.suppressed`); the banner has Snooze 10 min and Quiet until back. Stale fixes: a GPS fix or the last known location more than 30 s old is dropped (`fix.droppedTooOld`), the last known location more than 2 km from the line does not start navigation (`droppedTooFar`), and with no usable fix for 30 s the bar says "No GPS fix for N s" (`fix.lost`). `etaVsPlan` is a pace ratio, (fix time since the first fix + the model's time still to go) / the planned time (the route's `RouteSummary` time; the line's model time for tracks): 1.0 at the start, above 1 behind plan; `pace` has the parts. `layout` says where the Tracks and Routes chips sit: they stack below the stats card (`TopChips`), and the Routes chip sits below the open tracks list. Off the device: `./gradlew :devtool:run --args="nav replay --path shared/src/commonTest/resources/gpx/skyline-loop.gpx --path-track --fixes shared/src/commonTest/resources/gpx/skyline-offroute.gpx --expect-off 1 --expect-arrive"` runs the same off-route logic on the JVM (events, max distance, progress, `etaVsPlan` as JSON; exit 1 when an expectation fails).
- **Areas of interest** (T75; `areas/`, routes in `AreaRoutes.kt`, the manifest format in docs/SERVER.md › Areas of interest): a box or a route corridor with zooms, pinned on the phone. A box is "Download this region" (`RegionDownload`, through the server's `POST /area` when it has one, so the pack arrives with SHA-256 per archive; recorded as a pack-backed area, which stays until removed); a corridor (the trip card's Offline button, or `POST /areas/download?trip=<id>[&bufferM=500&minZoom=8&maxZoom=15][&contours=1]`, or a JSON body `{"kind":"corridor","line":[[lon,lat],...],"bufferM":500}`) fetches the manifest's DEM (from z6, or z8 with no server) and vector tiles through the online fetcher into the tile cache, skipping tiles in packs or already cached (a second run resumes), and pins them: `TileCache.keep` (one hook line in `online/TileCache.kt`) is `Areas.isPinned`, a spatial test of each key's z/x/y against the pinned covers, so eviction skips them until `POST /areas/{id}/pin?on=0`. `GET /areas` (each area's bytes, estimate, coverage now: tiles present out of the manifest's), `GET /areas/{id}[/manifest]`, `GET|DELETE /areas/download`, `DELETE /areas/{id}`, `POST /areas/trim?mb=N` (cap the online cache now, not saved; `restore=1`; answers evictions and every area's coverage before and after), `POST /areas/ui?open=1` (the "Offline areas" sheet, also a chip in the pack list; outlines on the map while open). Ahead on the route: while navigating and online, the next 3 km of the line (1 km segments, 300 m buffer, z12 to z15) are fetched and pinned until navigation stops; `GET /areas/prefetch` lists the segments with `aheadByM`, `secondsBeforeArrival` and `cachedAtArrival` (`POST /areas/prefetch?on=0` turns it off).
- **Sync**: the `/sync/*` and `/share/*` routes are in the Sync and Phone-to-phone sync paragraphs below; the share listener is a separate server with its own share code (T72: 16 characters, the link encrypted under it), not the loopback token.
- `tools/android-probe.py --port <port> --serial <serial>` sends malformed and oversized requests and checks the server answers 400/408/413/414/431 and stays up, that requests without the token (or with a wrong one) get 401, and (T57) that `/health` without the token is 401 on the debug port and that device port 8686 serves map routes only (debug routes 404).
- T57 also: `/stats` tile counters are cumulative since the app started (`counters.tileServiceOpens`), not reset when a pack install, a synced setting or `/reload` reopens the tile service (T65: `shadeGeneration` and `cliffs` too); `POST /settings?routeSnapM=50..1000` (default 300; the settings sheet offers 300 m, 500 m, 1 km) is how far a route's ends may be from a trail, and an off-network failure names the nearest trail, its distance and direction (`nearestName`, `nearestDirection`); `/route/status` has `decoder`; `POST /packs/catalog/refresh[?server=]` fetches the catalog again (T65: a server's vector-only single-file pack is listed and downloads as a map-only pack, `<name>-outdoors.pmtiles`, drawn over another pack's or the online DEM and never primary); `POST /location/replay?record=` is a 409 while a track is recording (replay without `record=` adds to it).
