# Android debug routes

Debug builds only, on the debug port (`android-app.md`, Loopback token). The KDoc at the top of each `*Routes.kt` file is the full reference for its routes; this page is the map. Tracks and sync: `android-tracks-and-sync.md`; direct sources, updates and first run: `android-online.md`.

## Endpoints

Debug endpoints (debug builds only, on the debug port; `curl -H "X-Dystopo-Token: $T" http://localhost:<forwarded port>/...`). They run on their own small thread pool, so they answer while contour tiles generate:
- `GET /health`: packs, server load (`rejected` counts per reason, tile and debug pool queues), map state. `map.idle` means style loaded, MapLibre's `isFullyLoaded`, last frame complete, no tile pending at the server, no camera move and no new frame for 500 ms; `map.notIdleBecause` names the blockers (`styleLoading`, `animating`, `pendingTiles`, `notFullyLoaded`, `frameNotFullyRendered`, `rendering`, `settling`); `map.lastScreenshot` says how the last screenshot settled; T138: `map.styleLoads` counts the styles set on the map since the process started (a tile that came without a style reload leaves it unchanged).
- `GET /screenshot[?wait=ms][&mode=window][&stable=0]`: PNG of the map (MapLibre snapshot). It waits for idle and then until two snapshots in a row agree, so it never returns a half-loaded map; `stable=0` skips the pixel check, `wait=0` captures at once. `mode=window` copies the map surface and draws the Compose overlays on top. **View it**, like the devtool PNGs.
- `GET /camera`; `POST "/camera?lat=46.853&lon=-121.76&zoom=12&bearing=0"` (or a JSON body; like any camera move that is not the app's own it stops following the fix, and a bearing other than north turns north-up into free rotate). T93, T100 (`controls/ControlRoutes.kt`): the map has one orientation state for the whole app (`controls/MapOrientation.kt`): `north-up` (the default), `free` (entered only by turning the map with two fingers) or `facing` (the map turned to the heading), kept across restarts as north-up or facing, plus `following` (the camera stays on each fix; a recentre turns it on, a one-finger pan, a fling or a move that is not ours turns it off; two-finger turns and pinches act about the centre and keep it). Navigation's camera modes (`/nav/camera`, the navigation card's Recenter, Heading up and North up) are a view of the same state, so the card, the button and the follow-me agree. `POST /camera/recenter[?animate=ms][&taps=n]` does what `n` taps (1 to 5) on the position button (lower right) do, by the owner's rule (T176, `OrientationRules.tap`): off centre a tap recentres on the fix and keeps the orientation, zooming in to the close zoom (`recenterZoom`, default 14) when the map is farther out; centred but farther out it only zooms in; centred and close it advances the orientation on the one-button layout (north-up to facing when the phone has a compass, facing and free rotate to north-up) unless the lock is on, and does nothing on two or three buttons; a tap never zooms out, and navigation keeps its own zoom (the navigation card's Recenter, or any tap while navigating); it answers once the camera is there with the camera, `fixOffsetPx`, `orientation`, `tap` (`action` `recenter`, `zoom`, `advance` or `none`, `centredBefore`, `orientationBefore`, `orientation`, `advanced`, `navFollowOn`, `layout`, `locked`, `closeZoom` (null while navigating), `zoomBefore`, `zoomTo`, `zoomAfter`) and `taps` (409 with `noFix` or `noPermission` when there is no fix). T176: `POST /camera/recenter?long=1` long-presses the position button (toggles the lock on one or two buttons, `result: ignored` on three; the answer's `button` has `lock` and the `toast`); `?button=orientation` taps the orientation button (the next mode, also under the lock), `?button=lock` the lock button. `POST /camera/gesture?kind=rotate&deg=40` injects a two-finger turn about the map's centre and `kind=pan&dx=-300&dy=200` a slow one-finger drag (px, no fling) as touch events into the map view, so MapLibre's detectors see them; it answers after the camera rests with `gesture` (`bearingBefore`, `modeBefore`, `zoomBefore`). The lock ("Keep north up", `orientationLock`): the rotate gesture is off, a north-up bearing found off north at rest turns back to north, free rotate is never entered (`POST /camera/orientation?mode=free` gives north-up); the orientation button and the navigation card still change the mode, and a pan never does. `POST /camera/orientation?mode=north-up|free|facing` sets the orientation; `POST /camera/heading?deg=` sets a simulated heading for facing while fixes are injected (no `deg` clears it; the same one as `/nav/heading` and `POST /location?bearing=`). `GET /camera` adds `fixOffsetPx`, `orientation` (`mode`, `following`, `centred` and its `centredTolerancePx`, `cameraMode`, `compass`, `heading` with `deg`, `source` `simulated` | `course` | `compass`, the course, the speed and the compass sensor's state, `lastChange`, `lastFollowEnd`, counters) (T176: `lock`, `lockReturns`, `rotateGestures`) and `recenter`: the button's `state`, `orientation`, `lastTap`, T176's `layout` (as set), `shownButtons` (as drawn), `lock`, `closeZoom`, `longPresses` and `lastButton`, and `button` (`boundsPx` and `clear` for the whole column, T176's `buttons` with each button's `id` (`position`, `orientation`, `lock`) and `boundsPx`, the credit, route card, track panel and navigation card edges, `clear`, and `icon`: the orientation and look it drew, `following` blue, `offCentre` dark, `disabled` grey; T106: `tripCardTopDp` and `updateCardTopDp`, the trip card's and the update offer's top edges, which it now rides above; it hid under the trip card and shared its corner with the update offer; T110: `topRightBottomDp`, the lowest of the track controls with their list, the Routes chip and the navigation card, which it never reaches up to: with a bottom panel that tall, as the route card with its directions open at font scale 2.0, it hides, `hiddenBecause: noRoomBelowChips`, T176: after dropping the lock, then the orientation button, the buttons left acting as that layout; it sat over the Tracks chip). Facing's heading is the course over ground while moving (faster than 1 m/s), else the compass (rotation vector plus WMM declination, running only while facing is on and the app is in the foreground). On the emulator the compass follows the virtual sensors: `adb emu sensor set acceleration 0:0:9.81` (lying flat) and `adb emu sensor set magnetic-field -20:0:-45` (pointing magnetic east; `-B sin H : B cos H : -45` for heading H) settle in about 10 s; a replayed GPX (`POST /location/replay`) gives the course. T162: `GET /camera` `openView` says what the map opened at (`android-app.md` › The open view): `won` (`fix`, `saved`, `pack`, `deepLink`, `restored`, `world`), the candidates with their times (`fixAt` when the fix last moved, `savedAt`, `packAt`, epoch ms, 0 for a pack never activated) and `window`, the fix window after open (`ms`, `state` `open`, `recentred`, `gesture`, `cameraSet`, `cameraMoved`, `expired` or `none`, `recentredTo`). On the emulator, `adb -s <serial> shell cmd location set-location-enabled false` keeps the emulator's own fixes out of a scripted open-view check, and `POST /location` gives the fix.
- **Scale bar** (T101, `controls/ScaleBarRoutes.kt`): `GET /scalebar` says what the bar lower left shows (`shown` or `hiddenBecause`; T106: it rides above the trip card and the update offer, `bottomCardsTopDp`, instead of hiding under the trip card; T115: it hides with `noRoomBelowTopLeft` when that would take it up to the search box and the online indicator, `topLeftBottomDp`, its own top `topDp`; `units`, `bothUnits`, `night`, the `zoom` and `lat` it was fitted at, `metersPerDp`) and per bar (the user's units first) `label`, `meters`, `widthDp`, `widthPx` and `drawnPx`, where it sits (`boundsPx`, the credit line, route card and track panel edges it stays above, `clear`), and `readBack`: each bar against MapLibre on the live camera (`mapLibreMetersPerDp`, the metres that width covers at it and `errorPct`; `measuredMeters` between two screen points that far apart and `measuredErrorPct`; T128: on the bar's own row, `measuredRowPx`, with the centre row's `centreRowMeters` and `centreRowErrorPct` beside it). T128: under tilt (0.5 degrees or more) the bar is fitted to the ground scale along its own row from MapLibre's projection (`measuredAt: row`, `rowPx`, `tilt`, `metersPerDp`; untilted `measuredAt: centre`, the Web Mercator rule `centreMetersPerDp`), so its label is right where it is drawn rather than at the centre row; `errorPct` (MapLibre's centre-latitude scale) is meaningful untilted only. T128: it also stays below the navigation card (`navCardBottomDp`, `clearOfNavCard`; `hiddenBecause: noRoomBelowNavCard` when no room is left); above the card's 1.5 font-scale cap a tall bottom panel pushed it up over the card. `POST /scalebar?both=on|off` is the Map options row "Scale bar" (One unit, Both units: a two-sided ruler, the other system below the line); T110: synced like the map options (`app.scaleBar.both`, `on` or `off`; `GET /sync/status` › `settingsSync`: `synced` this phone's values, `held` the log's). T110: `readBack` only for a bar that is shown and fitted at the live camera (the route waits up to 1.5 s for the bar's 500 ms refit; else `readBackSkipped`: `hidden` or `fitBehindCamera`), and a hidden bar keeps no lengths or bounds (`hiddenBecause` adds `notComposed`, while the no-pack line shows); before, a hidden bar's last lengths were read back against a camera that had moved.
- **Live readout** (T161, `controls/ScaleBarRoutes.kt` documents the routes; `android-app.md` › The live readout): `GET /readout` mirrors the bar on the scale bar's line: `shown`, `hiddenBecause` (T177: `off` with the bar switch off), `bar` (T177: `on`, `window` `s` and `label`, `windowFilledS`, `bothUnits`, `fields` in drawn order with `entry`, `state` `value`, `zero` or `dash`, `text` as drawn and `other` in both-units mode), `activity`, `units`, `options` per entry, `drawn` (each item as drawn: `caption`, `state`, `value`, `unit`, `full`, `other`, `dimmed`; T177: a gap is the first caption, "no fix 8 s"), `line`, `readout` (T160's values with `state` (`shown`, `zero`, `dash`, `hidden`), SI `value`, `sigma`, `source`, `reason` (the climb's `filling`, `still`, `near zero`); `climbWindowS` and `climbFilledS`; `heights` with `gnssM`, `baroM`, `demM` apart; `barometer` `state` off, none, calibrating, in use or suspect with its `reason`), `barometerSensor` (`present`, `listening`, `wanted`, `source` sensor or replay), `seaLevelPressure` (T173, `readout/PressureSource.kt`: `state` off, fetching, in use, no station in range or unavailable; the prior's `hPa`, `station`, `group`, `distanceM` from the fix, `ageS`, `source` and `credit`, `applied` (the estimator's priors); `limits`, the last `request` and `box`, `lastResponse` with `reports`, `stations`, `unusable` and `bytes`, `lastError`, `nextFetchInS`, `counts`), `route` while navigating, `inputs` and `layout` (`placement`, T177 `naturalWidthPx` and `besideRoomPx`, `boundsPx`, `sizePx`, `clearOfScaleBar`, `clearOfRecentre`, `clearOfNavCard`, `clearOfBottomPanels`). `POST /readout/reset` forgets every input between replays. T173: `POST /readout/stations?url=<endpoint>` points the weather station fetch at a mock endpoint (`url=` empty restores the registry's), forgets the stations and fetches at the next refresh; `GET /online` › `stationPressure` counts the requests (`fetches`, `failures`, `bytes`; `android-online.md` › Weather station pressure). The options are `POST /settings` keys (`readout.<entry>=pace=1` for the remembered activity, `readout.<activity>.<entry>`, `readoutBarometer=0`, T177 `readoutBar=0|1` and `climbWindow=30|60|300|600`). `POST /location/replay` reads a pressure column: a `pressure` element in hPa in a point's extensions (any prefix) goes to the readout at the fix's time (`GET /location/replay` `pressures` counts them; T178: and to the pressure trend while recording). T178, the pressure trend (`android-app.md` › The live readout): `GET /readout` › `trend` (`setting`, `sampling` with `recording` and `trendWanted`, `minutes` (one a minute while recording), `lastMinute`, `arrow` and `label`, `result` with `status`, `shown`, `band`, `alert`, `threeHour` and `oneHour` (`mode`, `seaLevelChangeHPa`, `interval` terms, `fallLowerHPa`, `passes`, `reason`), `alert`, `card` (`shown`, `title`, `body`, `station`, `boundsPx`), `spoken`, `station`, `stationTendency`, `persisted`, `counters`); `barometerSensor` adds `reasons`, `wakeUp`. `POST /readout/trend?fixture=<name>` (the devtool's fixtures: `still-fall`, `recovery`, ...) or a CSV body feeds a synthetic series ending now (live input ignored meanwhile), `?clear=1` returns to live input and forgets the warning's memory, `?dismiss=1` presses the card's Dismiss. `POST /settings?pressureFallWarning=off|more|standard|fewer`. The spoken line is listed in `GET /nav/speech` with index -3.
- **Help pop-ups** (T109, `help/HelpRoutes.kt`; `android-app.md` › Help pop-ups): `GET /help[?units=ft|m]` lists every help text with `key`, `title`, `text` (in the units setting or the given units), `placed` (where its icon is), `needs` (the state its icon needs, such as "hillshade on" or "no server set"), `onScreen` and `iconPx` (its touch target in window pixels while drawn), and `open`. `POST "/help/open?key=map.slope"` opens a pop-up as a tap on its icon does; when the icon is not on screen it first opens its screen (the settings page, Offline areas, the track bar, the long-press card at the map's centre), and the icon scrolls itself into view. The answer, once laid out, has `popup`: `side` (`below` or `above` the icon, `centre` with no icon in the window; T122: never `over` it, the text steps smaller instead), `boundsPx`, `windowPx`, `inside`, `textFits`, `coversIcon`, `fontScale`, `textScale` (T122: the text scale it drew at); when the icon's screen rebuilds and the pop-up lands in the middle or closes, it is opened again once the icon is back (twice at most); then `GET /screenshot?mode=window` shows it. An unknown key is a 404 with the keys; an icon still missing after 3 s (its `needs` unmet) a 409. `POST /help/close` closes it (T122: and answers once the closed screens' icons are gone, so the next `/help/open` does not find a closing screen's icon), and (T115) what `/help/open` brought up for icons since the last close and is still open (the settings sheet or the page it was on, Offline areas, the track bar, the long-press card, the Storage screen; `closed` names them), so a script finds the map it left; screens open before, or opened by taps since, stay.
- `GET /stats`: tiles served per source, contour generation ms (min/avg/max, recent tiles with sample/trace split, `warmup`), disk-cache hits, DEM decode cache, memory (Java heap, native heap, PSS by category), APK and pack bytes. T127: the direct renders' heap record (peak per render burst, the render limit from the free heap, the memory trims of `onTrimMemory` and of a short heap) is `GET /online` `direct.memory`, whatever the server setting since T135 (`android-online.md`, The Java heap); `tools/android-check.py`'s `directStep` samples `memory.javaHeapUsedBytes` here every 0.4 s (reported) and bounds the live heap that `am send-trim-memory <package> RUNNING_LOW` makes the app record (`direct.memory.recentTrims[].liveBeforeTrimBytes`); with a server configured the step runs with the app switched to no server and restores it (T135).
- T123, the phone's request log (`RequestLog.kt`, `Routes.kt`): `GET /stats/requests[?limit=N]` has `capacity` (4096 lines kept in memory, nothing on disk), `total`, `kept`, `dropped`, `perRoute` (requests, bytes, statuses, `maxMs` per route: the tile kinds, `glyphs`, `sprite`, `style`, else the path) and the newest `limit` lines (default 200), each `ts`, `method`, `path` (never the query, so never the token), `route`, `pack` (the region pack that answered a tile, `online:<source key>` for the online fallback), `status`, `bytes`, `ms`. `&format=jsonl` gives the kept lines one JSON object per line in the form `devtool cache-replay --log` reads (ADR 0034's revisit wants such a log from a phone): `curl -H "X-Dystopo-Token: $T" "http://localhost:<port>/stats/requests?format=jsonl" > out/phone-requests.log`. Debug builds only; both loopback servers (map port and debug port) log.
