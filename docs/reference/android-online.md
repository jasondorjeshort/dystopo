# Online on the phone: direct sources, updates, first run

The rules behind these: no Wi-Fi gates (ADR 0023), units (ADR 0022).

## No server: the phone reads the sources

**No server: the phone reads the sources** (T80; `online/DirectSources.kt`, `online/LocalPackBuild.kt`). With no server set (and `POST /firstrun/direct?on=1`, the default) the online fetcher's target is the pseudo-server `direct://sources` (cache key `sources`): DEM tiles are rendered on the phone from the shared `best` source as `LiveTiles.generateBest` does (from z8; rendered up to `directMaxZoom`, default 12, deeper ones synthesized from it; `maxZoom=15` renders every zoom including 3DEP lidar at z13+), vector tiles come from OpenFreeMap, contours, shade and cliffs are made as for server tiles. T85: contour tiles there read the DEM at the hillshade's zoom (`ContourTileOptions.sampleAtDemZoom`, the plan's `readZoom`, averaged down to its grid; pack and server plans unchanged), take the tiles the hillshade made or is making, render a missing tile only when it is in view (or under a tile of the view's own zoom or MapLibre's fallback zoom four up), leave the out-of-view halo ring NaN, and make tiles of other zooms from what exists without keeping them (`contourDem` in `GET /firstrun/direct`: cached, waited, rendered, haloSkipped, notAtViewZoom, partialTiles); since T88 a contour tile a DEM pack's bounds overlap reads the same way, taking the pack's tile wherever the pack answers one (it used the pre-T85 plan windows until then); with a configured server (T98) a contour tile a DEM pack's bounds overlap reads its window at least at the pack's first zoom (`OnlineTiles.serverContourOptions`; a z8 tile's plan samples z7 and a z7 tile's z6, zooms only the server has, so with the server unreachable every z7 and z8 tile over the Rainier pack came out with no line), and `/stats` `contourGeneration.noDemOverPack` counts contour tiles sampled with no elevation at all where a pack's bounds overlap them and the pack itself has an elevation in the tile's window (0 expected; `android-check.py` warns on it; T106: a coast inside a pack's box, no data in the pack either, is not counted); shade tiles (slope shading, multi-direction hillshade) take the same rule since T104: one a DEM pack's bounds overlap whose zoom is above the pack's first zoom (z6 and z7 over a z8 pack) reads at that first zoom, box-averaged, at most two zooms deeper (`OnlineTiles.shadeReadZoom`; `shadeGeneration.packFloorReads`, and `blankAtPackFloor` for one still without data, 0 expected); DEM tiles below z12 read the overview level for twice their cell size (`COARSER_OVERVIEW_BELOW`). Caps: 10 renders (fewer when the Java heap is short, T127, below) and 16 source requests at once, `directSessionMb` (a setting: `POST /settings?directSessionMb=`, default 300, also Settings › Sources) downloaded per session (then the map and the card say "Online data limit reached for this session"), any network (`directOnMobileData`, default on since T83; a user who turns it off in Settings › Sources sees "Online map paused: mobile data is turned off for it in Settings › Sources" on mobile data; a configured server is unaffected), `cache/sources/` trimmed to the cache budget's total (ADR 0034; 512 MB until the budget has started, T127); a DEM tile not ready in 9 s (a contour tile's DEM in 7 s) answers 503 and the style reloads once the renders those answers waited on are done (T88; before, once every render was done), with the reload count in the tile URLs (T85: MapLibre keeps a tile it got a 503 for when the style is the same, and never retries a timed-out one; its client times out at 10 s). "Download the map around me" then builds `<name>-dem.pmtiles` (z8 to `directMaxZoom`) and `<name>-outdoors.pmtiles` (OpenFreeMap, OpenMapTiles profile, z8 to 14) on the phone and installs them like an import. `GET /firstrun/direct` (session bytes, requests, renders per zoom and their ms, pools, cache), `POST /firstrun/direct?on=0|1&sessionMb=&maxZoom=`, `POST /firstrun/direct/trim`, `POST /firstrun/show[?lat=&lon=]` ("Show the map around me"); `GET /online` has `direct` too. Glyphs (every BMP range of the three Noto Sans fonts; a range the fonts lack is a valid empty glyph PBF) and the sprite sheet are bundled in the APK (`bundleMapAssets` in `androidApp/build.gradle.kts`, from the glyph cache and `devtool sprite`) and copied to the files dir on the first start of each build (`firstrun/BundledAssets.kt`); the loopback glyph route answers a valid empty PBF, never zero bytes. Costs measured in docs/PLANNING.md › The phone reads the sources. By taps on the release build: `python -I tools/android-firstrun.py --serial <serial> --direct [--download-at rainier|mont-blanc]` (install, "Show the map around me" at Rainier and at Mont Blanc with seconds to contours and to a settled map, T83's `mobile-data` step (wifi off, mobile data on, Paradise from the sources, no message about the network type; reported as skipped on an emulator, whose API 35 image has no cellular network), download, then wifi and data off and the downloaded place again).

**The Java heap** (T127; `online/HeapGuard.kt`, finding `../findings/2026-10-21-direct-view-out-of-memory-after-a-tour.md`). The direct renders are admitted by the heap: each running render counts at what it may take, 32 MB (a coarse tile reads overview blocks of every cell it spans, a z12 tile full-resolution blocks; counted at 12 MB, z12 renders let a z11 view reach 193 MB), and a render starts while they fit, with it, in what the max heap leaves after a reserve (an eighth of it, at least 24 MB), the heap the process held when no render ran (`baseBytes`) and the decoded blocks' cap (an eighth of the heap, at most 96 MB; it was a quarter; T138: a trim empties it in place, `DecodedBlocks.clear()`, since the geoid grids keep the cache they were opened with and a new cache beside it doubled them), and while that much is spare now; one always may run. On the 192 MB emulator heap a fresh process runs three at once (ten before; four, at 24 MB a render, still let cold z9 to z11 views reach the max). The in-memory caches (the decoded DEM tiles of the packs', the online and the direct pyramids, the cliff memo) are dropped by the application's `onTrimMemory` from `TRIM_MEMORY_RUNNING_LOW` up (`UI_HIDDEN`, the app leaving the screen, included; the activity is stopped in the background, so its own callback is not reached) and, at most every 5 s, when less than one render's 32 MB is spare at an admission or at the burst sampler's 100 ms reading while renders run (`heap short while rendering`; admissions alone rarely saw it: with three running the next waits on the budget and is asked again only after one ends and the collector has run), followed by a collection; each refills from its disk cache. The geoid offset memo (`Geoids.offsetCacheBytes`, 32 MB on a server) is 4 MB on the phone: a heap dump after a tour found it holding 31 MB of offsets for windows rendered once. T138: the direct sources register three trims with `HeapGuard`, each a key of `droppedBytes`: `directSources` (the synthesis pyramid), `decodedBlocks` (the decoded COG blocks, `DecodedBlocks.clear()`) and `geoidMemo` (`Geoids.clearOffsetCache()`); a render running keeps the blocks it holds, and the rest are decoded again from `cache/sources/`. `GET /online` `direct.memory` (T135: with a server configured too, where `direct` is `{direct: false, memory}`; the record is the application's): `heapUsedBytes`, `heapMaxBytes`, `reserveBytes`, `spareBytes`, `peakHeapBytes` (the process's), `bursts` (per render burst: `seq`, `renders`, `peakHeapBytes`, sampled every 100 ms while renders run), `burstSeq`, `renderBytes`, `budgetBytes`, `baseBytes`, `cacheBytes`, `heapWaits` (renders that waited for the heap rather than for a permit), `renderingNow`, `committedBytes`, `trims`, `pressureTrims`, `recentTrims` (reason, heap before and after, bytes dropped per cache). The cost is time: the z8 to z10 views did not go idle within the 60 s either way, Mont Blanc z11 went idle in 45 s (not within 60 before), Bonneville z11 not within 60 s (25 s before), the z12 views in 10 to 20 s (14 to 24 s before), and the device tour's cold Rainier z8 view in 73 to 117 s over eight tours (50 to 61 s before, on the same slow days), so `tools/android-check.py` gives the tour's first view 120 s, a thin margin; the direct view itself was still rendering at 117 to 125 s in every tour (blank tiles can pass the step). The sampled peaks count garbage not yet collected and are reported only, as are idle and the screenshot: a view still rendering, blank tiles included, can pass), and `--direct-only --direct-view <views> --first-wait-ms 60000` makes the table.

**The cold view, stage by stage** (T88; measurements in docs/PLANNING.md › The phone reads the sources). `GET /firstrun/direct` has `stages`, summed over threads in ms: `renderWaitMs` (waiting for a render permit), `coarseFirstHeldMs` (the part of it held for coarse tiles), `renderFetchMs` (inside `best`), `renderEncodeMs`, `contourDemWaitMs` (contour tiles waiting for their DEM), and `sources` (`rangeReads` and `rangeMs` cold range reads, `rangeShared` reads joined by another render, `diskHits`, `blocksDecoded` and `decodeMs`, `blockWaits` blocks another render was decoding, `geoidMs`, `resampleMs`); `rangeStalls` (range reads with no byte for 4 s, dropped and retried); and `timeline`, the process's first 800 events in ms from the first: `dem?`, `dem>`, `dem. <ms>` (a render queued, started, done), `read <file> <KB> <ms>`, `d?`, `d200`, `d503` (the map's DEM tiles), `c?`, `c200`, `c200p`, `c503` (contour tiles; `p` made partial and not kept), `refresh` (a style reload); T115: `o?`, `o<status> <ms>`, `oERR <ms> <exception>` (OpenFreeMap's vector tiles; T123: under a stall guard, `DirectSources.ofmGet`: an attempt fails with no connection in 4 s or no byte for 4 s, and a second attempt is made only while it can still end within 9 s of the first, so a host that accepts and never answers, or a dropped connection, gives up after about 8.5 s, before MapLibre's own 10 s timeout; the tile is then answered 404 (an empty tile), and T138 (`online/StalledOsmTiles.kt`, `OsmSourceRefresh.kt`) records it (`oStall` in the timeline) and fetches it again in the background once the online fetcher's 30 s per-tile failure memo has passed (then after 60, 120 and at most 240 s; given up after 30 minutes or when the style loads), and once one comes back (`oBack`) replaces the map's vector source in place (`osmRefresh`; T144: recoveries are coalesced, `OsmRefreshCoalescer`: the first opens a settle window of 10 s, the refresh comes 2 s after the last recovery or at the window's end, never twice within one window, so a trickle of 20 retries over 31 s got 3 refreshes where T138's rule redrew every layer every 5 to 6 s; the swap is posted to the UI thread, and one the map skipped because its style was loading is asked for again at the next look): the layers that use it are taken off, the source put back with a new tile URL version (`-o<n>`) and the layers re-added at their indexes, so MapLibre asks for its tiles again and the recovered ones are drawn with no style reload (`GET /health` `map.styleLoads` unchanged); `GET /online` `stalledOsm` (`pending`, `recorded`, `retried`, `recovered`, `givenUp`, `droppedByStyleLoad`, T144's `settleMs`, `quietMs`, `refreshes`, `coalesced`, `refreshPending`, `skippedRetried`, and `sourceRefreshes`, `lastSourceRefresh`). Not a 503: MapLibre never asks for an errored tile again (its tile loader drops the request with the answer) and the map never counts as fully loaded with one in view, so a view with a failed tile never went idle (tried on the emulator, T138). Measured with the base pointed at a host that accepts and never answers: an unvisited Glacier/Waterton z11 view idle in 11.8 s with hillshade and contours but no vector features; host restored, the first tiles fetched again 6 s later, the source replaced at 8 s (60 layers) and 122 vector features drawn, the last tile at the next retry a minute later; no style load throughout; `osmStalls` and `osmGuardMs` in `GET /firstrun/direct`; the TileJSON fetch takes the same guard. Before, 30 s an attempt and two attempts held the loopback request and `/health` `pendingTiles` for up to a minute while the DEM was long done: finding `../findings/2026-10-16-cold-view-gap-on-a-quiet-device.md`. Test hook, debug builds only: `POST /firstrun/direct/osm-base?url=http://10.0.2.2:<port>|default` fetches the tiles from that scheme and host, a host-side socket that accepts and never answers) and, in debug builds, `camera z<zoom>` (a `POST /camera`, where a script's view starts: the device tour's quiet wait before its first view is a stretch with no request in it). Release builds have no debug routes: the same lines go to logcat (`adb logcat -v epoch -s DystopoDirect:V`, `trace <ms> <event>`; logcat's clock is the device's), T106: without the places, tile columns and rows and source file names replaced (`dem? 12/-/-`, `read - 812 KB 640 ms`; `DirectTrace.redact`), since logcat reaches `adb` and bug reports; debug builds keep whole lines. How a view is scheduled: while direct, DEM, contour and shade requests run on the loopback server's wait pool (up to 48 workers, no queue; `server.pools.wait` in `/stats`), so they never hold the tile or generation workers, and the map's DEM requests have their own threads; renders at the view's zoom wait up to 1.5 s for coarse renders in flight (`COARSE_FIRST_MS`, tiles below z12, which MapLibre shows first), and the source pool queues block reads by priority (coarse tiles, then the view, then out-of-view tiles); a tile deeper than `directMaxZoom` renders its ancestor and in-view neighbours together, then the out-of-view ones its edge needs; source connections are kept alive. A 503 to a request made before the last reload brings no further reload. A contour tile made with an out-of-view halo tile left out is cached under a key naming it (`<key>.halo-z-x-y[_...].pbf`, `OnlineTiles.contourKey`), so it is made whole once that tile exists; T106: making a tile again deletes its other `.halo-` variants (`/online` `contours.haloVariantsDropped`; they stayed until the cache trim). A render interrupted while it waits for the coarse renders or a permit gives its counters back (`online/RenderSlots.kt`, T106). LERC2 headers are checked before anything is allocated (8192 px a side, 16 M pixels, micro block 256), and a GeoTIFF level reads its tile index on its first tile, not at open. T110, the cold no-server z8 view of the device tour on fresh AVDs: 9.7 to 14.5 s after the quiet wait, 7 DEM renders, 12 blocks and 21 range reads (5.1 MB) for the view itself, which is mostly the reads (9.7 to 18.5 s summed over threads); blocks decode in 0.01 to 0.1 s each there, and in 1.8 to 3.3 s each while the just-booted device is busy (`android-emulator.md`), so the 43 s T105 saw is the device's load. The LZW decoder (3DEP's compression) is one loop over plain locals since T110: 1.8 times faster interpreted (HotSpot `-Xint`, 240 to 135 ms a block), byte for byte the same.

## No Wi-Fi gates

**No Wi-Fi gates** (owner's rule, 2026-10-11): nothing in the app is limited to Wi-Fi; everything except LAN discovery works over mobile networks. Data use is steered by visible limits (the direct-sources session limit, cache budgets), never by a network-type check that silently fetches nothing. T83 flipped the T80 default (`directOnMobileData` on; the setting stays, the "needs Wi-Fi" message is gone) and its update check and download run on any network.

## Pinned areas and content versions

**Pinned areas and content versions** (T95; `online/OnlineFetcher.kt`, `areas/`). The phone's online tiles are keyed by the server's content versions (T74: `GET /version`; `dem` changes with any `/build`, `osm` with a new OpenFreeMap planet). A pinned offline area records the versions its tiles were fetched at. When the server moves on, the area's `dem` and `osm` tiles are kept at that version and served from it, online and offline, until the area is updated: its card in Offline areas says "Older than the source" and offers Update, and the Storage screen's pinned row names it. While navigating online, the prefetch ahead refreshes the segments ahead. Other old-version tiles, and the contour and shade tiles made from an old DEM, are dropped as before. The trip's Offline button shows the corridor's size before it downloads and refuses one over the offline areas' budget (`pinnedCacheMb`). T106: an area fetched from another source than the phone reads now (its server changed, or no server became one) is older too, its card says "Downloaded from another source. Update downloads it from the one set now.", and a whole Update deletes the old source's tiles in its cover (`refreshDropped`) that no other area fetched from there holds; `GET /areas` `pinnedBySource` lists the pinned tiles and bytes per source key with `inUse`. An unpinned area stays unpinned until the budget lets its Update go on (a refused Update pinned it before). A failed, cut short or refused download offers Retry and Dismiss on its card (Dismiss clears the message and keeps what is on the phone, or removes an area with nothing downloaded). `POST /online/cache/clear` keeps pinned tiles (`pinned=1` for all). Rule and reasons: docs/PLANNING.md › Design goals, "Pinned tiles and content versions".

## In-app updates

**In-app updates** (T83; `androidApp/.../update/`, routes in `UpdateRoutes.kt`). Release builds read the public releases API (`https://api.github.com/repos/jasondorjeshort/dystopo/releases`, no token, pre-releases included) 15 s after start and then once a day (a failed check retries after an hour; T99: a build installed over another one, by the in-app update or by hand, checks at its own first start, because the check times count only under the versionCode that recorded them, `checkedByCode`), and on "Check for updates" (Settings, the Updates row under Sources; it also shows a declined version again). `UpdateFeed` picks the newest non-draft release with a `dystopo-*-universal.apk` and calls it newer when its `version.json` versionCode is above ours, or, for releases without `version.json` (v0.1.2-alpha, v0.1.3-alpha), when its tag's numbers are above our version name's (`0.1.3-alpha-12-g...-sweep` counts as 0.1.3). A newer one is downloaded to `cache/updates/<name>.part` (redirects checked by `CleartextPolicy`; with the default feed every URL and redirect target must be https on github.com, api.github.com or *.githubusercontent.com, `UpdateFeed.githubUrlProblem`) and renamed, and offered, only when its SHA-256 matches `SHA256SUMS.txt` (and `version.json` when present), and the package manager reads it as our package with a higher versionCode signed by exactly the running app's certificates (`Signing`, SHA-256 of each certificate; the release key's starts `47313810a4313ca3`); otherwise it is refused with the reason in Settings and once on the map (OK hides it; a refused version is not downloaded again by the daily check). A verified one shows "Update to <version>" on the map (Install, Not now; T106: the offer and a refusal's card report their top edge, `MapInsets.updateCardTop`, and the recentre button, the scale bar, the long-press card with the other track panels, and the first-run card sit above it; it waits while a trip, the Routes list or a planned route's card is open (T110: not during navigation, which hides that card), and comes back when they close; Settings' Updates row wraps its buttons, so Install stays on the sheet at font scale 2.0; T110: it sits above the credit line, whose two lines at font scale 2.0 it covered; installing replaces the running app, so during navigation the offer says "Installing closes the map and ends navigation." and offers After navigation, Install now and Not now, and an install asked for during navigation (the offer, Settings' Install) waits for the session to end and then starts by itself, "Installs when navigation ends.", with Install now on the offer and in Settings; the offer's height is capped to the room below the navigation card, so it never covers it, and with less than 96 dp of room it waits; `GET /update` `waitingForNavigation`, `overlay` with `clearOfNavCard`; `POST /update/install?now=1`) and as a notification (once per version, if notifications are allowed); Install hashes the bytes it writes into a `PackageInstaller` session and commits only when they are the checked ones (`REQUEST_INSTALL_PACKAGES`; the first time Android asks to allow installs from Dystopo: Settings, the switch, back, then Update), and Not now or a cancelled installer declines that version for the daily check. The verified file survives a restart (re-checked). Debug builds never check by themselves (no banner in device tours): `GET /update` (state, version, signers, API in use), `POST /update/check[?api=<releases URL>|default][&wait=0]`, `POST /update/install`, `/update/dismiss`, `/update/ack`, `/update/reset`. A release build is pointed at another feed only by `update-api.txt` in its external files dir naming a URL on the device or the home network (`adb shell "echo http://10.0.2.2:9171/repos/jasondorjeshort/dystopo/releases > /sdcard/Android/data/io.github.jasondorjeshort.dystopo/files/update-api.txt"`; other hosts are ignored); whatever the feed, only an APK signed with our key is offered. `release.yml` writes `version.json` (`tag`, `versionCode`, `versionName`, `apk`, `sha256` of the universal APK) next to the APKs and into `SHA256SUMS.txt`. Tested by taps with `python -I tools/android-ui.py update` (release realism, below).

## First run

**First run** (T79; `androidApp/.../firstrun/`). A fresh install with no pack shows the first-run card over the map: "Download the map around me" (the last fix, else the last known location, else up to 30 s for a fix; a 16 km box around it through T38's region download from the configured server, or built on the phone without one (T80)), "Show the map around me" (T80, camera to the fix), "Choose from server" (the pack list with "From server" open) and "Import pack files" (the system file picker, several files at once: `PackManager.importFiles` copies each into the packs dir, validates it like a download (whole PMTiles archive, the role from the name checked against the tile type, raster = terrain, MVT = map), then the pack joins the map like a download; nothing is installed when a file fails). "Not now" hides it for the session (then the plain no-pack line names the same three). T106: it also gives the bottom of the map to an open trip card, the Routes list, a planned route's card or navigation, and comes back when they close (`GET /firstrun` `cardYieldedTo` `bottomCards`; it covered the trip card after a relaunch with no pack). The Settings sheet starts with **Sources**: the server URL, Save (as `POST /settings?server=`), Test (fetches the catalog: "Connected: N packs on <server>" or the error; N is the server's catalog, so the sweep's first-run server, which starts with an empty `server-out`, reads 0 while the Rainier pair arrives by import, T106) and "Packs ›"; the pack list's "From server" status links there when no server is set or the catalog fails. **Cleartext**: Android's network security config cannot express address ranges, so `res/xml/network_security_config.xml` (one file, debug and release) permits cleartext and `firstrun/CleartextPolicy.kt` gates every `HttpURLConnection` the app opens (online tiles, catalog, builds, pack downloads, sync, phone-to-phone sync links): https anywhere, plain http only to loopback, 10/8, 172.16/12, 192.168/16, 169.254/16 (dotted-decimal IPv4 without leading zeros: `010.0.0.1` is refused), IPv6 unique-local and link-local, and `.local` names. Automatic redirects are off (Java follows same-protocol redirects by itself, so a private server's 302 to a public http address would bypass the check); the pack downloader follows them through `CleartextPolicy.redirectTarget`, which checks each `Location`. Not covered: the Share screen's LAN client (`share/LanHttp.kt`) uses a raw socket, and its payload is encrypted end to end under the share code (T72); the server setting (sheet or `POST /settings?server=`) is a 400 with that message otherwise. Messages that send the user to a screen name only screens in `firstrun/Screens.kt` (`ScreenNamesTest` checks every string literal and that each screen has a chip). Debug routes (`FirstRunRoutes.kt`): `GET /firstrun` (card state, server, the around-me step and box, region download, last import, last server test), `POST /firstrun/download[?lat=&lon=]`, `POST /firstrun/test[?server=]` (502 when it fails), `POST /firstrun/dismiss[?undo=1]`, `POST /packs/import?dem=<path>[&osm=<path>][&name=]` (paths absolute or under the app's external files dir; 400 with the reason for a truncated file or a missing terrain file), `GET /packs/import`, `POST /packs/import/pick`.
