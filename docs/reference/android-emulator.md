# Android emulators on this machine

Booting, running several side by side, and the host requirements. Paths and ports: `machines.md`. Device matrix flags (`-Api`, `-Device`, `-Locale`, `-FontScale`, `-Dark`, network flags): `release-realism.md`.

## Several emulators side by side

Several emulators side by side (one per task): own AVD, console port and host port; the script uses the serial `emulator-<EmuPort>` for every adb call, prints it, and refuses a console port or host port that belongs to another AVD (`-Port` is the host side, forwarded to the debug server's device port read from logcat). `-Gpu` defaults to `host` when there is a hardware GPU: under `swiftshader_indirect` MapLibre draws no text and no dash patterns. The GPU mode is fixed at boot (`-Stop`, then boot again); every run reinstalls the app and re-pushes the packs (`-PackName rainier` pushes a named pack, `<name>-dem.pmtiles` / `<name>-outdoors.pmtiles`). `-Build` writes `local.properties` if the worktree has none. T65: the script's progress (build, boot, install, push) goes to the output stream, so `| Tee-Object`, `> log` or a parent process see each step as it happens. Each AVD takes about 6 GB: on this machine put task AVDs on E: with `-AvdHome E:\dystopo-avd` (C: ran out of space with eight), and remove them when done with `-Stop -Delete` (same `-AvdHome`). T105: `-Server <url>|none` sets the app's server from its first start (written into a fresh install's preferences with `run-as`, then `POST /settings?server=`); without it a debug build on an emulator uses the host's 8765, the coordinator's live viewer, so give a task emulator its own server or `none` (`android-check.py --server` does the same before a tour). Pass the serial to the checker too, so it refuses to drive anything else:
```
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build -Avd dystopo35-T28a -AvdHome E:\dystopo-avd -EmuPort 5570 -Port 8694   # serial emulator-5570, debug server on localhost:8694
python -I tools/android-check.py --port 8694 --serial emulator-5570 --views-file tools/android-tour.txt --out out/t28a/tour.png
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd dystopo35-T28a -AvdHome E:\dystopo-avd -EmuPort 5570 -Port 8694 -Stop -Delete   # kill it, drop the forward, delete the AVD
```

**The Rainier packs in a worktree.** The script pushes `out\rainier-dem.pmtiles` and `out\rainier-outdoors.pmtiles` from the checkout it runs in (`-Dem`, `-Osm`), and a new worktree's `out\` is empty. Copy the two packs from the main checkout's `out\` into the worktree's `out\` (in Git Bash `mkdir -p out && cp <main>/out/rainier-dem.pmtiles <main>/out/rainier-outdoors.pmtiles out/`); never a junction or symlink to the main `out\`, which removing the worktree follows and deletes (`CLAUDE.md`, Working in parallel). When a chore is still building them, wait in the foreground for its file (`until [ -f <main>/out/rainier-outdoors.pmtiles ]; do sleep 30; done`, or the marker the brief names) before copying. The sprite sheet needs no copy: every push makes it (below). `tools\sweep.ps1` copies the packs itself from `-DataDir`.

**Two starts at once** (T147, T137's follow-up): two `android-emu.ps1` runs in one checkout, each with its own AVD, console port and host port, can start together. `android-push-pack.ps1` makes each run's sprite sheet (`devtool sprite`) in a folder of the run's own, `out\push-pack\<pid>-<random>\` with its `sprite.log`, pushes it from there, then renames each file over `out\sprite*` (where `android-release.ps1` and `android-ui.py` read it) and deletes the folder; before, both runs wrote `out\push-pack-sprite.log` and `out\sprite*`, and the second run's step failed because its log was open in the first. Glyphs fetched into the shared cache land under a name of the run's own and are renamed. With `-Build` the two builds take turns (a lock per checkout; the second finds the APK up to date) and each writes `out\android-emu-build-<Avd>.log`. Tested with two real starts on consoles 5652 and 5654, both booted with the pack pushed.

## Host requirements

The emulator needs CPU virtualization, which an administrator enables once: Windows Hypervisor Platform (`Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All`, reboot) or the Android Emulator hypervisor driver. Without it, x86_64 images never start under `-accel off` and ARM images are refused on x86_64 hosts, so `android-emu.ps1` stops with these instructions; `-NoEmulator` uses a phone connected with USB debugging instead.

## Known quirks

- Under `-gpu swiftshader_indirect` MapLibre Native draws no text and no dash patterns; `-Gpu host` is the default when there is a hardware GPU, and the GPU mode is fixed at boot (finding `../findings/2026-10-10-emulator-software-gpu-draws-no-text.md`).
- Images before API 30 need `-Feature GLESDynamicVersion`, or the emulator offers only OpenGL ES 2 and MapLibre crashes in its render thread.
- On API 35 emulators keep wifi enabled, or 10.0.2.2 (the host) is unreachable.
- A screen capture (`adb exec-out screencap`) can come back empty right after a fresh install, or cut short while a build runs beside it (wave 22's sweep, T173). The scripts capture through `Device.capture` in `tools/android-firstrun.py` (T185): it checks the exit code and the bytes (a whole PNG, or a raw frame whose length matches its header), retries after 0.5, 1, 2 and 4 s, never writes an empty PNG, and each `android-ui.py` part and the first-run report count `captureRetries` (with `captureRetryReasons`). The device tour asks a GET whose body arrived cut short (`IncompleteRead`) once more, never a POST, and its summary's `connection` counts it (`incompleteReadRetries`). The sweep adds the non-zero counts to the part's `steps.tsv` line.
- adb on the second PC drops a host forward now and then (T155, T170): a request then fails with a refused connection. The device tour (`android-check.py`) forwards the port again to the app's device port (`--no-rebind`, so never a port another device holds) and sends the request once more, counted as `connection.forwardRestores`; the debug-build parts of `android-ui.py` (`routes`, `search`, `bothunits`) do the same through the logcat line (`forwardRestores` in their report). To try it: `adb -s <serial> forward --remove tcp:<port>` during a tour.
- A just-booted emulator is busy for minutes: a new API 35 AVD with four cores used 1.6 to 3.9 cores besides the app (from `/proc/stat`) for two and a half to three minutes after `sys.boot_completed`, then 0.0 to 0.3; `android-emu.ps1`'s install, pack push and first start take the first one to one and a half of them. A cold view started in that time took 40 to 47 s instead of 10 to 18 (T88, T98); `android-check.py` waits for a quiet device before its first view (`--quiet-cores`, T105: 75 and 100 s on two fresh AVDs, then the z8 view in 16.6 and 11.0 s). T110, five more fresh AVDs with no server (two, at the end three, other emulators on the host): the busy time comes in two parts, 2 to 3 cores besides the app for the first half minute after the setup and 3.3 to 3.8 cores from about 45 to 85 s, with a dip of one sample (1.1 to 1.6 cores, once 0.8) between them; the quiet wait took 71 to 90 s and the cold no-server z8 view then 9.7 to 14.5 s (before and after T110's changes). Renders on the busy device decode a 3DEP block in 1.8 to 3.3 s against 0.01 to 0.1 s on the quiet one, so a view started there (24.2 s with the wait cut to 19 s; T105's 43 s) pays for the device, not for the view; the first view of a tour now waits up to 60 s for idle and every view reports `idleSeconds` and `deviceCpu` (`android-app.md`). T115, one more fresh AVD whose tour started about three minutes after `sys.boot_completed`: quiet wait 6.2 s, cold no-server z8 view 11.2 s; a first view that stays not idle on a quiet device is a request still open at the loopback server (`notIdleBecause` in the tour's report), finding `../findings/2026-10-16-cold-view-gap-on-a-quiet-device.md`.
- Two emulators on one host share a virtual Wi-Fi network (`wlan0`, 10.0.2.x): they discover each other over NSD and connect directly to each other's `10.0.2.x:8841` when both have a Wi-Fi carrier; an emulator that never gets one can only go through the host (`adb forward`, reached at 10.0.2.2), so restart it (finding `../findings/2026-10-10-emulator-share-direct-connect.md`, resolved by T90). Every agent's emulators share that network, so discovery also finds other agents' phones; keep a pair to itself with `iptables` (`android-tracks-and-sync.md`).
