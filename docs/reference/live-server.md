# The browser demo, live world mode and the JVM stand-in for the phone

The viewer agents and the owner use, and how to check it headlessly. Ports and the coordinator's own servers are in `machines.md`; server deployment is `../SERVER.md`.

## Browser demo

Browser demo (MapLibre over our DEM tiles and OSM PMTiles): generation commands are at the top of `tools/demo/index.html`; then `python -I tools/demo-server.py 8765` and open http://localhost:8765/tools/demo/. Units there are a stored preference (localStorage), seeded by region on first open, changed with the Units select; `?units=ft|m` overrides one load. T107: the scale bar (bottom left) is a port of the phone's rule (T101, `UnitFormat.scaleBar`: 1, 2 or 5 times a power of ten that fits 100 px, in feet up to 500 ft then miles from 0.1 mi, or metres up to 500 m then kilometres); `demo-check.py` checks the port against the Kotlin test's cases on its first view (`scaleRule` in the JSON) and reports the bar shown per view (`scale`). T107: in live mode the Map options' Slope shading select offers off, avalanche and steepness (T104's `slope` option; `?slope=on` still means avalanche) and shows the phone's legend under it: the band swatches in degrees, what they mean and "Slope shading is not an avalanche forecast." (`SlopeLegendTest` keeps the page's bands and words equal to `Slope` and the phone's Map options). The demo tour (`--views-file tools/demo-tour.txt`) must pass against both this page and `devtool serve` (its `req=` names are roles mapped to each style's layers). **Agents check it headlessly** with `python -I tools/demo-check.py --view <z/lat/lon> --out out/check.png` (Playwright + Chrome): exit 0 means the map went idle with no console errors, page exceptions, or failed requests; the JSON lists rendered feature counts per layer and the screenshot path, so you can see what a user would see. A zero count on a layer that should have features is a bug, not a style choice.

## Live world mode

**Live world mode:** `./gradlew :devtool:run --args="serve --live --port 8687"` and open http://localhost:8687/ (the same demo page). Packs in `out/` (and `--dem`/`--osm`) answer the tiles they hold; everywhere else the DEM is rendered on request from the `best` source (3DEP, Copernicus, EGM2008) through the `tiles` per-tile path, contours are generated from it, and OSM base layers come from OpenFreeMap (registry id `openfreemap`; outdoors-only layers exist only inside packs). Both are cached under the cache dir (`live/`, `openfreemap/`; T74: with contours and shade in `derived/`, each byte-capped with LRU, `DYSTOPO_CACHE_CAPS=live=4096,openfreemap=2048,derived=1024` MB, `DYSTOPO_TILE_CACHE` to keep them apart from the source downloads, `/stats` `caches`), so a second view anywhere is warm; the first view of a new place takes 10 to 30 s. The box at the top right says which source the visible tiles came from (pack, live-3dep, live-copernicus, openfreemap); `Build pack here` calls `POST /build?name=&bbox=&minZoom=&maxZoom=` (see `BuildRoutes.kt`: progress at `GET /build/{id}`, cancel with `DELETE`), which writes `out/<name>-dem.pmtiles` from the live DEM and `out/<name>-outdoors.pmtiles` from OpenFreeMap tiles (OpenMapTiles schema, not the outdoors profile), serves them under `/out/` and from then on as packs. With `&profile=outdoors` (the page's Vector select) the vector pack is the real outdoors profile instead: one Overpass request for the box (cached) when it is under 0.05 square degrees, else a Geofabrik extract on disk in `cache/extracts/` or one downloaded on demand from the regions in `extractDownloads` (`DYSTOPO_EXTRACT_DOWNLOADS` for `serve`), each covered by its `.poly` polygon; a box nothing covers gets a 422, and 413 is only for a forced `source=overpass` over the cap (T66), converted and built by tilebuild in a subprocess, so run `./gradlew :tilebuild:installDist` once (and again after changing tilebuild); `&fallback=1` falls back to OpenFreeMap when Overpass refuses. Small boxes read only the ocean polygons that reach them (none inland; `waterPolygons` in tilebuild's report), so a Paradise-sized rebuild takes about 5 s warm. `GET /stats` has per-route, per-source tile counts and timings, `/phone` the phone style over the live routes. **Map options** (the phone's T47 settings) work in both `serve` modes as query parameters of `/style.json`, `/phone` and `/` (the demo page also has a Map options section that writes them to the URL): `hillshade=off|single|multi`, `hillshadeIntensity=0..1`, `slope=off|avalanche|steepness` (T104; `on` is avalanche), `contourInterval=auto|<n>` (in the contour units), `contourLabels=sparse|normal|dense`, `night=on`, `trails|water|landcover|pois|boundaries=off`; a bad value is a 400. The style then points at `/shade/{z}/{x}/{y}.png?...` (hillshade and slope rasters from the DEM, as on the phone; `shadeGeneration` in `/stats`) and `/contours/...?interval=<n>`. Check it with `python -I tools/demo-check.py --url "http://localhost:8687/?live=1" --views "12/45.83/6.86|src=live-copernicus" "12/46.85/-121.76|src=pack"`: in live mode every view must also show hillshade and OSM features, and `|src=` checks the DEM source. T92: the elevation readers' own downloads have a byte budget (`DYSTOPO_SOURCE_CAPS=request=256,hour=8192`, MB per download and per hour, 0 for none; `/stats` `sourceDownloads`), and at start the server deletes once per cache the live tiles rendered from Kartverket data before T66's zero-cell rule (`staleCachePrune.norway-zero-rule` in `/stats`; it touches the shared `DYSTOPO_CACHE`, which is regenerable).

## Trip editor

**Trip editor** (T68, live mode; `tools/demo/trips.js`, routes in `RouteRoutes.kt`, docs/SERVER.md › Route planning): T107: the Trips box at the top right (the layer panel on the left keeps the map, "Build a pack here" and the Server token); with "Plan a route" on, click the start and the end, click again to add a via point, drag a numbered point to move it, right-click to remove it. The open route's card in the box has distance, time, climb, descent, the profile (hover it), the trip's waypoints, T111: the route's turn directions (T102's `instructions` from the server's reply, at the phone's default detail level, each with the distance to the next in the page's units: the count, the first five, "Show N more" for the rest and "Show fewer"), "Save trip" (into the browser's own sync replica in localStorage, then pushed to the server's `/sync/push`; a phone syncing with the server gets it; T116: with its directions, the reply's `directionsValue` written as the trip's `directions` after each path, so the phone shows them with no graph), "GPX file" and "Clear"; below it the saved trips and "Get from server", "Send to server", ".dsync file". At phone width both boxes start closed, opening one closes the other and planning closes the Trips box. Every request the editor makes carries the Server token when one is set. Its distances follow the phone's rule (T101, `UnitFormat.distance`: metres, then kilometres with two decimals below 10; feet below a tenth of a mile, then miles with one decimal); `--route` checks the port against the Kotlin test's 29 cases (the `distance rule` step). `window.dystopoTrips` scripts it. Check the flow with `python -I tools/demo-check.py --url "http://localhost:8687/?live=1" --views "12/46.85/-121.76|src=pack" --route "46.7864,-121.7366;46.8024,-121.7289;46.7960,-121.7262"` (Paradise to Panorama Point with real clicks, a via point added on the line and dragged to the third place, GPX, save and push; `route` in the JSON, screenshot `<out>-route.png`). T111: its `directions` step checks the card's directions after the drag: the count in the title, the first five lines against the server's texts, the arrival last, a click on "Show N more" lists every one (screenshot `<out>-route-directions.png`) and "Show fewer" folds them; the Paradise to Panorama Point hike with its dragged via point has 10 (in feet), the Paradise to Sunrise drive with `--route-mode drive` 14 of 16 (in metres with `?units=m`). T111 (after T108): the Mode select offers Crow, T108's straight line between the points: the phone's line under its picker ("A crow route is a straight line between the points, not a path to walk.", `TravelMode.CROW_NOTICE`, also the crow route's `notice`) shows under the select, the card gives each leg's bearing ("Bearing 18° (north)", from the reply's `summary.bearings`, words of `Directions.compass`) and no off-trail count, and the directions list holds the arrival only; `--route-mode crow` checks all of it (the `crow` step). T116: the `saved directions` step after the save: the browser's `directions` op is the open reply's `directionsValue`, after the trip's last `path` op, and the server's replica counts as many saved directions for the trip's path (`GET /sync/routes?full=1` `directions`); the `bundle` step writes the browser's trips as `<out>-route.dsync` for `devtool sync-sim --bundle` (docs/reference/devtool-commands.md). The texts carry the server's "then" cues (T116, `Directions.cued`). `BrowserTripsTextTest` keeps the select's modes, the crow line, the compass words and the directions' detail level equal to the shared code. **Long drives** (T77): `--long-route "47.6062,-122.3321;46.6021,-120.5059" [--long-route-packs 2] [--long-route-ms 10000]` clicks both ends in drive mode (`--route-mode`) and checks the route follows roads across at least that many packs within the time (`longRoute` in the JSON, `<out>-long-route.png`; needs packs covering the way in `out/`); the card says how many packs and overlay tiles the server used. Long drives search through `DriveOverlay` (docs/PLANNING.md › Routing; `GET /route?...&overlay=0` to compare). T92: `tools/demo/trip-sync.js` (served as `/trip-sync.js`, loaded after trips.js) adds "Get trips from the server" (`GET /sync/routes?full=1`: trips saved or edited on a phone, renamed or deleted elsewhere, come into the browser's list) and waypoints for the open saved trip ("Add waypoint", click; drag to move; rename or remove in the list; each edit a `wpt:<id>` operation pushed like any trip edit). Check: `python -I tools/demo-check.py --url http://localhost:<port>/ --view 14/46.794/-121.733 --route "46.7864,-121.7366;46.8024,-121.7289" --trip-sync [--token <user token>]`. On a server with users, `/route*` needs the page's Server token (trips.js and trip-sync.js send it with every request; T107 removed the page's fetch wrapper). T107: `--late-trips 12/45.83/6.86` (with `--route` after it) holds trips.js back until the map is loaded, releases it while the style is loading tiles elsewhere and checks the editor still adds its map layers (`lateTrips` in the JSON; before T107 it waited for a `load` event that had already fired and no route line ever drew).

**Route state files and `/route/status`** (T89; live mode only: plain `serve` answers 404 on `/route*`; the full field list is docs/SERVER.md › Route planning). A pack's graph opens on its first route, so right after a start `GET /route/status` has empty `graphs`, `driveOverlay.warm` and `cellFiles`. The first route then writes `out/<vector archive>-graph.idx` (`DYSG` v5; an older file is rebuilt, `graph.rebuildReason` in the route reply says why), and a drive-capable pack gets a background warm-up that writes `out/<vector archive>-overlay.idx` (`DYSO` v1: the drive overlay's z11 and z8 cells). For `rainier-outdoors.pmtiles` that is `rainier-outdoors-overlay.idx`, 1,549 bytes (15 level-1 and 2 level-2 cells), whose `warm` entry reads `state: "done"`, `cells: 15`, `level2Cells: 2` and `ms` 100 to 170. After a restart the next route finds `state: "loaded"` (`cells: 17`, `ms` 1 or 2) with `built: 0` and `level2Built: 0`, and `loadedFromFiles` counts the cells later drives read from it. `corruptGraphTiles` is `[]` unless a graph tile failed its checksum: such a tile is skipped, so routes near it fail as if the roads were missing, and the list names it (`file`, `x`, `y`, `error`). The list is in memory only (a restart empties it and the next route to the tile finds it again), so to repair, stop the server, delete `*-graph.idx` and `*-overlay.idx` in `out/` (both regenerate), start it and route: the graph is rebuilt (`rebuildReason: "missing"`), the list is empty and the warm-up writes the cell file again. Agents' servers write these files into their own worktree's `out/`, never the main checkout's.

## No device: `devtool serve` as the phone stand-in

**No device?** `./gradlew :devtool:run --args="serve"` serves the same routes from the same shared code (style, DEM with ancestor fallback, generated contours, glyphs from `cache/glyphs`) on http://127.0.0.1:8687/ with a MapLibre GL JS page, so the phone style can be checked with `python -I tools/demo-check.py --url http://localhost:8687/ --views 12.5/46.853/-121.76` (MapLibre GL JS, not Native: it catches style and tile bugs, not Android ones). `GET /stats` there gives desktop contour timings.

## Conventions for the coordinator's servers

- The coordinator's live viewer runs from the main checkout on port 8765, started by a chore agent from the installed distribution, not through Gradle (`./gradlew :tilebuild:installDist :devtool:installDist` once, then `devtool\build\install\devtool\bin\devtool.bat serve --live --port 8765` detached with `DYSTOPO_CACHE` set; a server started with `./gradlew :devtool:run` lives inside a Gradle daemon and dies when anyone runs `./gradlew --stop`, which happened twice on 2026-10-12), its PID recorded in `out/coordinator-pids.txt`. Agents read it; they never stop it and never ask it to build (`android-firstrun.py --until test` only reads its catalog).
- First-run tests use the standalone server (it binds 0.0.0.0) at the host's LAN address, not `devtool serve` (127.0.0.1 only) and not 10.0.2.2, so the private-range rule is what is tested (`android-online.md`, First run).
- A task's own server uses the ports in its brief and is stopped by its PID.
