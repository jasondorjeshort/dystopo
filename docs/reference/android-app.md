# The Android app: build, emulator scripts, device tour, loopback token

How the app serves the map and how agents drive it. Emulator setup and several emulators side by side: `android-emulator.md`. Every debug route: `android-debug-routes.md`.

## What it is and the scripts

`androidApp/` (Compose + MapLibre Native + `shared`) shows a region pack: hillshade from the DEM PMTiles (MapLibre `raster-dem`), OSM from the outdoors PMTiles, and **contour tiles generated on the device** (`shared/.../tiles/ContourTiles.kt`, cached on disk). MapLibre can't read PMTiles, so the app runs a loopback-only HTTP server (port 8686) serving `/dem`, `/osm`, `/contours`, `/glyphs` and `/style.json`; in debug builds the debug routes are on a second loopback server on a random port (T57, below) (the MapLibre style is translated from the devtool's `DefaultOsmStyle` by `shared/.../maplibre/MapLibreStyle.kt`). The module and `shared`'s android target exist only when an SDK is installed (`settings.gradle.kts` looks at `local.properties` / `ANDROID_HOME`), so SDK-less machines still build.
```
powershell -ExecutionPolicy Bypass -File tools\android-sdk.ps1     # SDK under %USERPROFILE%\Android\sdk + local.properties (no admin)
./gradlew :androidApp:assembleDebug
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build   # headless emulator, install, push out/rainier-*.pmtiles, launch, forward -Port to the debug server
powershell -ExecutionPolicy Bypass -File tools\android-push-pack.ps1 -Dem out\rainier-dem.pmtiles -Osm out\rainier-outdoors.pmtiles   # packs + glyphs only (-NoOsm: DEM only)
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd <avd> -EmuPort <n> -Port <p> -Forward   # after an app restart: re-read the debug port and token, re-forward
python -I tools/android-check.py --port 8686 --serial emulator-5554 --views-file tools/android-tour.txt   # device tour: JSON summary, out/android-tour-sheet.png; exit 1 on failure
```

## Settings

The Settings chip opens the settings sheet (`SettingsSheet.kt`, rows in `settings/`) on a list of groups (T103): Data and storage (Sources with the server field first, Storage ›, Offline areas ›), Map options (`options/MapOptionsSection.kt` placed whole, Night and the scale bar included), Units and display (Units, Text size), Navigation and tracking (Route snap and the two navigation thresholds), Sync and sharing (Sync status ›, Share ›), About and advanced (Updates, Contour warm-up, Credits: the Map data and sources screen). A tap opens a group's page, "‹ Settings" or Back returns to the list, and closing forgets the page; on a window 720 dp wide or more (a tablet) the list and the open page sit side by side. A list rather than tabs, because six tab labels do not fit across a phone at font scale 2.0 while list rows wrap at any text size; every row's choices wrap too. The server field stays two taps from the map (Settings, Data and storage), and the first-run card's Settings link, the pack list's "No server set" line and Download without a server open Data and storage directly. `settings/SettingsLayout.kt` is the order of groups and rows that the pages draw and `GET /settings/layout` returns (`SettingsLayoutTest` compares it with the rows of the old single sheet); `POST /settings/open?group=` opens a page in debug builds (`android-debug-routes.md`). Release builds are driven by text: `open_settings(dev, group, anchor)` in `tools/android-ui.py` taps Settings, then the group, until its page shows the anchor text.

## Map options (the Map section of the settings sheet)

`androidApp/.../options/MapOptionsSection.kt`; each choice is the `POST /settings` key of the same name (`android-debug-routes.md`), except the Scale bar row (T101, `POST /scalebar?both=on|off`). Rows: Hillshade (Off, Single, Multi) and its Intensity, **Slope shading** (T104: Off, Avalanche, Steepness, with "Slope shading is not an avalanche forecast." under it and, when on, a legend: a caption and one swatch per band, the band colour at the map's tint opacity over the paper tone; bands and wording in `GET /shade` `slopeLegend`, sources in docs/PLANNING.md › Slope shading), Contours, Contour labels, Layers, Night, Scale bar. Each row has its label above its choices, which wrap (a `FlowRow`), so nothing is squeezed at font scale 2.0. To screenshot it: `POST /settings/ui?open=1`, scroll the sheet to its end, `GET /screenshot`.

## Storage and the cache budget (T112)

Settings › Data and storage › Storage › (`storage/StorageScreen.kt`, `storage/Storage.kt`) shows what the app keeps on disk. At the top is the **cache budget** (`cachebudget/CacheBudget.kt`; ADR 0025 principle 3, ADR 0034): one total over three kinds, Online tiles (DEM, map and glyph tiles downloaded from a server or OpenFreeMap), Contours and shading (every contour, shade and cliff tile the phone made, from packs in `cache/contours/` or from downloaded DEM tiles in `cache/online/tiles/`) and Source data (the phone's own source downloads when no server is set), with presets Small 1 GB (the default), Medium 8 GB and Large 128 GB, and Custom: a size in GB, or 10, 25 or 50% of the free space turned into a fixed size once (never a live share). A stacked bar shows each kind's part; each kind's row shows its bytes, its share of the total and its floor (Online tiles 25%, Contours and shading 15%, Source data 5% of the total). When the kinds pass the total (checked after every tile write, every 30 s, and at once when the total is set) a run evicts contour and shade tiles first, then from the kind furthest above its floor, least recently used first and across both caches that hold a kind, never below a floor and never a tile in view (the visible box grown by half on every side) or within 300 m of the next 3 km of a navigated route, until 1% of the total (at least 4 MB) is free. Pinned offline areas (their own budget, `pinnedCacheMb`: chips from 128 MB to 128 GB, any size up to 1 TB through `POST /storage`, T115; it stopped at 8 GB before, below the Large preset, with a warning line when it is more than the free space, as for the total) and packs are outside it; Clear stays per row. T115: a help icon on the Cache budget heading and on each row, and the Data and storage line of the settings list names the total ("… storage with a 1 GB cache budget"). `onlineCacheMb` and `contourCacheMb` stay as each cache's ceiling; setting the total sets both to it. An install from before T112 starts at the small preset, or at its two caps together when they were raised past it. Routes: `GET /storage` (`budget`) and `POST /storage?budgetMb=` (`android-debug-routes.md`); the rule was measured with `devtool cache-replay` (`devtool-commands.md`).

## Trips and the trip card (T60, T108)

The Routes chip (top right, under the track controls) opens the Routes list; a trip opens on the map with the trip card at the bottom (`trips/TripControls.kt`): its totals and elevation profile with waypoint flags, the editor (Drag, +Via and +Waypoint, a chip per travel mode, Hike, Bike, Drive and Crow, and one per via point to remove it), then Go, Offline, GPX, Share link and Delete, and Done. T108: the directions saved with the trip sit on the card as "Show N directions", which opens their list (the default detail level, each line numbered with the distance it then runs, scrolling within 160 dp; "Hide directions" closes it); a trip saved without them (before T108, or in the browser) is given them in the background when it opens on a phone whose packs' graph covers it ("Making the directions from the map pack…"), else the card says "Directions were not saved with this route. Open it with its map pack on this phone to add them."; a crow trip shows its bearing instead ("Bearing 18° (north)", one per leg with via points). Routes: `GET /routes/{id}` `directions`, `POST /routes/{id}/directions?open=1|0` and `?save=1` (the KDoc of `trips/TripRoutes.kt`).

## Help pop-ups (T109)

A question mark beside a control opens a short help text about it (`androidApp/.../help/`). `HelpIcon(key)` draws the icon: 24 dp at font scale 1.0, sized in sp so it grows with the font scale as the row's label does, inside a touch target of at least 48 dp (the icon plus 20 dp; T128: `flat = true` lays the target out at the icon's height, overflowing its row, for a short row such as the navigation card's header); its accessibility label is "Help: <title>" and the question mark is not text, so scripts that find a row by its label never meet it. A tap opens the pop-up (`HelpHost`, drawn after the other overlays: since T115 the last line of `MainActivity`'s map screen, so it is over every screen, the Share screen and its scanner included): a faint scrim, and a card with the title, the text and OK, below the icon when it fits there, else above it, with a caret pointing at the icon; T122: when the text fits on neither side (large font scales) the card goes on the larger side with its text a step smaller at a time, down to three quarters of the font scale (never below 1.0), and scrolls only past that (`PopupPlace`, `PopupPlaceTest`); it never covers its icon (at 2.0 it covered three: Sources, Offline areas, Cache budget). An icon laid out outside the window (a row still scrolling into view) counts as none, and a pop-up whose icon leaves and comes back within 300 ms stays open. A tap anywhere or Back closes it. The texts are declared in the file of the control that shows them, as a `HelpText(key, title, placed, needs, show)` in that file's list (`MAP_OPTIONS_HELP`, `SETTINGS_HELP`, `DIRECT_SOURCES_HELP`, `AREAS_HELP`, `TRACK_BAR_HELP`, `LONG_PRESS_HELP`, T115 `STORAGE_HELP`, T122 `NAV_HELP`), which `HelpRegistry` gathers; `HelpRegistryTest` reads the sources and fails on a key a screen names without a text, a text no screen shows, or a text declared in another file than its icon. Texts are one short paragraph (at most 330 characters, so they fit beside the icon at font scale 1.0 and on the screen at 2.0), name no other mapping software (the test and `tools/user-text-check.py`), and put a distance through `UnitFormat` in the units setting (the corridor's 500 m reads "0.3 mi" in feet). Placed on every Map options row and the slope legend, the Offline areas sheet (its title: pinned areas and the budget; the line under it: corridors), Settings › Sources (the server), its Mobile data and Limit per session rows, Units, Text size, Route snap, the two navigation thresholds, Sync status, Share and Contour warm-up, the unfolded track bar, the long-press card, (T115) the Storage screen's Cache budget heading and each of its rows, and (T122) the navigation card: its header (`nav.card`), the "No GPS fix" line (`nav.fixLost`) and the off-route banner (`nav.offRoute`), each needing a navigation session in that state (`POST /help/open` cannot start one: 409 otherwise). A text's placement (`GET /help` `placed`) reads as messages name screens, "Settings › Map options › Hillshade": T115 made the settings groups sections in `firstrun/Screens.kt`, and `HelpRegistryTest` checks every placement against it as `ScreenNamesTest` checks messages. Debug routes: `GET /help`, `POST /help/open?key=`, `POST /help/close`, which since T115 also closes what `/help/open` brought up for the icon (`android-debug-routes.md`).

## Route to here (T114)

A long-press on the map opens a card whose first action is Route to here: a route from the phone's position to the pressed point, planned at once in the route card's mode (`routing/RouteSession.kt`; the conventions it follows are the finding `../findings/2026-10-17-route-to-flows-in-other-apps.md`). The position is the newer of the recorder's last fix and the map's device fix, the Waypoint chip's "here" (`routing/RouteOrigin.kt`). The route card names both ends: "From: Your location" (with the fix's age when it was older than 120 s: "Your location, 14 min ago") and "To:" the point's coordinates; Change on the From line offers Your location, Choose on map (the next long-press is the start) and Swap. With no fix yet the card says "Waiting for your location..." and plans on the first one; with the location setting off or the permission missing it says so and offers Turn on location (the permission prompt, else the phone's location settings). Route from here keeps the two long-presses for a route from a placed start. A route with no path offers Try Crow, and Go comes first among the card's actions. Not yet (the route-to finding's open part): Go on a route that does not start at the fix follows it and alerts as T61 does, and a fresh fix far from a stale one does not replan (Route to here again does). Debug routes: `android-debug-routes.md` (Routes, Waypoints at any time); the release build by taps: `android-ui.py features` (`route-to`).

T122, the camera fits: a planned route and a trip opened in the editor are fitted between everything that floats across the top of the map (the search column, the online indicator, and at the right the track controls with an open list, the Routes chip and the navigation card: `MapInsets.topChromeBottomPx`) and the card at the bottom (the route card, or the trip card once it has been laid out, 250 ms after opening), 16 dp clear of each (`FitPadding`, `FitPaddingTest`); when the two leave less than 160 dp, the top gives way first. The fit's padding is dropped from the camera when it lands, for trips as for routes (T114). `GET /route` `ui.lastFit` and `ui.tripFit` carry `paddingPx`, `chromeBottomPx` and `clearOfChrome`.

## The navigation card (T61, T102, T122, T128)

While navigating, the card across the top of the map (`nav/NavOverlay.kt`) shows the next turn (arrow, distance, text), the next waypoint and the end, the off-route banner with Snooze and Quiet until back, the lost-fix line, and the camera actions and Stop. T122: it follows the system font scale up to 1.5 (`NAV_MAX_FONT_SCALE`; its type is large already, and at 2.0 the card with the banner covered the screen); the turn text steps down from 18 to 13 sp to fit and takes a third line before it is ever cut (T116's cued texts, "Head south on the service road, then turn right", ran past the two lines it had); the number lines and the banner's actions wrap whole. `GET /nav` `layout.navTurnText` has the turn text's `lines`, `cut` and `fontSp` as last laid out. Help icons on the header, the lost-fix line and the banner (Help pop-ups, above). T128: the header's icon is `HelpIcon(key, flat = true)`: the 48 dp touch target stays, laid out at the icon's own height and reaching past the row above and below, so the header is its text's height (`GET /nav` `layout.navHeaderDp`: 24 dp at 1.0, it was 48). The lost-fix line's icon stays a full-height target: two flat targets 4 dp apart would overlap, and the lower one would take taps on the upper icon. The scale bar stays below the card (`GET /scalebar` `clearOfNavCard`).

## The device tour (`android-check.py`)

`android-check.py` relaunches the app and clears the contour cache first, then per view sets the camera, waits for idle, screenshots, diffs `/stats` and reads `/features`; it fails a view on: style not loaded, not idle, tile server errors, an expected source (pack covers the view) serving no tiles, a blank screenshot, no contour lines rendered, or labels placed but not drawn (`/features/text`); and the tour when no glyphs were served for a font the style uses. Contour tiles over `--contour-budget-ms` (1000) are warnings, failures with `--strict` (timings swing with host load). It also reports the app's logcat warnings. Look at the contact sheet (`out/android-tour-sheet.png`). T98: the summary records the server the app reads and its state at the start and the end (`setup.online`, `online`, and an `online:` line on stderr): a debug build on an emulator defaults to `http://10.0.2.2:8765`, the host's live viewer, so a tour runs online when that server is up and with an unreachable server when it is not (`POST /settings?server=` for no server: the phone reads the sources); T105: `--server <url>|none` sets it before the relaunch (`setup.serverSet`), and the first view waits until the device's CPU use besides the app is at most `--quiet-cores` (1.0) in two 3 s windows in a row (`setup.quiet`; a just-booted emulator is busy for about two minutes, `android-emulator.md`). T110: the first view, the cold one, waits up to `--first-wait-ms` (60000) for idle and the others `--wait-ms` (30000); each view reports `idleSeconds` (how long `/screenshot` waited) and `deviceCpu` (`others` and `app`, the cores the device used besides the app and the app's own while the view ran), so a slow view shows whether the device was busy; T115: a view that did not go idle reports `notIdleBecause` (`pendingTiles`: a request still open at the loopback server, such as a stalled OpenFreeMap fetch, finding `../findings/2026-10-16-cold-view-gap-on-a-quiet-device.md`). A view whose contour tiles were sampled with no elevation over a DEM pack (`contourGeneration.noDemOverPack`; T106: only where the pack itself has data in the tile's window, so not off a coast inside the pack's box) gets a warning naming them.

## Loopback token and the debug port

**Loopback token** (T49, `LoopbackToken.kt`): any app on the device can open 127.0.0.1:8686, so every request, tiles and the style included, must carry the app's per-launch random token, as `?t=<token>` or an `X-Dystopo-Token: <token>` header; anything else gets 401 (`/health` `server.tokenRefused` counts them). The style MapLibre loads puts `t=` in every tile, glyph and shade URL. **Debug port** (T57): debug builds serve the debug routes on a second loopback server on a random port per launch and announce it, with the token, only in logcat: `I/Dystopo: debug server on port N token T` (other apps cannot read another app's logcat, so the token stays with the app's process). Port 8686 then answers like a release build: map routes with the token, 404 for every debug route, no `/health`. `android-emu.ps1`, `android-check.py` and `android-probe.py` read the line through `adb logcat` (helper `tools/android_debug.py`) and forward the host port to it, again after a relaunch; by hand: `adb -s <serial> logcat -d -s Dystopo:I`, then `adb -s <serial> forward tcp:8686 tcp:<N>` and `curl -H "X-Dystopo-Token: <T>" localhost:8686/stats`. The setting `POST /settings?debugFixedPort=1` (from the next launch) puts the debug routes back on 8686 with the T49 bootstrap, where `GET /health` without the token answers only `{"token": "..."}` to a loopback caller; the logcat line then names 8686. Release builds have no debug routes and no bootstrap, so there the token never leaves the process.
