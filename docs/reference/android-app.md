# The Android app: build, emulator scripts, device tour, loopback token

How the app serves the map and how agents drive it. Emulator setup and several emulators side by side: `android-emulator.md`. Every debug route: `android-debug-routes.md`.

## What it is and the scripts

`androidApp/` (Compose + MapLibre Native + `shared`) shows a region pack: hillshade from the DEM PMTiles (MapLibre `raster-dem`), OSM from the outdoors PMTiles, and **contour tiles generated on the device** (`shared/.../tiles/ContourTiles.kt`, cached on disk). MapLibre can't read PMTiles, so the app runs a loopback-only HTTP server (port 8686) serving `/dem`, `/osm`, `/contours`, `/glyphs` and `/style.json`; in debug builds the debug routes are on a second loopback server on a random port (T57, below) (the MapLibre style is translated from the devtool's `DefaultOsmStyle` by `shared/.../maplibre/MapLibreStyle.kt`). The module and `shared`'s android target exist only when an SDK is installed (`settings.gradle.kts` looks at `local.properties` / `ANDROID_HOME`), so SDK-less machines still build.
```
powershell -ExecutionPolicy Bypass -File tools\android-sdk.ps1     # SDK under %USERPROFILE%\Android\sdk + local.properties (no admin)
./gradlew :androidApp:assembleDebug
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build   # headless emulator, install, push out/rainier-*.pmtiles, launch, forward -Port to the debug server
powershell -ExecutionPolicy Bypass -File tools\android-push-pack.ps1 -Dem out\rainier-dem.pmtiles -Osm out\rainier-outdoors.pmtiles   # packs + glyphs only (-NoOsm: DEM only)
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd <avd> -EmuPort <n> -Port <p> -Forward   # after an app restart: re-read the debug port and token, re-forward
python -I tools/android-check.py --port 8686 --serial emulator-5554 --views-file tools/android-tour.txt   # device tour: JSON summary, out/android-tour-sheet.png; exit 1 on failure
```

T143: Diagnostics (`settings/DiagnosticsRow.kt`, `Diagnostics.kt`, on every build) shows the max heap, the heap used now, the peak since launch, the native heap, PSS, the phone's free memory and low flag, the heap guard's renders and trims and the last `onTrimMemory` level, read on a worker thread when the row opens and on Refresh, never polled; under "Last session", how the previous process ended (`ApplicationExitInfo`, Android 11 and up: the reason, RSS and PSS at the system's last sample) and the high-water mark it left (`settings/HeapMark.kt`: peak heap, native and PSS where read, last trim level; a preferences file written only when the peak rises 5 MB and at most every 10 s, plus at each `UI_HIDDEN`). T172: under "Recording now" or "Last track", the live or newest track's start (and end), activity, points with how many are less accurate than the limit and how many came from network location, its gaps by reason with their total length, and while it records the watchdog's GPS restarts; no name or position, in the report too. Routes: `/diagnostics` (`android-debug-routes.md`); release builds: `android-ui.py diagnostics`. A tap opens a group's page, "‹ Settings" or Back returns to the list, and closing forgets the page; on a window 720 dp wide or more (a tablet) the list and the open page sit side by side. A list rather than tabs, because six tab labels do not fit across a phone at font scale 2.0 while list rows wrap at any text size; every row's choices wrap too. Credits (the Map data and sources screen, `about/AboutActivity.kt`, and `GET /attribution`) are composed by `about/AppCredits.kt` from the open packs, what the server or the phone's own readers reported, and the registry ids of the data the app ships (`AppCredits.BUNDLED_SOURCE_IDS`; T141: `natural-earth` for the bundled country set and the Norway border mask), so Natural Earth is credited whenever the app runs, with no pack open (`usedBy` `bundled`, "Used by: built-in boundaries" on the screen); the on-map credit line is unchanged by it.

## Sun and shade (T188)

The phone half of T181's sun and shade (`options/SunShade.kt`, `SunPoint.kt`; the tiles and the point answer are `shared/.../tiles/ShadeTiles.kt`, `dem/Horizon.kt`, `nav/Sun.kt`). Settings › Map options › Shade: On and Off, off by default and off again at each launch (not a setting: the shade of one instant is a question asked now). Turned on, it picks today at the view's centre and opens the time at now while the sun is up there, else two hours before that day's flat sunset (solar noon in polar day or night): one behaviour, from the survey of 2026-10-30 (the overlay is off by default everywhere, with a time control and a pickable date; Google Earth opens at now). Under the chips: the date (`<` and `>` a day, a tap on it opens the system's date picker, Today when another day is shown; a date picks its opening instant by the same rule), the time with the phone's zone named (`<` and `>` a quarter hour) and a slider over the day from an hour before the flat sunrise to an hour after the sunset at the centre, in five-minute steps on an absolute grid (the ends' times under it); the map's shade follows when the slider is let go. The map draws `GET /shade/sun/{z}/{x}/{y}.png?m=<epoch minute>` as a `raster` layer added at run time under the contours (`SunShadeLayer`; the style itself is unchanged, so the shade off leaves the map as before), z10 to z14, each 256 px tile drawn over 512 px (a view takes a quarter of the tiles; at 256 MapLibre timed out the last of some 30) with no coarser tiles fetched ahead, stretched past z14 and none below map zoom 10 (a z9 tile took over a second on the emulator): a cool blue (`#1e3a6e`) at 40% where the terrain hides the sun, ridges up to 30 km toward the sun included, all of it at night (CalTopo's blue-shade convention, sunlit ground left clear). Tiles are cached in the contour LRU per instant and pack (`shade1-c1_sun<minute>_40-<dem id>/`). The long-press card has a line under its coordinates (`tracking/LongPressMenu.kt` `PointLines`, help `longPress.sun`): "Sun reaches here 7:46, leaves 17:54 PDT", with "hidden 12:31 to 13:12" between them for each stretch a peak blocks the sun, "No direct sun reaches here", or "Sun on this spot all day"; for today, or the date shown while the shade is on (then prefixed, "Mon 2 Nov: sun reaches here ..."); times 24-hour in the phone's zone with its short name (the place's own zone is a Later lookup). It reads "Sun: working out when it reaches here..." while T181's horizon sweep runs on its own thread, "Sun: no elevation data here" off every pack and server. No surveyed app gives this one line (CalTopo draws a year graph; photo apps use a flat horizon). Routes: `GET /shade` `sun`, `POST /shade/sun`, `GET /shade/sun/bench`, `GET /map/longpress` `sun` (`android-debug-routes.md`).

## Storage and the cache budget (T112)

Settings › Data and storage › Storage › (`storage/StorageScreen.kt`, `storage/Storage.kt`) shows what the app keeps on disk. At the top is the **cache budget** (`cachebudget/CacheBudget.kt`; ADR 0025 principle 3, ADR 0034): one total over three kinds, Online tiles (DEM, map and glyph tiles downloaded from a server or OpenFreeMap), Contours and shading (every contour, shade and cliff tile the phone made, from packs in `cache/contours/` or from downloaded DEM tiles in `cache/online/tiles/`) and Source data (the phone's own source downloads when no server is set), with presets Small 1 GB (the default), Medium 8 GB and Large 128 GB, and Custom: a size in GB, or 10, 25 or 50% of the free space turned into a fixed size once (never a live share). A stacked bar shows each kind's part; each kind's row shows its bytes, its share of the total and its floor (Online tiles 25%, Contours and shading 15%, Source data 5% of the total). When the kinds pass the total (checked after every tile write, every 30 s, and at once when the total is set) a run evicts contour and shade tiles first, then from the kind furthest above its floor, least recently used first and across both caches that hold a kind, never below a floor and never a tile in view (the visible box grown by half on every side) or within 300 m of the next 3 km of a navigated route, until 1% of the total (at least 4 MB) is free. Pinned offline areas (their own budget, `pinnedCacheMb`: chips from 128 MB to 128 GB, any size up to 1 TB through `POST /storage`, T115; it stopped at 8 GB before, below the Large preset, with a warning line when it is more than the free space, as for the total) and packs are outside it; Clear stays per row. T115: a help icon on the Cache budget heading and on each row, and the Data and storage line of the settings list names the total ("… storage with a 1 GB cache budget"). `onlineCacheMb` and `contourCacheMb` stay as each cache's ceiling; setting the total sets both to it. An install from before T112 starts at the small preset, or at its two caps together when they were raised past it. Routes: `GET /storage` (`budget`) and `POST /storage?budgetMb=` (`android-debug-routes.md`); the rule was measured with `devtool cache-replay` (`devtool-commands.md`).

## The area picker (T142, ADR 0041 §5)

The Offline areas sheet (`areas/AreasScreen.kt`) has two ways in, **Choose a country** and **Draw an area**; **Keep offline around here** is on the long-press card and under a chosen search result (`areas/AreaPicker.kt`). Each ends in the same size-first card over the map: the name (renamable; the area card's Rename after), "About 170 MB (1,300 tiles) at full detail", the other details as choices (T157, ADR 0047: three details, full z8 to z15, medium elevation to z13 with vector to z14, less z8 to z13; the two not shown as links, "Medium detail (about 24 MB)", "Less detail (about 23 MB)", "Full detail (about 64 MB)", always offered; at medium "Every path and place of full detail; the terrain shading and contours are coarser" under the size line, which says "at medium detail"), the time line, and the refusal past the budget with no Download. T152 (ADR 0045): an area's tiles are rows, so no area is too large for the heap: a country at full detail shows its size ("About 174 GB (1,437,049 tiles) at full detail" for France; T170: whole gigabytes from 100 GB, and the budget sentence's budget in the same units, "11.5 TB; 1.6 GB of your 1 TB offline budget"; sizes from 1 TB read "11.5 TB") and Download proceeds once the budget admits it; the download walks the manifest row by row (zoom, route, row) with at most 24 tiles queued. The plan is the phone's own manifest, made on a worker thread as the shape changes; Download asks the server once (T140). The country list (`areas/CountryList.kt`) groups T141's bundled countries by continent, then alphabetical, with a filter box over `Countries.find`; each row is the `NAME`, T157: the three details' sizes ("Less 1.1 GB · Medium 1.2 GB · Full 13.3 GB"; measured on the phone over the manifest's cover, each zoom's cover filled once for the three, the rows on screen first; the full size estimated from z14's cover, a few percent high, when its floor is past the budget; T170: each country's cover counts per zoom and its three area ids are kept in `files/areas/country-covers.txt` for the bundled set they came from (`CoverCounts`), so only the first open fills the covers, about 34 s of CPU on the emulator, and later opens, in any process, add up stored counts in 0.25 s; the list redraws at most every 150 ms as sizes arrive) and a DOWNLOADED mark, and opens at the deepest detail that fits the budget; a row over the budget is greyed with the budget sentence, Antarctica (no area can hold it) with "Too large to download whole at this detail; draw an area instead"; T152: the heap greys no row, and a country's sizes are measured row by row in well under a second. A country is its rings with T141's tolerance as `bufferM`. The drawing (`areas/AreaDraw.kt`) starts as four vertices from the view; a tap on the map adds a vertex to the edge it lengthens least (not the first tap of a double tap), a vertex or a midpoint handle drags, a long press on a vertex removes it (three stay), Undo steps back; touches reach it through the map view's one touch listener (`TripOverlay`'s asks it first). Around a point: 2, 5, 10, 20 km or 1, 3, 5, 10 mi by the units setting, a typed value up to 20 km, the circle drawn live. Routes: `GET /areas/countries`, `POST /areas/country`, `POST|GET /areas/draw`, `POST /areas/draw/touch`, `POST /areas/around`, `POST /areas/picker[/download|/close]` (`android-debug-routes.md`).

"Download this region" (T153; the online indicator's button, `online/OnlineOverlay.kt`) opens the same card for the visible box, titled "Download this region": the view's rectangle drawn and fitted above the card, a generated name (`view-<date>-<n>`), no span cap, and the detail chosen for the view: full detail from a z10 view, T170: medium detail from a z8 view, less detail below (a z6 state view), the others as the links. At full detail a box within the server's build limits (`RegionDownload.packFits`: 3 degrees a side and 20,000 tiles at z8 to z14, the server's `DYSTOPO_BUILD_MAX_SPAN_DEG` and `DYSTOPO_BUILD_MAX_TILES`) keeps the pack path (the server's build, or the phone's own with no server, then the pack with its trail graph and search; sized at z8 to z14 and outside the pinned budget, so never refused by it), with the line "With routing and place search (a map pack)"; any wider box takes the area path (a rectangle polygon through the area download, T151's cursor and T156's chain) with "Tiles only: routing needs a smaller box", and less (T157: and medium) detail always takes it, with "Tiles only: routing needs full detail". A typed name that is not a pack name becomes one for the pack path ("Mount Rainier 2" to `Mount-Rainier-2`). The button is hidden while the card is up; the pack path's progress is the indicator's line as before, the area path's the sheet's. Route: `POST /areas/region` (`android-debug-routes.md`); `POST /online/download` still starts the pack path directly.

Interrupted area downloads (T151, `areas/ResumeCheck.kt`): the record keeps a cursor, the last row of the download's walk before which every row is whole, with the tiles that failed in those rows; it is saved every 2 s while rows complete and when the run ends. A start of an unfinished or cancelled area (the resume check, Retry, Download again on a cancelled one) walks those failed tiles, then the rows after the cursor, so its cost follows what is left; when the source's versions moved on since, the whole walk runs again. At start a record left "downloading" by an ended process becomes partial (Retry shows at once) or cancelled when the user had cancelled it. A cheap check over the records already read from `files/areas/areas.json` (never the tile cache; about 0.1 ms) starts the oldest unfinished area at app start, when the app comes to the foreground, after a download ends and when a backoff is over; triggers that arrive while a check is queued make one check, and one area download runs at a time. A start first lets the fetcher try the network at once (its own backoff after a lost connection would fail every tile). A walk stops as stalled after 48 tiles in a row could not be fetched ("The download paused: the network stopped answering."); the card says "Continues by itself" (with the minutes during a backoff). Not against the user: a cancel is kept in the record at once and never resumed; a budget refusal stops the resumes until the budget changes; runs that end partial back off 30 s, 2, 10 and 30 min, then every 2 h, and five in a row that fetched nothing (a stall is not counted) stop the resumes with "The download kept failing, so it stopped trying; press Retry to try again." No setting: the owner's requirement is resume without a toggle. The sheet's coverage (polled every 1.5 s) and Remove work row by row: the tile cache's keys are kept as rows (`TileCache.onIndex`), so a France record's coverage takes about 50 ms and its removal 0.1 s, against 45 s and 123 s per tile before. T170: a finished country's removal is the index pass and one unlink per tile, about 0.05 ms each on the emulator (2,000 in 105 ms), so Liechtenstein at less detail (254 tiles) goes in about 50 ms; deleting in parallel batches measured no faster and was not kept. A download started with contours (`contours=1`) records it, so its resume, Retry and Download again make them too. The area card's zooms say a medium area's cap ("z8-14, elevation to z13"), and its pins hold no elevation tile past the cap (`AreaPins`' `demTops`): DEM tiles browsed at z14 or deeper inside a medium area stay evictable, the vector and the contours made on the phone keep the area's zooms. Since T156 the in-process triggers start a download in the background only while the process has the network (below).

Area downloads in the background (T156, ADR 0046, `areas/DownloadWorker.kt`): one WorkManager unique one-time work, `area-download`, with a `CONNECTED` constraint (never unmetered, ADR 0023) keeps a download going when the app is in the background or its process is gone; it runs T151's check and cursor and adds no resume logic. Every start hands the download over (a tap, Retry or a trip's corridor replaces the work, so a fresh worker runs now; any other start keeps it), and a check that finds a record that may resume and starts nothing keeps the work enqueued at the backoff's end. A run watches the running download or runs the check (trigger `worker`, which skips the backoff's wait) and appends the next step at the record's backoff while one may resume. It asks for the foreground (type `dataSync`) with the notification "Downloading <name>", "N of M tiles", a progress bar and Cancel (channel "Area downloads"); started in the background the request is refused (`ForegroundServiceStartNotAllowedException` on API 35) and the run goes on as a plain job of about ten minutes. A stop by the system with the app in the background (the network, the job's time, Android 15's six hours a day of `dataSync`) pauses the walk ("The download paused in the background.", cursor saved, no failure counted) and WorkManager runs the work again. In the background a cached app has no network outside a job (`dumpsys netpolicy`: `blocked=APP_BACKGROUND`), and WorkManager runs a due step in a living process before JobScheduler's job starts, so a worker waits for the network (5 s polls, up to 9 min) and the in-process triggers start a download there only while the network is usable. The chain survives a reboot (WorkManager's boot receiver reschedules it; the worker resumed without the app being opened) and a cached process's death; a user's force-stop cancels it until the next launch, whose start trigger enqueues it again. `POST_NOTIFICATIONS` is asked at the first Download in the area picker (`tracking/NotificationPrompt.kt`, once for recording and downloads). Tests on a device: `adb shell cmd connectivity airplane-mode enable|disable`; `am kill <pkg>` after HOME once the worker stopped; `cmd jobscheduler run -f -n androidx.work.systemjobscheduler <pkg> <id>` (WorkManager 2.10 schedules in that namespace; the id from `dumpsys jobscheduler`); `device_config put activity_manager data_sync_fgs_timeout_duration 30000` shortens the `dataSync` timeout (`device_config delete` restores it); the notification shade: `cmd statusbar expand-notifications`, then `screencap`. A process frozen in the background answers no debug route: read `logcat -s DystopoResume DystopoAreas` then.

## Help pop-ups (T109)

A question mark beside a control opens a short help text about it (`androidApp/.../help/`). `HelpIcon(key)` draws the icon: 24 dp at font scale 1.0, sized in sp so it grows with the font scale as the row's label does, inside a touch target of at least 48 dp (the icon plus 20 dp; T128: `flat = true` lays the target out at the icon's height, overflowing its row, for a short row such as the navigation card's header); its accessibility label is "Help: <title>" and the question mark is not text, so scripts that find a row by its label never meet it. A tap opens the pop-up (`HelpHost`, drawn after the other overlays: since T115 the last line of `MainActivity`'s map screen, so it is over every screen, the Share screen and its scanner included): a faint scrim, and a card with the title, the text and OK, below the icon when it fits there, else above it, with a caret pointing at the icon; T122: when the text fits on neither side (large font scales) the card goes on the larger side with its text a step smaller at a time, down to three quarters of the font scale (never below 1.0), and scrolls only past that (`PopupPlace`, `PopupPlaceTest`); it never covers its icon (at 2.0 it covered three: Sources, Offline areas, Cache budget). An icon laid out outside the window (a row still scrolling into view) counts as none, and a pop-up whose icon leaves and comes back within 300 ms stays open. A tap anywhere or Back closes it. The texts are declared in the file of the control that shows them, as a `HelpText(key, title, placed, needs, show)` in that file's list (`MAP_OPTIONS_HELP`, `SETTINGS_HELP`, `DIRECT_SOURCES_HELP`, `AREAS_HELP`, `TRACK_BAR_HELP`, `LONG_PRESS_HELP`, T115 `STORAGE_HELP`, T122 `NAV_HELP`), which `HelpRegistry` gathers; `HelpRegistryTest` reads the sources and fails on a key a screen names without a text, a text no screen shows, or a text declared in another file than its icon. Texts are one short paragraph (at most 330 characters, so they fit beside the icon at font scale 1.0 and on the screen at 2.0), name no other mapping software (the test and `tools/user-text-check.py`), and put a distance through `UnitFormat` in the units setting (the corridor's 500 m reads "0.3 mi" in feet). Placed on every Map options row and the slope legend, the Offline areas sheet (its title: pinned areas and the budget; the line under it: corridors), Settings › Sources (the server), its Mobile data and Limit per session rows, Units, Text size, Route snap, the two navigation thresholds, Sync status, Share and Contour warm-up, the unfolded track bar, the long-press card, (T115) the Storage screen's Cache budget heading and each of its rows, and (T122) the navigation card: its header (`nav.card`), the "No GPS fix" line (`nav.fixLost`) and the off-route banner (`nav.offRoute`), each needing a navigation session in that state (`POST /help/open` cannot start one: 409 otherwise). A text's placement (`GET /help` `placed`) reads as messages name screens, "Settings › Map options › Hillshade": T115 made the settings groups sections in `firstrun/Screens.kt`, and `HelpRegistryTest` checks every placement against it as `ScreenNamesTest` checks messages. Debug routes: `GET /help`, `POST /help/open?key=`, `POST /help/close`, which since T115 also closes what `/help/open` brought up for the icon (`android-debug-routes.md`).

## Route to here (T114)

A long-press on the map opens a card whose first action is Route to here: a route from the phone's position to the pressed point, planned at once in the route card's mode (`routing/RouteSession.kt`; the conventions it follows are the finding `../findings/2026-10-17-route-to-flows-in-other-apps.md`). The position is the newer of the recorder's last fix and the map's device fix, the Waypoint chip's "here" (`routing/RouteOrigin.kt`). The route card names both ends: "From: Your location" (with the fix's age when it was older than 120 s: "Your location, 14 min ago") and "To:" the point's coordinates; Change on the From line offers Your location, Choose on map (the next long-press is the start) and Swap. ## The UI thread and the watchdog (T144)

The rule: the UI thread never takes a lock and never does disk or network I/O; it reads snapshots that workers publish. The online indicator (`online/OnlineOverlay.kt`) shows an `OnlineUi` snapshot made each second on a worker (the camera is read on the UI thread, the view's source, the server state and "Download this region"'s record off it); the credit line's pack attributions are read off it too. `DystopoApp.reload` (a pack activated, downloaded, imported, updated or deleted, a setting that changes the tiles) opens the new tile service off the UI thread, publishes it through a volatile field and posts the style swap; the old service is reference counted (`RefCounted`, `Leases` in `TileService.kt`): every loopback request holds the service it started with (`LocalServer` takes the lease around the handler and releases it on every exit), the contour warm-up holds one while it runs, and the last holder closes the old packs. `PackManager.jumpTo` posts the camera move. **The watchdog** (`MainWatchdog.kt`, every build, release included; no setting): a worker posts a heartbeat to the UI thread every second; one unanswered for 3 s writes one dump per freeze to `files/reports/freeze-<UTC time>.txt` (the newest five kept; the format, `dystopo-report 1`, is the KDoc of `MainWatchdog`, which T145's report screen reads), naming the topmost app frame of the main stack most often seen in samples taken every 200 ms from the first silent second. It ticks only between the activity's `onResume` and `onPause`, from the first drawn frame after the process started (a cold start's first frame took 10 s on a just-booted emulator), never with a debugger attached, and rearms when a heartbeat returns. Debug routes: `android-debug-routes.md`.

## The app in the background (T150)

Nothing of the map's own runs while the app is stopped. `Foreground.kt` is one flag for the process, on while a `MainActivity` is started (counted at `onStart` and `onStop`); every Compose polling loop waits with `Foreground.delay` (one more pass at most after `onStop`, then paused until the next start), the country list's size worker and the ahead-on-the-route poll wait with `Foreground.block` (the poll goes on in the background only while a navigation runs). One flag rather than `repeatOnLifecycle(STARTED)` per effect: the thread loops have no lifecycle owner and a paused loop keeps its state. The map's device-location listener (`MapController.setForeground`) is removed at `onStop` and registered again at `onStart`, so the puck and follow mode resume on the next fix; track recording (its foreground service, its fixes on a thread of their own since T159, `android-tracks-and-sync.md`) and navigation (`NavSession`'s own GPS listener) keep their fixes, and the heading sensor was already released at `onStop` (T100). `MainActivity` is `singleTask`: a task started by a link, a notification or `am start -n` stacked another activity and map at each launcher tap (six after five taps); links that arrive while it lives reach `onNewIntent` (`DeepLink.install`, `ShareLink`). ## Loopback token and the debug port

**Loopback token** (T49, `LoopbackToken.kt`): any app on the device can open 127.0.0.1:8686, so every request, tiles and the style included, must carry the app's per-launch random token, as `?t=<token>` or an `X-Dystopo-Token: <token>` header; anything else gets 401 (`/health` `server.tokenRefused` counts them). The style MapLibre loads puts `t=` in every tile, glyph and shade URL. **Debug port** (T57): debug builds serve the debug routes on a second loopback server on a random port per launch and announce it, with the token, only in logcat: `I/Dystopo: debug server on port N token T` (other apps cannot read another app's logcat, so the token stays with the app's process). Port 8686 then answers like a release build: map routes with the token, 404 for every debug route, no `/health`. `android-emu.ps1`, `android-check.py` and `android-probe.py` read the line through `adb logcat` (helper `tools/android_debug.py`) and forward the host port to it, again after a relaunch; by hand: `adb -s <serial> logcat -d -s Dystopo:I`, then `adb -s <serial> forward tcp:8686 tcp:<N>` and `curl -H "X-Dystopo-Token: <T>" localhost:8686/stats`. The setting `POST /settings?debugFixedPort=1` (from the next launch) puts the debug routes back on 8686 with the T49 bootstrap, where `GET /health` without the token answers only `{"token": "..."}` to a loopback caller; the logcat line then names 8686. Release builds have no debug routes and no bootstrap, so there the token never leaves the process.
