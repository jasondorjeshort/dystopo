# The Android app: build, emulator scripts, device tour, loopback token

How the app serves the map and how agents drive it. Emulator setup and several emulators side by side: `android-emulator.md`. Every debug route: `android-debug-routes.md`.

## What it is and the scripts

`androidApp/` (Compose + MapLibre Native + `shared`) shows a region pack: hillshade from the DEM PMTiles (MapLibre `raster-dem`), OSM from the outdoors PMTiles, and **contour tiles generated on the device** (`shared/.../tiles/ContourTiles.kt`, cached on disk). MapLibre can't read PMTiles, so the app runs a loopback-only HTTP server (port 8686) serving `/dem`, `/osm`, `/contours`, `/glyphs` and `/style.json`; in debug builds the debug routes are on a second loopback server on a random port (T57, below) (the MapLibre style is translated from the devtool's `DefaultOsmStyle` by `shared/.../maplibre/MapLibreStyle.kt`). The module and `shared`'s android target exist only when an SDK is installed (`settings.gradle.kts` looks at `local.properties` / `ANDROID_HOME`), so SDK-less machines still build.
```
powershell -ExecutionPolicy Bypass -File tools\android-sdk.ps1     # SDK under %USERPROFILE%\Android\sdk + local.properties (no admin)
./gradlew :androidApp:assembleDebug
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build   # headless emulator, install, push out/rainier-*.pmtiles, launch, forward -Port to the debug server
powershell -ExecutionPolicy Bypass -File tools\android-push-pack.ps1 -Dem out\rainier-dem.pmtiles -Osm out\rainier-outdoors.pmtiles   # packs + glyphs only (-NoOsm: DEM only)
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd <avd> -EmuPort <n> -Port <p> -Forward   # after an app restart: re-read the debug port and token, re-forward
python -I tools/android-check.py --port 8686 --serial emulator-5554 --views-file tools/android-tour.txt   # device tour: JSON summary, out/android-tour-sheet.png; exit 1 on failure
```

## Settings

The Settings chip opens the settings sheet (`SettingsSheet.kt`, rows in `settings/`) on a list of groups (T103): Data and storage (Sources with the server field first, Storage ›, Offline areas ›), Map options (`options/MapOptionsSection.kt` placed whole, Night and the scale bar included), Units and display (Units, Text size), Navigation and tracking (Route snap, Spoken directions on or off (T126), and the two navigation thresholds), Sync and sharing (Sync status ›, Share ›), About and advanced (Updates, Diagnostics, Report a problem (T145, below), Contour warm-up, Credits: the Map data and sources screen). T143: Diagnostics (`settings/DiagnosticsRow.kt`, `Diagnostics.kt`, on every build) shows the max heap, the heap used now, the peak since launch, the native heap, PSS, the phone's free memory and low flag, the heap guard's renders and trims and the last `onTrimMemory` level, read on a worker thread when the row opens and on Refresh, never polled; under "Last session", how the previous process ended (`ApplicationExitInfo`, Android 11 and up: the reason, RSS and PSS at the system's last sample) and the high-water mark it left (`settings/HeapMark.kt`: peak heap, native and PSS where read, last trim level; a preferences file written only when the peak rises 5 MB and at most every 10 s, plus at each `UI_HIDDEN`). Copy report puts the same lines with the app version, build type, Android version, device model, `memoryClass`, `largeMemoryClass` and the large-heap flag on the clipboard as plain text, through the report scrubber (`shared/.../reports/Scrub.kt`: coordinates, keyed lat/lon values, boxes, tile paths, query strings, storage paths, pack, area and search names become placeholders); a toast only below Android 13. Routes: `/diagnostics` (`android-debug-routes.md`); release builds: `android-ui.py diagnostics`. A tap opens a group's page, "‹ Settings" or Back returns to the list, and closing forgets the page; on a window 720 dp wide or more (a tablet) the list and the open page sit side by side. A list rather than tabs, because six tab labels do not fit across a phone at font scale 2.0 while list rows wrap at any text size; every row's choices wrap too. The server field stays two taps from the map (Settings, Data and storage), and the first-run card's Settings link, the pack list's "No server set" line and Download without a server open Data and storage directly. `settings/SettingsLayout.kt` is the order of groups and rows that the pages draw and `GET /settings/layout` returns (`SettingsLayoutTest` compares it with the rows of the old single sheet); `POST /settings/open?group=` opens a page in debug builds (`android-debug-routes.md`). Release builds are driven by text: `open_settings(dev, group, anchor)` in `tools/android-ui.py` taps Settings, then the group, until its page shows the anchor text.

Credits (the Map data and sources screen, `about/AboutActivity.kt`, and `GET /attribution`) are composed by `about/AppCredits.kt` from the open packs, what the server or the phone's own readers reported, and the registry ids of the data the app ships (`AppCredits.BUNDLED_SOURCE_IDS`; T141: `natural-earth` for the bundled country set and the Norway border mask), so Natural Earth is credited whenever the app runs, with no pack open (`usedBy` `bundled`, "Used by: built-in boundaries" on the screen); the on-map credit line is unchanged by it.

## Storage and the cache budget (T112)

Settings › Data and storage › Storage › (`storage/StorageScreen.kt`, `storage/Storage.kt`) shows what the app keeps on disk. At the top is the **cache budget** (`cachebudget/CacheBudget.kt`; ADR 0025 principle 3, ADR 0034): one total over three kinds, Online tiles (DEM, map and glyph tiles downloaded from a server or OpenFreeMap), Contours and shading (every contour, shade and cliff tile the phone made, from packs in `cache/contours/` or from downloaded DEM tiles in `cache/online/tiles/`) and Source data (the phone's own source downloads when no server is set), with presets Small 1 GB (the default), Medium 8 GB and Large 128 GB, and Custom: a size in GB, or 10, 25 or 50% of the free space turned into a fixed size once (never a live share). A stacked bar shows each kind's part; each kind's row shows its bytes, its share of the total and its floor (Online tiles 25%, Contours and shading 15%, Source data 5% of the total). When the kinds pass the total (checked after every tile write, every 30 s, and at once when the total is set) a run evicts contour and shade tiles first, then from the kind furthest above its floor, least recently used first and across both caches that hold a kind, never below a floor and never a tile in view (the visible box grown by half on every side) or within 300 m of the next 3 km of a navigated route, until 1% of the total (at least 4 MB) is free. Pinned offline areas (their own budget, `pinnedCacheMb`: chips from 128 MB to 128 GB, any size up to 1 TB through `POST /storage`, T115; it stopped at 8 GB before, below the Large preset, with a warning line when it is more than the free space, as for the total) and packs are outside it; Clear stays per row. T115: a help icon on the Cache budget heading and on each row, and the Data and storage line of the settings list names the total ("… storage with a 1 GB cache budget"). `onlineCacheMb` and `contourCacheMb` stay as each cache's ceiling; setting the total sets both to it. An install from before T112 starts at the small preset, or at its two caps together when they were raised past it. Routes: `GET /storage` (`budget`) and `POST /storage?budgetMb=` (`android-debug-routes.md`); the rule was measured with `devtool cache-replay` (`devtool-commands.md`).

Open it with its map pack on this phone to add them."; a crow trip shows its bearing instead ("Bearing 18° (north)", one per leg with via points). Routes: `GET /routes/{id}` `directions`, `POST /routes/{id}/directions?open=1|0` and `?save=1` (the KDoc of `trips/TripRoutes.kt`).

## The area picker (T142, ADR 0041 §5)

The Offline areas sheet (`areas/AreasScreen.kt`) has two ways in, **Choose a country** and **Draw an area**; **Keep offline around here** is on the long-press card and under a chosen search result (`areas/AreaPicker.kt`). Each ends in the same size-first card over the map: the name (renamable; the area card's Rename after), "About 170 MB (1,300 tiles) at full detail", the other details as choices (T157, ADR 0047: three details, full z8 to z15, medium elevation to z13 with vector to z14, less z8 to z13; the two not shown as links, "Medium detail (about 24 MB)", "Less detail (about 23 MB)", "Full detail (about 64 MB)", always offered; at medium "Every path and place of full detail; the terrain shading and contours are coarser" under the size line, which says "at medium detail"), the time line, and the refusal past the budget with no Download. T152 (ADR 0045): an area's tiles are rows, so no area is too large for the heap: a country at full detail shows its size ("About 173.8 GB (1,437,049 tiles) at full detail" for France; sizes from 1 TB read "11.5 TB") and Download proceeds once the budget admits it; the download walks the manifest row by row (zoom, route, row) with at most 24 tiles queued. The plan is the phone's own manifest, made on a worker thread as the shape changes; Download asks the server once (T140). The country list (`areas/CountryList.kt`) groups T141's bundled countries by continent, then alphabetical, with a filter box over `Countries.find`; each row is the `NAME`, T157: the three details' sizes ("Less 1.1 GB · Medium 1.2 GB · Full 13.3 GB"; measured on the phone over the manifest's cover, each zoom's cover filled once for the three, the rows on screen first; the full size estimated from z14's cover, a few percent high, when its floor is past the budget) and a DOWNLOADED mark, and opens at the deepest detail that fits the budget; a row over the budget is greyed with the budget sentence, Antarctica (no area can hold it) with "Too large to download whole at this detail; draw an area instead"; T152: the heap greys no row, and a country's sizes are measured row by row in well under a second. A country is its rings with T141's tolerance as `bufferM`. The drawing (`areas/AreaDraw.kt`) starts as four vertices from the view; a tap on the map adds a vertex to the edge it lengthens least (not the first tap of a double tap), a vertex or a midpoint handle drags, a long press on a vertex removes it (three stay), Undo steps back; touches reach it through the map view's one touch listener (`TripOverlay`'s asks it first). Around a point: 2, 5, 10, 20 km or 1, 3, 5, 10 mi by the units setting, a typed value up to 20 km, the circle drawn live. Routes: `GET /areas/countries`, `POST /areas/country`, `POST|GET /areas/draw`, `POST /areas/draw/touch`, `POST /areas/around`, `POST /areas/picker[/download|/close]` (`android-debug-routes.md`).

"Download this region" (T153; the online indicator's button, `online/OnlineOverlay.kt`) opens the same card for the visible box, titled "Download this region": the view's rectangle drawn and fitted above the card, a generated name (`view-<date>-<n>`), no span cap, and the detail chosen for the view: full detail from a z10 view, less detail below (a z6 state view), the other as the link. At full detail a box within the server's build limits (`RegionDownload.packFits`: 3 degrees a side and 20,000 tiles at z8 to z14, the server's `DYSTOPO_BUILD_MAX_SPAN_DEG` and `DYSTOPO_BUILD_MAX_TILES`) keeps the pack path (the server's build, or the phone's own with no server, then the pack with its trail graph and search; sized at z8 to z14 and outside the pinned budget, so never refused by it), with the line "With routing and place search (a map pack)"; any wider box takes the area path (a rectangle polygon through the area download, T151's cursor and T156's chain) with "Tiles only: routing needs a smaller box", and less (T157: and medium) detail always takes it, with "Tiles only: routing needs full detail". A typed name that is not a pack name becomes one for the pack path ("Mount Rainier 2" to `Mount-Rainier-2`). The button is hidden while the card is up; the pack path's progress is the indicator's line as before, the area path's the sheet's. Route: `POST /areas/region` (`android-debug-routes.md`); `POST /online/download` still starts the pack path directly.

Interrupted area downloads (T151, `areas/ResumeCheck.kt`): the record keeps a cursor, the last row of the download's walk before which every row is whole, with the tiles that failed in those rows; it is saved every 2 s while rows complete and when the run ends. A start of an unfinished or cancelled area (the resume check, Retry, Download again on a cancelled one) walks those failed tiles, then the rows after the cursor, so its cost follows what is left; when the source's versions moved on since, the whole walk runs again. At start a record left "downloading" by an ended process becomes partial (Retry shows at once) or cancelled when the user had cancelled it. A cheap check over the records already read from `files/areas/areas.json` (never the tile cache; about 0.1 ms) starts the oldest unfinished area at app start, when the app comes to the foreground, after a download ends and when a backoff is over; triggers that arrive while a check is queued make one check, and one area download runs at a time. A start first lets the fetcher try the network at once (its own backoff after a lost connection would fail every tile). A walk stops as stalled after 48 tiles in a row could not be fetched ("The download paused: the network stopped answering."); the card says "Continues by itself" (with the minutes during a backoff). Not against the user: a cancel is kept in the record at once and never resumed; a budget refusal stops the resumes until the budget changes; runs that end partial back off 30 s, 2, 10 and 30 min, then every 2 h, and five in a row that fetched nothing (a stall is not counted) stop the resumes with "The download kept failing, so it stopped trying; press Retry to try again." No setting: the owner's requirement is resume without a toggle. The sheet's coverage (polled every 1.5 s) and Remove work row by row: the tile cache's keys are kept as rows (`TileCache.onIndex`), so a France record's coverage takes about 50 ms and its removal 0.1 s, against 45 s and 123 s per tile before. Since T156 the in-process triggers start a download in the background only while the process has the network (below).

Area downloads in the background (T156, ADR 0046, `areas/DownloadWorker.kt`): one WorkManager unique one-time work, `area-download`, with a `CONNECTED` constraint (never unmetered, ADR 0023) keeps a download going when the app is in the background or its process is gone; it runs T151's check and cursor and adds no resume logic. Every start hands the download over (a tap, Retry or a trip's corridor replaces the work, so a fresh worker runs now; any other start keeps it), and a check that finds a record that may resume and starts nothing keeps the work enqueued at the backoff's end. A run watches the running download or runs the check (trigger `worker`, which skips the backoff's wait) and appends the next step at the record's backoff while one may resume. It asks for the foreground (type `dataSync`) with the notification "Downloading <name>", "N of M tiles", a progress bar and Cancel (channel "Area downloads"); started in the background the request is refused (`ForegroundServiceStartNotAllowedException` on API 35) and the run goes on as a plain job of about ten minutes. A stop by the system with the app in the background (the network, the job's time, Android 15's six hours a day of `dataSync`) pauses the walk ("The download paused in the background.", cursor saved, no failure counted) and WorkManager runs the work again. In the background a cached app has no network outside a job (`dumpsys netpolicy`: `blocked=APP_BACKGROUND`), and WorkManager runs a due step in a living process before JobScheduler's job starts, so a worker waits for the network (5 s polls, up to 9 min) and the in-process triggers start a download there only while the network is usable. The chain survives a reboot (WorkManager's boot receiver reschedules it; the worker resumed without the app being opened) and a cached process's death; a user's force-stop cancels it until the next launch, whose start trigger enqueues it again. `POST_NOTIFICATIONS` is asked at the first Download in the area picker (`tracking/NotificationPrompt.kt`, once for recording and downloads). Tests on a device: `adb shell cmd connectivity airplane-mode enable|disable`; `am kill <pkg>` after HOME once the worker stopped; `cmd jobscheduler run -f -n androidx.work.systemjobscheduler <pkg> <id>` (WorkManager 2.10 schedules in that namespace; the id from `dumpsys jobscheduler`); `device_config put activity_manager data_sync_fgs_timeout_duration 30000` shortens the `dataSync` timeout (`device_config delete` restores it); the notification shade: `cmd statusbar expand-notifications`, then `screencap`. A process frozen in the background answers no debug route: read `logcat -s DystopoResume DystopoAreas` then.

## Help pop-ups (T109)

A question mark beside a control opens a short help text about it (`androidApp/.../help/`). `HelpIcon(key)` draws the icon: 24 dp at font scale 1.0, sized in sp so it grows with the font scale as the row's label does, inside a touch target of at least 48 dp (the icon plus 20 dp; T128: `flat = true` lays the target out at the icon's height, overflowing its row, for a short row such as the navigation card's header); its accessibility label is "Help: <title>" and the question mark is not text, so scripts that find a row by its label never meet it. A tap opens the pop-up (`HelpHost`, drawn after the other overlays: since T115 the last line of `MainActivity`'s map screen, so it is over every screen, the Share screen and its scanner included): a faint scrim, and a card with the title, the text and OK, below the icon when it fits there, else above it, with a caret pointing at the icon; T122: when the text fits on neither side (large font scales) the card goes on the larger side with its text a step smaller at a time, down to three quarters of the font scale (never below 1.0), and scrolls only past that (`PopupPlace`, `PopupPlaceTest`); it never covers its icon (at 2.0 it covered three: Sources, Offline areas, Cache budget). An icon laid out outside the window (a row still scrolling into view) counts as none, and a pop-up whose icon leaves and comes back within 300 ms stays open. A tap anywhere or Back closes it. The texts are declared in the file of the control that shows them, as a `HelpText(key, title, placed, needs, show)` in that file's list (`MAP_OPTIONS_HELP`, `SETTINGS_HELP`, `DIRECT_SOURCES_HELP`, `AREAS_HELP`, `TRACK_BAR_HELP`, `LONG_PRESS_HELP`, T115 `STORAGE_HELP`, T122 `NAV_HELP`), which `HelpRegistry` gathers; `HelpRegistryTest` reads the sources and fails on a key a screen names without a text, a text no screen shows, or a text declared in another file than its icon. Texts are one short paragraph (at most 330 characters, so they fit beside the icon at font scale 1.0 and on the screen at 2.0), name no other mapping software (the test and `tools/user-text-check.py`), and put a distance through `UnitFormat` in the units setting (the corridor's 500 m reads "0.3 mi" in feet). Placed on every Map options row and the slope legend, the Offline areas sheet (its title: pinned areas and the budget; the line under it: corridors), Settings › Sources (the server), its Mobile data and Limit per session rows, Units, Text size, Route snap, the two navigation thresholds, Sync status, Share and Contour warm-up, the unfolded track bar, the long-press card, (T115) the Storage screen's Cache budget heading and each of its rows, and (T122) the navigation card: its header (`nav.card`), the "No GPS fix" line (`nav.fixLost`) and the off-route banner (`nav.offRoute`), each needing a navigation session in that state (`POST /help/open` cannot start one: 409 otherwise). A text's placement (`GET /help` `placed`) reads as messages name screens, "Settings › Map options › Hillshade": T115 made the settings groups sections in `firstrun/Screens.kt`, and `HelpRegistryTest` checks every placement against it as `ScreenNamesTest` checks messages. Debug routes: `GET /help`, `POST /help/open?key=`, `POST /help/close`, which since T115 also closes what `/help/open` brought up for the icon (`android-debug-routes.md`).

## Route to here (T114)

A long-press on the map opens a card whose first action is Route to here: a route from the phone's position to the pressed point, planned at once in the route card's mode (`routing/RouteSession.kt`; the conventions it follows are the finding `../findings/2026-10-17-route-to-flows-in-other-apps.md`). The position is the newer of the recorder's last fix and the map's device fix, the Waypoint chip's "here" (`routing/RouteOrigin.kt`). The route card names both ends: "From: Your location" (with the fix's age when it was older than 120 s: "Your location, 14 min ago") and "To:" the point's coordinates; Change on the From line offers Your location, Choose on map (the next long-press is the start) and Swap. Not yet (the route-to finding's open part): Go on a route that does not start at the fix follows it and alerts as T61 does, and a fresh fix far from a stale one does not replan (Route to here again does). Debug routes: `android-debug-routes.md` (Routes, Waypoints at any time); the release build by taps: `android-ui.py features` (`route-to`).

T122, the camera fits: a planned route and a trip opened in the editor are fitted between everything that floats across the top of the map (the search column, the online indicator, and at the right the track controls with an open list, the Routes chip and the navigation card: `MapInsets.topChromeBottomPx`) and the card at the bottom (the route card, or the trip card once it has been laid out, 250 ms after opening), 16 dp clear of each (`FitPadding`, `FitPaddingTest`); when the two leave less than 160 dp, the top gives way first. ## The open view (T162)

The map opens at the newest of three views (the owner's rule, 2026-10-28; `OpenView` in `MapViewport.kt`, chosen by `MainActivity.startCamera`): the last location fix (`LastFix.kt`), the saved view (where the camera last came to rest after a move the app did not make itself, written on camera idle at most every 2 s and when the activity stops) and the primary pack's view (its box fitted to the screen, timed when `PackManager` activated it with the camera; 0 for a pack found on the device). A `dystopo://map` link comes first, and an activity recreated with saved state keeps the camera MapLibre restores. The fix's time is when it last moved, more than its accuracy and at least 50 m, so a phone lying still does not outrank a view panned to after it; the fix opens at the saved view's zoom, else 14. After open, a fix the map receives within 10 s, before a gesture or any other camera move, recentres the camera once if it moved after the open view was set; when the open view is older than a week, or never set, any fix counts and the window is 60 s. The three are per-device state in the `device-view` preferences file, never synced settings. Every receiver of fixes calls `LastFix.record(fix)`: the map's listener and injected fixes (`MapController.onFix`) today. `GET /camera` `openView` says which won and why (`android-debug-routes.md`).

## The trail graph and the search index: built on first use, behind the heap guard (T149)

Neither is built when a download finishes (`RegionDownload` records the area and stops) nor at launch: the trail graph by the first route that needs it (a long-press, Route to here, `POST /route`, the trip editor, navigation's directions), the search index while the search box has the focus, its result list is open or it holds text (`SearchUi.wanted`; until then `GET /search/status` and `GET /packs` `search` read `idle` and start nothing). Before either builds, the build's peak heap is estimated (the graph: `RoutingGraphBuilder.measure`, the tiles at the read zoom and the routable vertices of 256 of them scaled to all, 48 MiB plus 300 bytes a vertex; the index: 12 MiB plus the archive's bytes; both times 1.5, fitted to T149's emulator measurement) and `HeapGuard.admitBuild` lets it start only when that fits the heap free now (the max less what is used and the reserve): a trim first, then up to 10 s of waiting, then the refusal; one build at a time. A refused graph says on the route card "This map is too large to route across on this phone; download a smaller area for routing" (while it waits: "Waiting for memory to build the trail network"); a refused index says "Not enough memory to index places now; try again in a minute". Either is asked again by a use after 30 s. Routes: `android-debug-routes.md` › Routes (`guard`, `POST /route/guard`, `force=1`).

## The UI thread and the watchdog (T144)

The rule: the UI thread never takes a lock and never does disk or network I/O; it reads snapshots that workers publish. The online indicator (`online/OnlineOverlay.kt`) shows an `OnlineUi` snapshot made each second on a worker (the camera is read on the UI thread, the view's source, the server state and "Download this region"'s record off it); the credit line's pack attributions are read off it too. `DystopoApp.reload` (a pack activated, downloaded, imported, updated or deleted, a setting that changes the tiles) opens the new tile service off the UI thread, publishes it through a volatile field and posts the style swap; the old service is reference counted (`RefCounted`, `Leases` in `TileService.kt`): every loopback request holds the service it started with (`LocalServer` takes the lease around the handler and releases it on every exit), the contour warm-up holds one while it runs, and the last holder closes the old packs. `PackManager.jumpTo` posts the camera move. **The watchdog** (`MainWatchdog.kt`, every build, release included; no setting): a worker posts a heartbeat to the UI thread every second; one unanswered for 3 s writes one dump per freeze to `files/reports/freeze-<UTC time>.txt` (the newest five kept; the format, `dystopo-report 1`, is the KDoc of `MainWatchdog`, which T145's report screen reads), naming the topmost app frame of the main stack most often seen in samples taken every 200 ms from the first silent second. It ticks only between the activity's `onResume` and `onPause`, from the first drawn frame after the process started (a cold start's first frame took 10 s on a just-booted emulator), never with a debugger attached, and rearms when a heartbeat returns. Debug routes: `android-debug-routes.md`.

## The app in the background (T150)

Nothing of the map's own runs while the app is stopped. `Foreground.kt` is one flag for the process, on while a `MainActivity` is started (counted at `onStart` and `onStop`); every Compose polling loop waits with `Foreground.delay` (one more pass at most after `onStop`, then paused until the next start), the country list's size worker and the ahead-on-the-route poll wait with `Foreground.block` (the poll goes on in the background only while a navigation runs). One flag rather than `repeatOnLifecycle(STARTED)` per effect: the thread loops have no lifecycle owner and a paused loop keeps its state. The map's device-location listener (`MapController.setForeground`) is removed at `onStop` and registered again at `onStart`, so the puck and follow mode resume on the next fix; track recording (its foreground service) and navigation (`NavSession`'s own GPS listener) keep their fixes, and the heading sensor was already released at `onStop` (T100). `MainActivity` is `singleTask`: a task started by a link, a notification or `am start -n` stacked another activity and map at each launcher tap (six after five taps); links that arrive while it lives reach `onNewIntent` (`DeepLink.install`, `ShareLink`). Debug builds run StrictMode with a penalty listener only (`debug/StrictModeCounts.kt`): a violation counts under the topmost frame in the app's package, one with none is exempt; release builds do not install it. Check: `GET /debug/cpu` twice, 60 s apart, after HOME; `dumpsys location` lists no registration of the package then. Routes: `android-debug-routes.md`.

## Problem reports (T145)

Crashes, freezes and kills are kept on the phone in `files/reports/`, every build, no setting (the crash-report survey of wave 20 found one practice: opt-in per report): the watchdog's `freeze-` dumps; `crash-` files, written by an uncaught-exception handler (`reports/Reports.kt`, `CrashCapture`, installed in `DystopoApp.onCreate`) before the platform's handler runs, with the crashing thread, its causes, the main thread and blocked threads; and `exit-` files, one per `ApplicationExitInfo` record (Android 11 and up) newer than the last one seen (`files/reports/.exits-seen`), read on a worker at launch: a crash the handler did not catch, a native crash, an ANR with the system's thread dump, a kill for low memory where the device reports one. One format for all (`dystopo-report 1`, the KDoc of `MainWatchdog`); the newest five of every kind together are kept. Settings › About and advanced › **Report a problem** (`reports/ReportRow.kt`) lists them; a tap shows one exactly as it would be sent (`reports/Report.kt`: the header in words, then the crashing, main and blocked threads, at most 40 frames each, every text through the scrubber of `shared/.../reports/Scrub.kt` with the phone's pack, area and search names), the privacy notice, **Open GitHub issue** and **Delete**. Open GitHub issue (T148) opens `https://github.com/jasondorjeshort/dystopo/issues/new` in the browser with `title`, `labels=crash` (applied only for users with triage rights) and a `body` of at most 4,000 encoded characters (the header and up to 12 top frames), the title alone past that. When the body holds everything the row shows (no stack, or the one kept stack fits and no thread was left out) nothing is copied, the body ends without a paste line and the line under the button says "The issue is complete; press Submit."; otherwise the clipboard first gets only what the body lacks (the stack frames past the body's, then the other stacks; no header) and the body's last line and the line under the button say "The rest of the stack trace is on your clipboard; paste it below."; a title-only link copies the whole text; no `template=`; the tester signs in and submits, the app sends nothing. Manual filers get `.github/ISSUE_TEMPLATE/problem-report.md`. To force each kind on an emulator: `POST /debug/crash`; `POST /debug/freeze?ms=6000` (a freeze dump); an ANR needs input waiting on the frozen UI thread and the process ended by the system: `POST /debug/freeze?ms=40000`, `adb shell input tap` within a second, then "Close app" in the "isn't responding" dialog (a `kill -9` of the process is recorded as a signal, not an ANR). Generated pack names (Download this region, Download the map around me) are `view-<local date>-<n>` (`view-2026-10-25-1`) since T145, no longer the view's centre and zooms; older names stay and still read. Routes: `android-debug-routes.md`.

## The device tour (`android-check.py`)

`android-check.py` relaunches the app and clears the contour cache first, then per view sets the camera, waits for idle, screenshots, diffs `/stats` and reads `/features`; it fails a view on: style not loaded, not idle, tile server errors, an expected source serving no tiles (T154: a source is expected when a tile of the viewport, from `GET /attribution` `viewBounds` at the zooms MapLibre asks that source for, overlaps its pack's bounds; a viewport tile over a pack still listed that the request log shows a pack answered before the view's baseline counts, as `servedBeforeBaseline`, since MapLibre keeps tiles the app's start fetched; each view's `expectation` gives the reason per source, finding `../findings/2026-10-26-z8-tiles-check-misses-the-start-up-tile.md`), a blank screenshot, no contour lines rendered, or labels placed but not drawn (`/features/text`); and the tour when no glyphs were served for a font the style uses. Contour tiles over `--contour-budget-ms` (1000) are warnings, failures with `--strict` (timings swing with host load). It also reports the app's logcat warnings. Look at the contact sheet (`out/android-tour-sheet.png`). T98: the summary records the server the app reads and its state at the start and the end (`setup.online`, `online`, and an `online:` line on stderr): a debug build on an emulator defaults to `http://10.0.2.2:8765`, the host's live viewer, so a tour runs online when that server is up and with an unreachable server when it is not (`POST /settings?server=` for no server: the phone reads the sources); T105: `--server <url>|none` sets it before the relaunch (`setup.serverSet`), and the first view waits until the device's CPU use besides the app is at most `--quiet-cores` (1.0) in two 3 s windows in a row (`setup.quiet`; a just-booted emulator is busy for about two minutes, `android-emulator.md`). T110: the first view, the cold one, waits up to `--first-wait-ms` (60000) for idle and the others `--wait-ms` (30000); each view reports `idleSeconds` (how long `/screenshot` waited) and `deviceCpu` (`others` and `app`, the cores the device used besides the app and the app's own while the view ran), so a slow view shows whether the device was busy; T115: a view that did not go idle reports `notIdleBecause` (`pendingTiles`: a request still open at the loopback server, such as a stalled OpenFreeMap fetch, finding `../findings/2026-10-16-cold-view-gap-on-a-quiet-device.md`). A view whose contour tiles were sampled with no elevation over a DEM pack (`contourGeneration.noDemOverPack`; T106: only where the pack itself has data in the tile's window, so not off a coast inside the pack's box) gets a warning naming them.

## Loopback token and the debug port

**Loopback token** (T49, `LoopbackToken.kt`): any app on the device can open 127.0.0.1:8686, so every request, tiles and the style included, must carry the app's per-launch random token, as `?t=<token>` or an `X-Dystopo-Token: <token>` header; anything else gets 401 (`/health` `server.tokenRefused` counts them). The style MapLibre loads puts `t=` in every tile, glyph and shade URL. **Debug port** (T57): debug builds serve the debug routes on a second loopback server on a random port per launch and announce it, with the token, only in logcat: `I/Dystopo: debug server on port N token T` (other apps cannot read another app's logcat, so the token stays with the app's process). Port 8686 then answers like a release build: map routes with the token, 404 for every debug route, no `/health`. `android-emu.ps1`, `android-check.py` and `android-probe.py` read the line through `adb logcat` (helper `tools/android_debug.py`) and forward the host port to it, again after a relaunch; by hand: `adb -s <serial> logcat -d -s Dystopo:I`, then `adb -s <serial> forward tcp:8686 tcp:<N>` and `curl -H "X-Dystopo-Token: <T>" localhost:8686/stats`. The setting `POST /settings?debugFixedPort=1` (from the next launch) puts the debug routes back on 8686 with the T49 bootstrap, where `GET /health` without the token answers only `{"token": "..."}` to a loopback caller; the logcat line then names 8686. Release builds have no debug routes and no bootstrap, so there the token never leaves the process.
