### T42. DEM decode speed
**Goal:** after T35, DEM PNG decoding is the biggest cost per contour tile on the phone (about 90 ms warm, up to 950 ms cold per tile through `BitmapImageDecoder` into `DemPyramid`). Decode each Terrarium tile once into a shared `FloatArray` grid cached by the pyramid (not a Bitmap), with a pure-Kotlin PNG decoder in `commonMain` (zlib through the injected `Decompressor`; filters 0 to 4; 8-bit RGB/RGBA only, which is all Terrarium needs) so Android, JVM and later iOS share it and the Android path skips `Bitmap` entirely; measure both decoders on the JVM (`contours bench` gains a decode split) and on the device; keep `BitmapImageDecoder` as a fallback behind a flag. Also let a map request pre-empt a warm-up tile in progress (T35) by checking a cancel flag between levels.
**Owns:** new `shared/.../png/**` (+ tests with small fixtures generated in-test), `shared/.../tiles/DemPyramid.kt`, `shared/.../tiles/ContourTiles.kt` (cancel checks), `androidApp/.../TileService.kt` (decoder choice, warm-up pre-emption), `devtool/.../ContoursCommand.kt` (decode split).
**Done when:** JVM decode of a 256×256 Terrarium tile under 1 ms warm; emulator z13 contour tiles under 100 ms warm and a fresh-install zoom-in max under 700 ms; goldens unchanged; `check` green.
**Status: merged (PR #48).** JVM target met (0.68 ms per tile); on the device the Kotlin decoder matches BitmapFactory rather than beating it. Follow-ups: Adler-32 and chunk CRC checks with fallback on any decode error and an IHDR size clamp (T50); bench honours the decoder setting; Kotlin decoder in `RoutePlanner` (T49) and devtool (T50).

### T44. Sync core and simulator
**Goal:** the phase-2 foundation for offline-first user data. In `shared`: an append-only operation log for tracks, waypoints, routes and settings (create, update field, append points, delete) with hybrid logical clocks and per-device ids; a merge that is deterministic and commutative (last-writer-wins per field by HLC, append-union for points, tombstones with a retention window); the `TrackStore` becomes a materialised view of the log (migration from the current tables, keeping ids); a `SyncTransport` interface with two implementations: a file bundle (export/import a `.dsync` file, for USB or any file share) and HTTP against a peer (`POST /sync/pull?since=` and `/sync/push` on the devtool server as the always-on peer, stored in a SQLite file there). A **sync simulator** in devtool: `sync-sim --peers 3 --ops 2000 --seed 42 --partitions 5 --reorder` runs in-process peers over a fake network with latency, partitions and reordering, checks that every peer converges to the same state, and replays any failure from its seed. On the phone: a "Sync now" action and a debug route `POST /sync?with=<url|file>`, `GET /sync/status`.
**Owns:** new `shared/.../sync/**` (+ tests), `shared/.../store/**` (log-backed store, migration `2.sqm`), new `devtool/.../SyncCommand.kt` and `SyncRoutes.kt` (server peer), new `androidApp/.../sync/**`, `SyncRoutes.kt` (app), Gradle only if a permissive dependency is truly needed (prefer none), the Sync section of `docs/PLANNING.md` (design as built).
**Done when:** `sync-sim` converges for 20 seeds with partitions and reordering and prints a JSON report; two emulators (or emulator plus JVM store) exchange a track both ways through the server peer and through a file bundle with identical GPX afterwards; a concurrent rename on two peers resolves the same way on both; existing tracks survive the migration; `check` green.
**Status: merged (PR #44).** Follow-ups: clock-skew guard on received HLCs; truncation and random-byte parsing tests with one exception type; chunked first sync and run-merged appends; sync app settings; authentication and signatures (phase 3); CLAUDE.md sync commands and routes.

### T45. Offline route planning over the trail network

**Owns:** new `shared/.../routing/**` (+ tests with a synthetic network and a Rainier fixture derived from public trails), new `devtool/.../RouteCommand.kt`, new `androidApp/.../routing/**`, `RouteRoutes.kt`, one hook in `packs/` for the graph build, one line in `Main.kt`.

### T46. Outdoors packs from the server for any small box
**Goal:** server-built packs today use OpenFreeMap tiles, which lack the outdoors layers (wilderness, cliff ticks, climbing routes, huts detail). Add `POST /build?profile=outdoors` that fetches raw OSM for the box from the Overpass API (respect its usage policy: one request, bbox under a configurable area, timeout, a polite user agent, cache the response), writes an `.osm.pbf` or `.osm.xml` the tilebuild profile can read, runs `tilebuild` in-process or as a subprocess with the outdoors profile for that box, and publishes `<name>-outdoors.pmtiles` with real provenance; fall back to the OpenFreeMap path with a warning when Overpass refuses or the box is too big. Pack precedence then prefers the outdoors profile (T41).
**Owns:** new `devtool/.../OverpassSource.kt`, `BuildRoutes.kt` (profile option and the tilebuild step), `tilebuild/**` (a bbox/extract entry point callable from devtool, keeping the heavy deps in tilebuild), `sources.json` (Overpass entry), `tools/demo/index.html` (profile choice on the build button).
**Done when:** a Paradise-area outdoors pack built from the browser shows wilderness fill, cliff ticks and climbing routes on the phone (screenshot viewed) and `pmtiles info` says `dystopo:profile=outdoors`; Overpass is called once per build and cached; a box over the limit gets a clear 413; `check` green.
**Status: merged (PR #42).** Follow-ups: faster water polygons for small builds; a wilderness fill in the style; document `profile=outdoors` and `:tilebuild:installDist` in CLAUDE.md; pack precedence by profile key (T41).
