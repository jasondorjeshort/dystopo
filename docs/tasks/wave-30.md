### T242. The online tile cache's index off the main thread and compact, the snapshot if the day allows (added 2026-11-07 from the owner's phone; launched after T235, a release after it)

The launch inventory's second candidate, now with the owner's traces (issues 31 and 32, Samsung SM-N975U1, Android 12): "no first frame within 120.04 s", 119.93 s under the mark `OnlineService: TileCache` at `TileCache.<init>`, 640 of 1172 samples, running 1056, disk 116, CPU 93.88 s; and a start whose first frame came at 82.35 s, 81.79 s under the same mark. The sampled stack is `FileTreeWalk.gotoNext` in `File.isDirectory`. The mark settles where the data sits: `cacheDir/online/tiles`. `OnlineService` is built in `DystopoApp.onCreate` on the main thread, and `TileCache`'s constructor walks that directory twice, makes a `(File, mtime)` pair per file, sorts the list, fills a `LinkedHashMap` entry per file and then `recountPinned` asks `Areas.isPinned` for each (`online/TileCache.kt`, `init`); `Areas.attach` then walks every key again (`rowsOf`). The critic's estimate: about 250 B transient plus about 165 B of index per file, so a million files is about 415 MB live and 1.3 million about 540 MB against the phone's 576 MB large heap (`AreaLimit`'s figure; T149 planned France at full detail as 1.44 million tiles for 174 GB): the hour is garbage collection near the limit (an OOM would have crashed, not frozen), and a force-kill means nothing is kept, so every launch starts over. Every hot and warm start in the same history read 0.1 to 0.4 s. T152 left "a compact or on-disk index for real 100 GB use" as a follow-up; this is it. Critic: `out/wave30-research/critic-T242.md` [no-check: gitignored] (3 blocking, 8 serious, 12 minor), all taken below.
**Goal:** in this order; the cuts if the day runs out, first to last: (c) whole, then the packed keys of (b) (keep the struct of arrays with interned string keys), then (d)'s largest count. (a) **The launch does not wait for the index, and nothing on the main thread waits for the walk.** `TileCache` starts in state `indexing`; a worker started by the constructor walks the directory into a private structure without holding the cache's lock and swaps it in (or inserts in short batches under the lock), then the state is `ready`. Meanwhile: `get` reads the file directly and adds the entry it finds; `put` writes and adds its entry at once; the walk skips keys already present; `contains` while indexing answers from a disk stat (so `OnlineFetcher`'s pinned older-version lookup and `DirectSources` do not refetch or re-synthesize); the getters `bytes`, `size`, `pinnedBytes`, `pinnedSize` and `json()` never wait and carry `partial: true` while indexing (T236's card reads them on the main thread). The methods that need the whole index wait for `ready` off the main thread, bounded, and are a `check` naming the caller on it (T229's rule): `trim`, `recountPinned`, `clearWhere`, `clear`, `clearUnkept`, `evictOldest`, `oldestTouch`, `bytesWhere`, `byPrefix`, `forEachKey`, and `ContourCache.collectGarbage`'s clear and `AreaDownload`'s per-key clear through them. `Areas.attach`'s `rowsOf` and `CacheBudget`'s first enforce run after `ready` on their own threads (`CacheBudget.set`'s 60 s `get` accounted for). `Areas.coverage` (through `rowsOf`) and `Storage.json` (through `byPrefix` and `bytesWhere`) answer `indexing` instead of waiting, so the one list and the Storage screen open during the walk and say "Counting the map tiles" where a figure would be (the strings listed); `ContourCache`, the same class, gets the same.
