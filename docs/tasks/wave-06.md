# Wave 6 (T1–T24 merged; phase 1 on the device)
Shared rules for this wave: the Android app files are split by task below; a task that needs a hook in a file it does not own adds **one line** there (a route registration, a callback) and says so in the PR. New debug routes go in a new `<Feature>Routes.kt` registered with one line in `Routes.kt`. Device testing: the `devtool serve` stand-in plus `demo-check.py` first; when a real device is needed, boot **your own** emulator (`tools\android-emu.ps1 -Avd dystopo35-<task> -Port <unique, 8690+>`; the machine has 128 GB, so several 4 GB AVDs are fine) and target it with `ANDROID_SERIAL=emulator-<port>`; never touch another task's AVD or `emulator-5554`, and kill yours when done (`adb -s emulator-NNNN emu kill`). Every task ends with the emulator numbers (`/stats`) and a viewed `/screenshot` in the PR body.

### T25. Labels on the device, and text scale
**Goal:** text renders on the phone. On the emulator no symbol text appears at all (names, peak elevations, contour labels) while the same style shows them in `devtool serve` + MapLibre GL JS; only 2 glyph requests were served, so suspect the glyph route or path (`/glyphs/{fontstack}/{range}.pbf`, URL-encoded font names with spaces, missing ranges returning 404 instead of an empty glyph PBF), `text-font` names in `MapLibreStyle`, or symbol layers filtered out by MapLibre Native (expressions GL JS tolerates but Native rejects: check logcat for style warnings). Fix it so names, elevations and contour labels render. Then add a **text scale** setting (the design goal that phone labels are too small): a multiplier applied to every `text-size` and icon size when the style is built, default 1.0, settable at runtime through `POST /settings?textScale=1.5` and `GET /settings`, persisted in app preferences. Larger text must not just overlap: check MapLibre collision settings and symbol spacing.
**Owns:** `shared/.../maplibre/MapLibreStyle.kt` (+ tests), the glyph handling in `androidApp/.../Routes.kt` and `devtool/.../ServeCommand.kt`, the glyph part of `tools/android-push-pack.ps1`, new `androidApp/.../SettingsRoutes.kt` and a settings holder, one-line hooks elsewhere.
**Done when:** a `/screenshot` at z13.5 near Paradise shows road names, peak names with elevations and contour labels (viewed and described); a second screenshot at `textScale=1.6` shows visibly larger text without a pile-up; a `MapLibreStyle` test asserts every symbol layer has a font the glyph route can serve; `check` green.
**Status: merged (PR #27).** Root cause was the emulator's software GPU; the glyph timeout was a second, real bug. Follow-ups: 400 for out-of-range `textScale`; POI markers as a sprite sheet so labels collide with them; denser contour labels; `TileService.glyph` is now only an HTTP fallback.

### T26. Contour tile performance and cache identity
**Goal:** every contour tile under 1 s on the emulator and no serialisation. Today z13 to z15 take 0.2 to 0.5 s but z12 takes 6.7 to 9.7 s and z7/z8 7 to 8 s (trace+encode 4 to 6 s, sampling 1 to 5 s), because low-zoom tiles sample a DEM level that is far too fine; and `TileService.contourTile` holds one lock so tiles generate one at a time (logcat: long monitor contention). Choose the DEM zoom per tile zoom (about 1 to 2 levels above the tile, with the zoom → interval table deciding what is worth tracing), simplify before encoding, generate tiles concurrently (per-tile parallelism, bounded by cores) with a per-tile lock rather than a global one, and keep the DEM decode cache thread-safe. Key the contour disk cache on the DEM pack identity (file size and mtime, or the PMTiles header hash) so a replaced pack never serves stale contours; drop stale entries lazily. Report everything in `/stats` (per-zoom min/avg/max, concurrency, cache version).
**Owns:** `shared/.../tiles/ContourTiles.kt` (+ tests), `androidApp/.../TileService.kt`, the DEM decode cache; one-line hooks elsewhere.
**Done when:** a JVM test proves the DEM zoom choice per tile zoom; the emulator `/stats` after a z8 → z15 zoom-in shows max contour ms under 1000 and at least 2 tiles generating concurrently; a pack swap (push a second DEM file, `/reload`) is followed by fresh contours without `/cache/clear` (show a stats or hash difference); `check` green.
**Status: merged (PR #29).** Follow-ups: cold-start z12 tiles still 2 to 2.9 s (warm them in the background after install or pack activation); a cheaper tracer in `render/Contours.kt`; in-flight decode dedup needs a platform wait primitive in shared code; identity by content hash instead of mtime so an identical re-push keeps the cache; measure Java heap after zoom-ins against the phone budget.

### T29. Region packs on the device
**Goal:** the app manages packs instead of assuming one Rainier pair. A pack is a DEM PMTiles plus an optional vector PMTiles sharing a name (`<name>-dem.pmtiles`, `<name>-outdoors.pmtiles`); the app lists packs in its files dir with name, bounds, zoom range, size and attribution read from the PMTiles headers and metadata (shared code: `shared/.../packs/PackInfo.kt` over the existing reader), lets the user pick the active pack (Compose list screen reached from the map) and jumps the camera to its bounds, and can **download** a pack pair from an HTTP(S) URL with progress and resume (range requests; the server is a plain static host; the devtool `serve` can serve `out/` as that host for testing). Debug: `GET /packs`, `POST /packs/activate?name=`, `POST /packs/download?url=`, `GET /packs/download` (progress), `DELETE /packs/{name}`.
**Owns:** new `shared/.../packs/**` (+ tests), new `androidApp/.../packs/**` (manager, download, Compose screen), `androidApp/.../Packs.kt`, new `PacksRoutes.kt`, a static `out/` route in `devtool/.../ServeCommand.kt` (one block), one-line hooks elsewhere.
**Done when:** `/packs` lists the pushed Rainier pack with correct bounds and zooms; a download of a second small pack from `devtool serve` completes with progress visible in `/packs/download` and survives a kill and restart mid-download (resume); activating it moves the camera (screenshot viewed); `check` green.
**Status: merged (PR #26).** Follow-ups: move the 10.0.2.2 cleartext entry to a debug-only network config; refresh the attribution line and no-pack message on pack switch; dark status-bar icons on the pack screen; document `?kbps=`; the contour-cache clear on pack switch is redundant now that T26 keys the cache on the pack.

### T32. Live world mode for the viewer
**Goal:** the browser demo and `devtool serve` stop being pack-only. Today both read one Rainier pack pair from `out/`, so panning away shows nothing (the owner noticed). Add a **live** mode to `devtool serve` (`serve --live`): `/dem/{z}/{x}/{y}.png` is generated on request from the cloud sources through the existing `best` source (3DEP where covered, Copernicus elsewhere, EGM2008), using the `tiles` command's per-tile path and the shared disk cache, so any place on earth renders after a first-view fetch delay; `/contours` follows from the live DEM; packs in `out/` take precedence where they cover the tile (pack first, live fallback). For OSM, where no pack covers the tile, proxy a free public OpenMapTiles-schema vector source (OpenFreeMap, https://openfreemap.org, ODbL, no key; read its usage terms and record it in `sources.json` with attribution) with on-disk caching, so base layers draw everywhere; outdoors-only layers (wilderness, ticks, climbing routes) appear only inside packs, and the style must not error where their source-layers are absent. Hook the browser demo (`tools/demo/index.html`) to the serve endpoints when `?live=1` (or when it is opened from `serve`), with a status box showing which source each visible tile came from (pack / live-3dep / live-copernicus / openfreemap) and a `Build pack here` button that prints the `tiles` + `tilebuild` commands for the current view (no server-side build yet). Report per-tile source and timings in `/stats`. Keep `demo-check.py` working against both modes (`--url`).
**Owns:** `devtool/.../ServeCommand.kt` (live mode; T29 adds a static `out/` block to the same file, keep yours in a separate `LiveTiles.kt` and a one-line registration), new `devtool/.../LiveTiles.kt`, `tools/demo/index.html` (live hooks and status box), `tools/demo-check.py` (`--url` only), `sources.json` (OpenFreeMap entry), the browser-demo paragraph in `CLAUDE.md`.
**Done when:** `serve --live` plus `demo-check.py --url http://localhost:8687/?live=1 --views 12/45.83/6.86 12/-3.07/37.36 12/46.85/-121.76` passes (Mont Blanc, Kilimanjaro, Rainier: hillshade, contours and OSM base layers all non-zero; screenshots viewed and described, with the source box showing live-copernicus, live-copernicus and pack respectively); a cold Mont Blanc z12 view renders in under 60 s and a warm one under 2 s (numbers in the PR); `check` green; tour and demo tour still green.
