### T304. The phone parts over wireless debugging: a failed adb read is not a change
The first run on the owner's phone (2026-11-18, sweep `20261118-0901`, wireless debugging, an `ip:port` serial) went red on phone-tour, phone-startup and phone-diagnostics, each on one 60 s adb timeout during a five-minute stall of the wireless link, and on phone-release with "the release install changed". The release app was untouched: `Get-ReleaseFacts` reads `pm list packages` through `Tool-Text`, which returns an empty string on a timeout, and the empty string read as "not installed". Added on the owner's word ("Lets try to fix it then.").
**Goal:** (1) `phone-release` compares only facts it read: a failed or timed-out adb read is retried once or twice and then fails the part with "could not re-read the release install", never "changed"; the same holds for the `before` read. (2) Before the phone parts, a reachability probe that runs a command (`shell echo ok`, short timeout), not only `get-state`; on a failure it runs `adb reconnect` for that serial once and probes again. (3) When a phone part's adb stops answering (a timeout), the remaining phone parts are marked skipped with "adb stopped answering" rather than each spending its own timeout. (4) A phone part that exits non-zero carries its error log's last line in its note. Nothing else in the phone parts' behaviour changes, and the safety rules of T303 stay as they are.
**Owns:** `tools/sweep.ps1` (the phone parts, `Get-ReleaseFacts`, a strict variant of `Tool-Text` if needed), `tools/sweep-summary.py` (only if the phone section must show the new states), `docs/reference/release-realism.md` (the phone parts; wireless debugging: one transport, screen on, Wi-Fi power saving off).
