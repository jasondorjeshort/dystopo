# Wave 29 (T1–T226 merged, v0.1.20-alpha published; the owner's theme: trace the startup freezes)

Planned 2026-11-05 on the owner's words: "The android app still freezes sometimes quite significantly on startup. We need a way to trace this, even if it involves adding logging and reporting a problem with it through our github push interface." The interface is Report a problem's Open GitHub issue (T145, T148); the tester still sends each report by hand, and nothing is uploaded on its own. Two tasks, one at a time, T227 first; the fix of whatever the traces name is a later task, on evidence. Allowance: the 7-day meter at planning 82, two tasks at 1.25 each and the wave's fixed 3, adds up to about 87.5, under the hold of 97; the 5-hour meter at 3.

Why the present tools cannot answer it, read from the code and the filed issues: (1) `MainWatchdog` is armed only between `onResume` and `onPause` and only after the first drawn frame, so `DystopoApp.onCreate`, `MainActivity.onCreate`, the first composition and a return from the background (`onStart`) are not watched; only a system ANR sees them, and that needs input waiting and then an ANR record. (2) A freeze dump is written at 3 s and never updated, so a 40 s freeze reads 3 s and its later stacks are lost. (3) Release stacks are unreadable: issue 29's frames read `d7.m.c(r8-map-id-…:120)`; R8 renames our classes, no mapping is kept anywhere, and the app-frame test (`MainWatchdog.blockingFrame`, the same test in `CrashCapture` and `ExitImport`) matches our package name, so it finds nothing in a release build (the titles of issues 23 to 29 name no frame), and each long frame eats the issue body's 4,000 characters.

Decided: names stay readable rather than publishing mapping files and retracing. The code is public, so renaming hides nothing; the app's own frame matching then works on the phone, and a report reads without a tool. T227 found `-dontobfuscate` alone leaves frames unreadable (lambdas merged, lines rewritten), so `-dontoptimize` goes with it and shrinking stays on (ADR 0058; this replaces "shrinking and optimising stay on"; a real phone has not been compared). Thresholds are Android vitals' excessive start times (cold 5 s, warm 2 s, hot 1.5 s), so no setting (ADR 0044: one practice); a stall after the first frame counts from 2 s, and a map not drawn 15 s after the first frame is this wave's own figure, from T128's Later entry (a cold view not idle for 45 to 109 s). A system trace (`ProfilingManager`, API 35 and up) is left out: it is binary, large and cannot go in an issue. The critic's 14 objections are answered in the two tasks below, with three exceptions: the `MainWatchdog` KDoc item in Later was already done by T170, so it is struck; an ANR outside a trace window stays T148's open follow-up (issue 24 has no stack), untouched here; and the owner action "the first `MainWatchdog` dump that names a freeze's frame" stays open until a release carries T227. T229 (the launch's disk work off the main thread, "to plan" here) is planned in wave 30 from the launch inventory's top candidate; the rest of it waits for the owner's trace. **At the close (2026-11-07):** the 7-day meter had reset on 2026-11-05 (it read 27 at the close, after the five later tasks T230 to T233, the sweep and the release), so this wave's reading cannot be set against its figure and the per-task figure is left at 1.25.

### T228. A trace of every start, reported through Report a problem
**Goal:** a tester whose app froze on the splash can send one report that says where the time went. Launched after T227 merges.
**The windows.** A new `StartupTrace` with a pure, tested core, in every build, no setting (T144's reasoning). It starts in `DystopoApp.attachBaseContext` with a worker thread of its own and reads `Process.getStartElapsedRealtime()`. A window opens at process start (provisional until an activity appears), at a `MainActivity.onCreate` in a live process, and at an `onStart` with none open. Kinds: **cold** is an `onCreate` within about 1 s of `DystopoApp.onCreate`'s end in a new process; **warm** is any other `onCreate`, measured from that `onCreate` (a process started by WorkManager or the tracking service and brought forward later is warm, not "cold, first frame 21 s"); **hot** is the `onStart` case. On API 35 and up, `ApplicationStartInfo`'s start type wins. A window closes 30 s after the first drawn frame (5 s when hot), or at the end of a stall still running then, 120 s at most, and the worker stops. `MainWatchdog` writes no freeze dump while one is open and is armed from the close with its detector reset, so a freeze gives one report and no gap. Skipped under a debugger, as the watchdog does.
**What it records.** Named marks around each step of `DystopoApp.onCreate` and `MainActivity.onCreate`, `setContent`, `onStart`, `onResume`, the first drawn frame, the style loaded and `MapController.fullyLoaded` first true. A mark may name the view's source (fix, saved, pack), never coordinates. **Before the first frame** the main looper cannot answer a post (the launch's messages run first), so the worker samples the main stack every 100 ms throughout, with the thread's state and CPU time from `/proc/self/task/<tid>/stat` (running, waiting on a lock and starved read differently), attributed to the mark in force; it is reported by mark, not as a stall. **After the first frame** one heartbeat at a time every 100 ms finds stalls; while one is unanswered for 250 ms the worker samples the same way. Each stall of 500 ms and up keeps its true start and length, its mark, its most common stack, that stack's share of the samples and its topmost app frame. **A blank map with a responsive UI thread:** when `fullyLoaded` is still false 5 s and 15 s after the first frame, one snapshot each of every thread (as `MainWatchdog.dump`) plus the tile counters and `idleBlockers()` reasons, counts and reason names only, never a tile path. The header carries: kind, first start after an install or update, process start to `attachBaseContext` in a field labelled as loading and field initialisers, not sampled (no claim of stacks from process start), seconds since boot, available and total RAM, the low-memory flag, thermal status and battery saver where the API has them, Java heap max and used at the first frame and the GC count, the number and total bytes of packs (no names), and `ApplicationStartInfo`'s reason and timestamps on API 35 and up.
**Surviving a kill.** The case that matters most is the tester force-closing a frozen app. From 1 s into a window with a stall running (before the first frame, 1 s after the window opens), the worker rewrites an in-progress file (`tmp` then rename, off the main thread) every second, carrying the pid, a start id and the process importance read at attach (`getMyMemoryState`). The normal end writes the final trace, then deletes the in-progress file, and a reader dedupes by start id, so a kill between the two is not ambiguous. At the next launch a leftover becomes a report whose outcome says the process ended during the start, with what it had; the trace reads `getHistoricalProcessExitReasons` itself and matches by pid to name the reason, including user-requested (`ExitImport.kindOf` drops it, and its import races this one, so do not depend on it). A leftover with no activity mark whose importance at attach was not foreground is discarded (a background process killed by the system is not a slow start).
**The report.** A `startup-` report in `files/reports/`, in the `dystopo-report 1` format, when: the first frame is over the kind's threshold; a stall after the first frame reaches 2 s; `fullyLoaded` is still false 15 s after the first frame; or the start did not finish. A normal start under those writes no report. Kind label "Startup freeze" (the owner, 2026-11-05: "The screen freezes on the splash. That's what I mean by freeze. It's during the opening."; so the body and title lead with where the time before the first frame went, each mark with its top stack, largest first), title like `Startup freeze: 14.2 s, at PackSet.open (0.1.21-alpha)` or `Startup freeze: map not drawn after 15 s (0.1.21-alpha)`. The timeline and the stall list come first in the issue body, ahead of any frames, so they fit the 4,000 characters; the existing clipboard rule covers the rest. Every string goes through `Scrub`, and times are written with units between them ("1.2 s to 3.4 s"), since `PrivacyCheck` reads adjacent bare decimals as a coordinate pair. `startup-` reports have their own quota of 3 and never push out a crash, a freeze or a kill. Every start's trace is also kept (the newest 3, hidden from the list unless slow), and Report a problem gains **Report the last start**, for a start that felt slow but passed the thresholds. A small `.startup-history` (one line a start, the newest 20: version, kind, first frame, longest stall, outcome) goes in each report as its last section, since the owner says it happens "sometimes" and the pattern is the clue. The notice above the button says what the report now contains.
**Agent-testable:** `GET /debug/startup` (the current trace as JSON, the window's state, thresholds, history); `POST /debug/startup/stall?at=appOnCreate|activityOnCreate|afterFirstFrame&ms=` (debug builds only: one stall in the next launch, then forgotten); `POST /debug/startup/thresholds`; new `tools/android-startup.py --serial <s> --launches <n> [--warm|--hot]` (force-stops when cold, launches, prints one JSON summary of first-frame and longest-stall figures), with `tools/test_android_startup.py` for its parsing. [no-check: both tools are new in this task]
**Owns:** [no-check: new files named] new `androidApp/.../app/StartupTrace.kt`, new `app/StartupRoutes.kt`, new `androidApp/src/test/.../StartupTraceTest.kt`, new `tools/android-startup.py` and `tools/test_android_startup.py`, `app/reports/Report.kt`, `Reports.kt`, `ReportRow.kt`, `ReportRoutes.kt` and `ReportTest.kt`, in `app/MainWatchdog.kt` the suppression and the re-arming only, the marks in `app/DystopoApp.kt`, `app/MainActivity.kt` and `app/MapController.kt` (marks only, no reordering of startup and no work moved off the main thread: this task measures, a later one fixes), one dispatch line in `app/Routes.kt`, moving `ThreadCpu` out of `debug/DebugRoutes.kt`, the shared `Scrub` only if a new field needs it, and `docs/reference/android-app.md` (the watchdog's and Problem reports' sections), `docs/reference/android-debug-routes.md`.
**Interacts with:** T227, merged first: the freeze dump this task suppresses, and the readable frames it relies on.
**Done when:** `check` green with unit tests of the core (cold, warm and hot, the background start brought forward later, a stall's length and mark, each report rule, a healthy 3 s cold start writing no report, the window running on past a stall at its close, the leftover becoming a report, the discarded background leftover, the dedupe, the quota, the body's order and its 4,000-character limit, and `Scrub.text` leaving a timeline unchanged). On an API 35 emulator, each seen in `GET /reports` and on the row in a screenshot, its new strings listed in the report: `stall?at=appOnCreate&ms=8000` gives a Startup freeze report naming the injected frame under `DystopoApp.onCreate`'s mark; `at=activityOnCreate` likewise; `at=afterFirstFrame` gives one report and no `freeze-` file; `adb shell am force-stop` five seconds into a 30 s stall gives, at the next launch, a report saying the process ended during the start and the user-requested reason; a normal launch gives no report but Report the last start shows its timeline; `POST /debug/freeze?ms=12000` once `GET /debug/startup` shows the window closed gives a `freeze-` file and no `startup-` file; an HOME then return with a stall injected shows a hot window's figures; a blank-map case (`POST /settings?server=` an unreachable server with no pack, or whichever the implementer finds gives no full render) reports `map not drawn` with its snapshots and no tile path. `POST /reports/open?id=` on a Startup freeze report shows the timeline in the link's body. On a release APK, the app starts, reaches the map and Report the last start shows real class names. Cost: `tools/android-startup.py --launches 10` with the trace on and with it disabled in a scratch build gives the first frame's median for each; the report gives both, and a gap over 50 ms on a quiet device is a defect.
**Status: merged.** Startup traces and Startup freeze reports, the cost unmeasurable on an emulator; verifier MERGE WITH NOTES, no fix round; the implementer's report was lost, so the merge body is the verifier's runs. Follow-ups: a reused AVD keeps `.startup-test` thresholds, so the docs should say to clear them (`POST /debug/startup/thresholds?clear=1`) before a scenario; the emulator's ordinary cold start is often over the 5 s limit; the release stack was not read down to an app frame of our own package; the cost pair ran five launches each, not ten; a release carrying T228 to the owner's phone, then T229 from its trace.

### T231. An emulator guard in the boot script (small; before T230)
**Why:** the owner, 2026-11-06: "I've had too many problems with them eating up all my ram use", and the guard should be automated, not the coordinator's watch. Finding `docs/findings/2026-11-05-emulator-private-bytes-grow-per-cold-launch.md` (44 GB in 51 minutes, unread).
**Goal:** (a) Every boot by `tools/android-emu.ps1` starts a detached guard beside its emulator that reads the qemu PID from the emulator's lock, polls private bytes and the PC's free RAM, and stops that emulator alone (console `emu kill`, then the PID, as `emulator-stop.js` does) when its private bytes pass a limit or the PC's free RAM falls under a floor; each stop is a line in the lock folder's `stop.log` and the script's log, with the figures. The guard ends with its emulator. (b) Admission by RAM: a boot also waits or refuses, naming the figures, when free RAM is under the emulator's cost plus the floor, so the number of emulators follows the RAM free; `emulators.max` stays as a ceiling. Limits in the `emulators` block of `.claude/hooks/policy.json` with the defaults the implementer measures and states.
**Owns:** `tools/android-emu.ps1`, a new guard script under `tools/` [no-check: new], the `emulators` block of `.claude/hooks/policy.json`, `.claude/hooks/emulator-lock.js` and `test-hooks.js` only if the lock format changes, `docs/reference/android-emulator.md` (The emulator cap), the finding's Next.
**Done when:** on an emulator of its own with the limit set low, the guard stops it and logs why, and leaves any other emulator running; a boot with the floor set above free RAM is refused with the figures; a normal boot and `-Stop` leave no guard running; `node .claude/hooks/test-hooks.js` and `check` green.
**Status: merged.** The guard and RAM admission, defaults 8 GB private, 4 GB floor, 5 GB a boot; verifier MERGE WITH NOTES, no fix round.
