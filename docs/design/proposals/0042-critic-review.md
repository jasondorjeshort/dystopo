Date: 2026-10-23

## Code checks

- **What the export writes** (`shared/.../store/TrackExport.kt`, `gpx/Gpx.kt` `write(doc, ids)`): metadata name and time, waypoints, every track with `dystopo:id` when `ids = true`, `creator="Dystopo"` on the root, and each point's `extensions` **copied verbatim** (Garmin hr/cad/temp when imported). `ids = false` drops only the id. The upload writer therefore needs a document with no metadata, no waypoints and points stripped of `extensions`; the proposal's "no extensions" is right but `Gpx.write(ids = false)` alone does not deliver it (objection 7). The `creator` attribute leaves too and is not in item 3's list.
- **Trimming does not touch the stored track:** nothing is built yet (T134 owns no code), but the design holds: `TrackExport.document` returns a value built from the store, and the proposal sends a cut copy. Consistent.
- **Debug routes with no network:** `POST /osm/config?api=` restricted to home-network and loopback hosts is exactly `CleartextPolicy.problem` (`firstrun/CleartextPolicy.kt`), the same gate `update-api.txt` uses; `MockReleases` in `tools/android-ui.py` is a sound pattern for `tools/osm-mock.py`. Gap: the mock has no `/oauth2/revoke` (Sign out would fail against it) and the browser return path is bypassed by `signin?token=` (objection 5).
- **Strings:** every proposed string either names OpenStreetMap under the flagged exception or names no product. "Not sent: <reason>" may carry the server's error text; acceptable, say so. "anonymous" is a wording problem, not a product name (objection 2).
- **The return path as the share link does it:** `MainActivity` has `addOnNewIntentListener { ShareLink.handle(it) }` but the manifest sets **no `launchMode`**, so a browser's `ACTION_VIEW` on a `standard` activity creates a second `MainActivity` (and a second `MapView`) rather than delivering `onNewIntent` (objection 1).
- **Token storage precedent:** `AppSync` keeps its bearer token in `getSharedPreferences(..., MODE_PRIVATE)`; `allowBackup="false"` in the manifest, so it never reaches cloud backup. The same is adequate here.
- **Registry:** `SourceRegistry.attribution(ids)` composes credits by id only, so an `osm-traces` entry would not leak into any credit line; but `SourceKind.OSM` is documented as "inputs to the OSM vector tile build" and the enum is validated at parse (objection 12).
- **No share sheet exists today** (`grep ACTION_SEND|createChooser|FileProvider` over `androidApp/`: nothing); GPX export writes to the app's private `files/tracks/`, which no browser or picker can see. This is why C is worse than it looks, and it also undercuts the parent idea's premise that the cloud drive is "mostly covered today by GPX through the system file picker and share sheet".

## Objections

1. **Serious. The return of the authorization code is under-specified and, as written, broken.** Evidence: `AndroidManifest.xml` sets no `launchMode`; `MainActivity.kt` handles `intent` in `onCreate` and `onNewIntent` only for a reused instance; a browser's `VIEW` intent on a `standard` activity creates a second instance (two maps, back goes to the old one). The PKCE verifier and `state` live in process memory, and Android may kill the app while the browser is in front (the authorization code lives 10 minutes, Doorkeeper default). Resolution: a small exported no-UI `OsmAuthActivity` for host `osm` (`exported="true"`, BROWSABLE) that hands `code`/`state` to a process singleton and finishes, so `MainActivity` is untouched (or `singleTask` on `MainActivity`, saying what that changes for `map` and `share` links); the verifier, `state` and their expiry kept in the private preferences file; the objection is resolved when the device tour drives the return with `adb shell am start -d "dystopo://osm?code=...&state=..."` (objection 5).
2. **Serious. "Anonymous" over-promises.** Item 5 calls trackable "anonymous". The wiki's definition is "not linked to your user in the API"; the privacy policy says the raw file is kept, the website lists the trace under the owner's own account, the timestamps go out in order, and the description text is the user's own words. Resolution: never "anonymous"; one sentence each in the wiki's own terms ("Not shown under your name; the points and their times are public" / "Listed under your name with the points and their times") and the fixed line kept.
3. **Serious. The trace id "nullable column" is a data-format decision left implicit.** A new track column is a trackdb migration (`.claude/rules/trackdb.md`) and, if synced, a wire-format change: `sync/Ops.kt` `TRACK_FIELDS` is a closed set (`name, description, comment, source, type, extensions`), so a synced field means a new `SetField` name every device must accept (ADR 0033). A's exit cost says "no data migrates", which is only true if the column is local. Resolution: say "a local-only column, not in the op log, dropped by a later migration" (my recommendation: the id has one use, opening the trace on the website, and a second phone can fetch it from `user/gpx_files`), or flag the synced field per ADR 0033.
4. **Serious. The custom scheme rests on an undocumented behaviour; the fallback should be the documented one.** The wiki's rule is https except `http://127.0.0.1`; acceptance of `dystopo://osm` is a property of the validator's current code, and the three apps above prove it works today. Nothing stops OSMF from tightening the callable (`force_ssl_in_redirect_uri` is theirs); existing registrations would likely keep working until re-validated, but "What would change this recommendation" covers only refusal at registration. B (fixed port, a token-exempt route, a manual switch back) is the weaker fallback: an https App Link on a domain the project already uses as a namespace (`https://jasondorjeshort.github.io/dystopo/gpx/1` in `GpxExtensions.NS_DYSTOPO`; `.well-known/assetlinks.json` on GitHub Pages) is what OsmAnd does, is exclusive to this app on Android 12+, and is what the wiki says. Resolution: cite the three apps as the confirmation; correct "Who else" (OsmAnd: https App Link plus a shipped secret); add the App Link as A's fallback ahead of B, with its own moving part (a hosted file); state that `state` plus PKCE is what makes a non-exclusive scheme safe (RFC 8252 §8.1: any app may claim `dystopo://`); keep the dev registration as the first step.
5. **Serious. The riskiest piece has no agent path.** Item 10 drives sign-in by `POST /osm/signin?token=`, so the authorize redirect, the `state` check, the code exchange and the intent handling (objection 1) are never exercised by a script. Resolution: `GET /osm` exposes the pending `state` in debug builds; the mock's `/oauth2/token` accepts any code with the matching verifier; the tour step is `POST /osm/signin` (opens the browser or, with `?nobrowser=1`, only prepares the request), `am start -d "dystopo://osm?code=mock&state=<state>"`, then `GET /osm` shows `signedIn: true`. Add `/oauth2/revoke` to the mock.
6. **Minor. B's premise is wrong in a way that helps B.** Doorkeeper ignores the port for loopback redirects (RFC 8252 §7.3), so B needs no fixed port and the "another app on 8686" risk is avoidable with an ephemeral listener. B stays worse than A and the App Link (manual return, an exempt route), but its text should be corrected.
7. **Minor. Item 2 and item 3 contradict each other on the name, and item 3 omits two things that leave.** The description is prefilled with the track name, so the name leaves unless edited; the default name is `Track yyyy-MM-dd HH:mm` in local time (`Tracking.kt:160`). The GPX root carries `creator="Dystopo"`. If `Updater`'s User-Agent is reused it is `Dystopo/<version> (Android <sdk>)` (`Updater.kt:441`), which is "the device" item 3 excludes. Point `extensions` must be stripped explicitly (Code checks). Resolution: list the description (prefill), `creator` and the exact User-Agent (`Dystopo/<version>` with nothing else) under item 3.
8. **Minor. "SHA-256 is already in `sync/crypto`"** is `packs/Sha256.kt` (pure Kotlin, used by `Hkdf`). PKCE also needs 32 random bytes and base64url; randomness is the platform's (`SecureRandom` is `java.*`), so the shared API takes the verifier bytes as input. Factual fix.
9. **Minor. A remembered trim radius can silently become 0.** A user who once picks 0 for a trailhead track sends the next track from home untrimmed; the fixed caveat line is still true and the grey map still shows nothing cut. Also the rule uses the track's first and last point only; a multi-segment track (the recorder splits on `gapS`) can start a later segment at another private place. Resolution: remember the choice only when it is at least the default, or show the chosen radius on the Send button itself ("Send, ends cut 500 m" / "Send, nothing cut") so the state is read at the moment of sending; note the segment case as a known limit.
10. **Minor. Refusals do not all say who lifts them.** Not signed in: the sheet's Sign in button, the user (fine). Trims to nothing: "the sheet says so" should say the remedy (choose a smaller cut). A failed send: keep the sheet and its fields; a 401 after a website-side revoke must say "Sign in again" (the token never expires, so 401 means revoked). A recording track: the action is absent, not disabled, so the user is not told why; one line in the track's sheet. `POST /osm/send/confirm` with no sheet: 409 with "open the sheet first".
11. **Minor. The terms string asserts what the Contributor Terms do not say.** "Uploads are contributions under the OpenStreetMap Contributor Terms": the Contributor Terms never mention traces (the proposal admits it); the Terms of Use say contributions are governed by them and incorporate the usage policies; the Privacy Policy is the document that actually governs traces. Resolution: "Sending uses your OpenStreetMap account under its Terms of Use and Privacy Policy" with both linked, the Contributor Terms linked from the sign-in step as the account's own terms.
12. **Minor. The registry entry needs a kind of its own.** `SourceKind.OSM` is "inputs to the OSM vector tile build" and the parser rejects unknown kinds; a destination under `osm` muddles the comment, and the validator requires `attribution` text for an entry that is never credited. Resolution: a `destination` kind (one enum value, the file comment updated), or record the destination in `docs/PLANNING.md` › Licensing instead and leave the registry to sources.
13. **Minor. Prior art row 1 is now answerable.** The website defaults to trackable (Claims table). Replace "the default visibility is not stated publicly" and note that the departure from OsmAnd is an alignment with the service itself.
14. **Minor. The first account in the app is a pattern; say whether it generalises.** A token store, a Settings row, a redirect host and a registration will be wanted again by the cloud drive and fitness ideas. Resolution: one sentence either way ("`osm/` is specific; a second service extracts the PKCE flow and the token store then") so the next proposal does not re-decide it.

## The case against A, for B, for C

Against A: it adds the first standing credential, the first account UI and a new exported entry point to an app whose privacy story is that nothing leaves the phone; the redirect works by an undocumented property of the server's validator; a leaked preferences file is a non-expiring `write_gpx` token until the user notices; and the "one press" the owner asked for is, in practice, press, read a sheet, press again (which is the point). For B: the same flow with a loopback redirect that the wiki documents and Doorkeeper handles per RFC 8252, no new exported component, works on JVM too (a desktop `devtool` sign-in for testing); its costs are the token-exempt route and the manual switch back, and on iOS later it does not work at all. For C: zero new attack surface, no account, no token, no registration, nothing to revoke, the website's own form is the confirmation and the visibility choice; the strongest argument the proposal makes against it is the owner's "one press", but the real one is that the app has no way to hand a private file to the browser's file input (no share sheet, no `FileProvider`, export to a private directory), so C needs its own new surface (a `FileProvider` or a Downloads write) and has no agent path through the website. Weighed against offline-first (none of the three needs the network until Send), permissive dependencies (all three use none), agent-drivability (A and B through the mock; C not) and the design goals (ADR 0025 is silent on outside services), A with the App Link as fallback is the right order; B drops to third; C stays the owner's alternative.

## Hidden coupling

The decision quietly makes three later ones: (1) a token store and an account row that every later service will copy (objection 14); (2) a per-track column that either enters the sync wire format or sets the precedent that service ids are device-local (objection 3); (3) an exported component that receives data from the browser (objection 1), which the `map` and `share` links so far did not need to be safe against. It does not decide the share sheet, but it exposes that there is none (Code checks), which the parent idea assumed.

## Privacy pre-mortem

Ten years on, the regret is a trace that showed a street. The user had sent one trailhead track with the cut set to 0 because it chopped the first switchback; the choice was remembered; three weeks later a loop from home went out untrimmed, trackable, with timestamps in order, described by its default name with the local date and time; the fixed line "anyone can download the points and times" was true and was not read; the grey map showed nothing grey and nobody noticed the absence. The line that should have caught it is item 4's "remembered" (objection 9): a privacy default that a one-off choice can disarm silently is not a default. The second-order regret: the word "anonymous" on the visibility choice (objection 2) made the user think the trace could not be theirs; the raw file sat under their account on the service's server the whole time. A token leak is the least of the three: `allowBackup="false"`, a private file, a token with one scope, and revocation on the website.

## Recommendation

Accept A with the revisions above: a no-UI callback activity and persisted PKCE state (1), the wiki's words for visibility (2), a local-only trace id (3), the three apps as confirmation and an https App Link as the fallback ahead of B (4), the return path in the device tour (5), the corrections of 6 to 8 and 13, and the design lines of 9 to 12 and 14 for the owner to adjust under ADR 0031. Nothing here reverses the choice: the API, the terms, the visibility values, the default and the no-secret public client are all confirmed by primary sources, and the one unconfirmed premise (a custom scheme) is now confirmed by three shipping clients rather than a reading of the validator. Residual risks after revision: the service may change its redirect policy or its terms (covered by "What would change"); a non-expiring token in a private file on a rooted or compromised phone; the owner's registration is a single account's; and the trim is a radius, not an anonymisation, as the sheet will say. Confidence that A revised is the right choice: high (about 85%); that the custom scheme is accepted at registration today: high (three live clients); that the owner keeps a signed-in account in the app rather than C: the owner's call, not mine.
