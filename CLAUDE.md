# Dystopo — notes for agents

Open-source, offline-first topographic maps. System map and where each topic is documented: `docs/ARCHITECTURE.md`. Design, decisions, and findings: `docs/PLANNING.md` (read it before making architectural changes). Work breakdown: `docs/TASKS.md`.

## Layout
- `shared/` — Kotlin Multiplatform core (currently JVM target only; Android and iOS come later). `commonMain` must stay pure Kotlin: **no `java.*` imports**, so it compiles for every target. Platform-specific pieces (image decoding, HTTP, zlib) are injected through small interfaces such as `ByteRangeSource` and `Decompressor`.
- `devtool/` — JVM command-line tool that runs shared-core features and prints JSON reports. JVM-only code (image I/O, HTTP, elevation sources) lives here.
- `serverlib/` and `server/` — the server pieces (`LiveTiles`, `BuildRoutes`, `ServeStatic`, `SyncRoutes`, `PackCatalog`, the elevation sources; package `...dystopo.server`) shared by `devtool serve` and the standalone server (`./gradlew :server:installDist`, config file, `/catalog`, `/healthz`, token, Dockerfile): see `docs/SERVER.md`.
- `tilebuild/` — JVM-only build tool: OSM extract → PMTiles via Planetiler (heavy dependencies stay here, out of devtool). `./gradlew :tilebuild:run --args="--extract liechtenstein --out out/liechtenstein.pmtiles"`; first run downloads ~1.45 GB of aux data into the cache.
- `tools/` — repo tooling: `PrivacyCheck.java` and the git hooks in `tools/git-hooks`.
- `areas.json` — public named test areas. Personal areas go in `devtool.local.json` (gitignored, same format, main checkout only).

## Conventions
- Every raster goes through `MercatorWindow`, so grids from different sources line up pixel for pixel.
- Elevation is `Float` meters in **EGM2008**; `NaN` means no data. Sources convert their own datum before returning.
- Coverage edges between sources are feathered with `Composite.over`; never hard-cut.
- Commands print one JSON object to stdout (agents parse it) and write PNGs to `out/`. Add counters and timings to reports rather than printing logs.
- Tests in `shared/src/commonTest` must run offline and fast. Network-dependent checks are devtool commands, not tests.
- Rendering changes are guarded by golden images (`devtool/src/test/resources/goldens/`, synthetic terrain only). If `check` fails there and the change is intended: `./gradlew updateGoldens`, look at the new PNGs, commit them with the change. Those goldens are the one place PNGs belong in the repo.
- The PNG renderer and the phone style must agree: `StyleParityTest` (devtool tests) renders the Lake Cliff golden and evaluates the generated MapLibre style against every feature of the same archive (filters, zooms, paint, text, icons, sort keys, draw order, label priority); a new difference fails it until it is fixed or added to its explained list with the reason (report in `devtool/build/reports/style-parity.txt`).

## Commands
JDK 21 is required. If `java` isn't on PATH in your shell, set `JAVA_HOME=C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot` first.

```
./gradlew check                                           # all tests (no device needed)
./gradlew :devtool:run --args="areas"                     # list named areas
./gradlew :devtool:run --args="render --area rainier"     # hillshade + contours -> out/rainier-best-z13.png + JSON report
./gradlew :devtool:run --args="render --area rainier --source 3dep"   # sources: best (default; global, EGM2008), copernicus (global 30 m),
                                                                      #   3dep (US 10 m), 3dep-1m (US lidar, NaN = magenta), 3dep-best, swissalti3d (CH 2 m), kartverket (NO 1 m), bev (AT 1 m), hrdem (CA 1/2 m), linz (NZ 1 m), terrarium (legacy)
./gradlew :devtool:run --args="compare --area rainier --zoom 14"      # sources side by side + diff stats
DYSTOPO_3DEP_DESTRIPE=1 ./gradlew :devtool:run --args="render --area rainier --source 3dep"   # T70 Destripe on the 3DEP 1/3" grid (off by default; destripe* counters)
./gradlew :devtool:run --args="mvt dump --file tile.mvt"  # summarize a Mapbox Vector Tile (--gzip, --layer, --samples)
./gradlew :devtool:run --args="pmtiles info --file x.pmtiles"   # PMTiles header, metadata, per-zoom counts (--url for remote, --tile z/x/y)
./gradlew :devtool:run --args="tiles --area rainier --min-zoom 8 --max-zoom 13 --verify --preview-zoom 13"   # Terrarium XYZ tiles -> out/rainier-best/
./gradlew :devtool:run --args="render --area rainier --shading multi --slope-overlay"   # shading hillshade|multi|none; CalTopo-style slope bands
./gradlew :devtool:run --args="sources --ids best"        # data source registry; composed attribution for a source
./gradlew :devtool:run --args="tour --zooms 9,12"          # world sanity sweep: areas.json expectedElevation/tags -> out/tour/summary.json + contact-sheet.png; exit 1 on failure
./gradlew :devtool:run --args="gpx info shared/src/commonTest/resources/gpx/skyline-loop.gpx"   # track stats; also gpx render --osm ... and gpx export
./gradlew :devtool:run --args="tour --zooms 9,12"         # world tour: every area with expectedElevation, plausibility checks, contact sheet
./gradlew :devtool:run --args="sprite"                    # MapLibre sprite sheet (out/sprite.png/.json, @2x) from DefaultOsmStyle's marker table, drawn with the renderer's MarkerShapes; serve writes it too
./gradlew :devtool:run --args="route --pack out/rainier-outdoors.pmtiles --from 46.786,-121.736 --to 46.802,-121.729"   # trail route (graph <archive>-graph.idx, e.g. rainier-outdoors-graph.idx, built on demand; --mode bike, --gpx); PNG + JSON
./gradlew :devtool:run --args="sync-sim --peers 3 --ops 2000 --seed 42 --partitions 5 --reorder"   # sync simulator: in-process peers over a faulty network; --seeds N, --store sql
./gradlew :devtool:run --args="sync with --db out/sync/a.db --peer http://localhost:8687"          # a sync replica: status, with (peer URL or .dsync file), export, import, import-gpx, gpx
./gradlew :devtool:run --args="render --help"             # all render options
```
PNG text (labels, contact sheets) is drawn with the bundled Noto Sans TTFs (`serverlib/src/main/resources/fonts/`, OFL; `RenderFonts`), never the platform `SansSerif`, so goldens match on every OS without installing fonts.
Browser demo (MapLibre over our DEM tiles and OSM PMTiles): generation commands are at the top of `tools/demo/index.html`; then `python -I tools/demo-server.py 8765` and open http://localhost:8765/tools/demo/. Units there are a stored preference (localStorage), seeded by region on first open, changed with the Units select; `?units=ft|m` overrides one load. The demo tour (`--views-file tools/demo-tour.txt`) must pass against both this page and `devtool serve` (its `req=` names are roles mapped to each style's layers). **Agents check it headlessly** with `python -I tools/demo-check.py --view <z/lat/lon> --out out/check.png` (Playwright + Chrome): exit 0 means the map went idle with no console errors, page exceptions, or failed requests; the JSON lists rendered feature counts per layer and the screenshot path, so you can see what a user would see. A zero count on a layer that should have features is a bug, not a style choice.

**Live world mode:** `./gradlew :devtool:run --args="serve --live --port 8687"` and open http://localhost:8687/ (the same demo page). Packs in `out/` (and `--dem`/`--osm`) answer the tiles they hold; everywhere else the DEM is rendered on request from the `best` source (3DEP, Copernicus, EGM2008) through the `tiles` per-tile path, contours are generated from it, and OSM base layers come from OpenFreeMap (registry id `openfreemap`; outdoors-only layers exist only inside packs). Both are cached under the cache dir (`live/`, `openfreemap/`), so a second view anywhere is warm; the first view of a new place takes 10 to 30 s. The box at the top right says which source the visible tiles came from (pack, live-3dep, live-copernicus, openfreemap); `Build pack here` calls `POST /build?name=&bbox=&minZoom=&maxZoom=` (see `BuildRoutes.kt`: progress at `GET /build/{id}`, cancel with `DELETE`), which writes `out/<name>-dem.pmtiles` from the live DEM and `out/<name>-outdoors.pmtiles` from OpenFreeMap tiles (OpenMapTiles schema, not the outdoors profile), serves them under `/out/` and from then on as packs. With `&profile=outdoors` (the page's Vector select) the vector pack is the real outdoors profile instead: one Overpass request for the box (cached) when it is under 0.05 square degrees, else a Geofabrik extract on disk in `cache/extracts/` or one downloaded on demand from the regions in `extractDownloads` (`DYSTOPO_EXTRACT_DOWNLOADS` for `serve`), each covered by its `.poly` polygon; a box nothing covers gets a 422, and 413 is only for a forced `source=overpass` over the cap (T66), converted and built by tilebuild in a subprocess, so run `./gradlew :tilebuild:installDist` once (and again after changing tilebuild); `&fallback=1` falls back to OpenFreeMap when Overpass refuses. Small boxes read only the ocean polygons that reach them (none inland; `waterPolygons` in tilebuild's report), so a Paradise-sized rebuild takes about 5 s warm. `GET /stats` has per-route, per-source tile counts and timings, `/phone` the phone style over the live routes. **Map options** (the phone's T47 settings) work in both `serve` modes as query parameters of `/style.json`, `/phone` and `/` (the demo page also has a Map options section that writes them to the URL): `hillshade=off|single|multi`, `hillshadeIntensity=0..1`, `slope=on`, `contourInterval=auto|<n>` (in the contour units), `contourLabels=sparse|normal|dense`, `night=on`, `trails|water|landcover|pois|boundaries=off`; a bad value is a 400. The style then points at `/shade/{z}/{x}/{y}.png?...` (hillshade and slope rasters from the DEM, as on the phone; `shadeGeneration` in `/stats`) and `/contours/...?interval=<n>`. Check it with `python -I tools/demo-check.py --url "http://localhost:8687/?live=1" --views "12/45.83/6.86|src=live-copernicus" "12/46.85/-121.76|src=pack"`: in live mode every view must also show hillshade and OSM features, and `|src=` checks the DEM source.
**Trip editor** (T68, live mode; `tools/demo/trips.js`, routes in `RouteRoutes.kt`, docs/SERVER.md › Route planning): "Plan a trip" in the panel; with "Plan route" on, click the start and the end, click again to add a via point, drag a numbered point to move it, right-click to remove it. The card has distance, climb, descent, hike time, the profile (hover it), GPX and "Save as trip" (into the browser's own sync replica in localStorage, then pushed to the server's `/sync/push` with the Token field; a phone syncing with the server gets it). `window.dystopoTrips` scripts it. Check the flow with `python -I tools/demo-check.py --url "http://localhost:8687/?live=1" --views "12/46.85/-121.76|src=pack" --route "46.7864,-121.7366;46.8024,-121.7289;46.7960,-121.7262"` (Paradise to Panorama Point with real clicks, a via point added on the line and dragged to the third place, GPX, save and push; `route` in the JSON, screenshot `<out>-route.png`).

`devtool` runs with the repo root as working directory. Downloads are cached in `cache/` (or `$DYSTOPO_CACHE`), output goes to `out/`. Both are gitignored. **View output PNGs** to check rendering; several bugs so far were only visible in the image.

## Android
`androidApp/` (Compose + MapLibre Native + `shared`) shows a region pack: hillshade from the DEM PMTiles (MapLibre `raster-dem`), OSM from the outdoors PMTiles, and **contour tiles generated on the device** (`shared/.../tiles/ContourTiles.kt`, cached on disk). MapLibre can't read PMTiles, so the app runs a loopback-only HTTP server (port 8686) serving `/dem`, `/osm`, `/contours`, `/glyphs` and `/style.json`; in debug builds the debug routes are on a second loopback server on a random port (T57, below) (the MapLibre style is translated from the devtool's `DefaultOsmStyle` by `shared/.../maplibre/MapLibreStyle.kt`). The module and `shared`'s android target exist only when an SDK is installed (`settings.gradle.kts` looks at `local.properties` / `ANDROID_HOME`), so SDK-less machines still build.
```
powershell -ExecutionPolicy Bypass -File tools\android-sdk.ps1     # SDK under %USERPROFILE%\Android\sdk + local.properties (no admin)
./gradlew :androidApp:assembleDebug
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build   # headless emulator, install, push out/rainier-*.pmtiles, launch, forward -Port to the debug server
powershell -ExecutionPolicy Bypass -File tools\android-push-pack.ps1 -Dem out\rainier-dem.pmtiles -Osm out\rainier-outdoors.pmtiles   # packs + glyphs only (-NoOsm: DEM only)
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd <avd> -EmuPort <n> -Port <p> -Forward   # after an app restart: re-read the debug port and token, re-forward
python -I tools/android-check.py --port 8686 --serial emulator-5554 --views-file tools/android-tour.txt   # device tour: JSON summary, out/android-tour-sheet.png; exit 1 on failure
```
Several emulators side by side (one per task): own AVD, console port and host port; the script uses the serial `emulator-<EmuPort>` for every adb call, prints it, and refuses a console port or host port that belongs to another AVD (`-Port` is the host side, forwarded to the debug server's device port read from logcat). `-Gpu` defaults to `host` when there is a hardware GPU: under `swiftshader_indirect` MapLibre draws no text and no dash patterns. The GPU mode is fixed at boot (`-Stop`, then boot again); every run reinstalls the app and re-pushes the packs (`-PackName rainier` pushes a named pack, `<name>-dem.pmtiles` / `<name>-outdoors.pmtiles`). `-Build` writes `local.properties` if the worktree has none. T65: the script's progress (build, boot, install, push) goes to the output stream, so `| Tee-Object`, `> log` or a parent process see each step as it happens. Each AVD takes about 6 GB: on this machine put task AVDs on E: with `-AvdHome E:\dystopo-avd` (C: ran out of space with eight), and remove them when done with `-Stop -Delete` (same `-AvdHome`). Pass the serial to the checker too, so it refuses to drive anything else:
```
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Build -Avd dystopo35-T28a -AvdHome E:\dystopo-avd -EmuPort 5570 -Port 8694   # serial emulator-5570, debug server on localhost:8694
python -I tools/android-check.py --port 8694 --serial emulator-5570 --views-file tools/android-tour.txt --out out/t28a/tour.png
powershell -ExecutionPolicy Bypass -File tools\android-emu.ps1 -Avd dystopo35-T28a -AvdHome E:\dystopo-avd -EmuPort 5570 -Port 8694 -Stop -Delete   # kill it, drop the forward, delete the AVD
```
`android-check.py` relaunches the app and clears the contour cache first, then per view sets the camera, waits for idle, screenshots, diffs `/stats` and reads `/features`; it fails a view on: style not loaded, not idle, tile server errors, an expected source (pack covers the view) serving no tiles, a blank screenshot, no contour lines rendered, or labels placed but not drawn (`/features/text`); and the tour when no glyphs were served for a font the style uses. Contour tiles over `--contour-budget-ms` (1000) are warnings, failures with `--strict` (timings swing with host load). It also reports the app's logcat warnings. Look at the contact sheet (`out/android-tour-sheet.png`).
**Loopback token** (T49, `LoopbackToken.kt`): any app on the device can open 127.0.0.1:8686, so every request, tiles and the style included, must carry the app's per-launch random token, as `?t=<token>` or an `X-Dystopo-Token: <token>` header; anything else gets 401 (`/health` `server.tokenRefused` counts them). The style MapLibre loads puts `t=` in every tile, glyph and shade URL. **Debug port** (T57): debug builds serve the debug routes on a second loopback server on a random port per launch and announce it, with the token, only in logcat: `I/Dystopo: debug server on port N token T` (other apps cannot read another app's logcat, so the token stays with the app's process). Port 8686 then answers like a release build: map routes with the token, 404 for every debug route, no `/health`. `android-emu.ps1`, `android-check.py` and `android-probe.py` read the line through `adb logcat` (helper `tools/android_debug.py`) and forward the host port to it, again after a relaunch; by hand: `adb -s <serial> logcat -d -s Dystopo:I`, then `adb -s <serial> forward tcp:8686 tcp:<N>` and `curl -H "X-Dystopo-Token: <T>" localhost:8686/stats`. The setting `POST /settings?debugFixedPort=1` (from the next launch) puts the debug routes back on 8686 with the T49 bootstrap, where `GET /health` without the token answers only `{"token": "..."}` to a loopback caller; the logcat line then names 8686. Release builds have no debug routes and no bootstrap, so there the token never leaves the process.
Debug endpoints (debug builds only, on the debug port; `curl -H "X-Dystopo-Token: $T" http://localhost:<forwarded port>/...`). They run on their own small thread pool, so they answer while contour tiles generate:
- `GET /health`: packs, server load (`rejected` counts per reason, tile and debug pool queues), map state. `map.idle` means style loaded, MapLibre's `isFullyLoaded`, last frame complete, no tile pending at the server, no camera move and no new frame for 500 ms; `map.notIdleBecause` names the blockers (`styleLoading`, `animating`, `pendingTiles`, `notFullyLoaded`, `frameNotFullyRendered`, `rendering`, `settling`); `map.lastScreenshot` says how the last screenshot settled.
- `GET /screenshot[?wait=ms][&mode=window][&stable=0]`: PNG of the map (MapLibre snapshot). It waits for idle and then until two snapshots in a row agree, so it never returns a half-loaded map; `stable=0` skips the pixel check, `wait=0` captures at once. `mode=window` copies the map surface and draws the Compose overlays on top. **View it**, like the devtool PNGs.
- `GET /camera`; `POST "/camera?lat=46.853&lon=-121.76&zoom=12&bearing=0"` (or a JSON body).
- `GET /stats`: tiles served per source, contour generation ms (min/avg/max, recent tiles with sample/trace split, `warmup`), disk-cache hits, DEM decode cache, memory (Java heap, native heap, PSS by category), APK and pack bytes.
- `POST "/location?lat=..&lon=..&accuracy=10"`: inject a fake GPS fix (the location puck moves; device fixes stay detached until `POST /location?device=1`); `GET /location`.
- `GET /settings`; `POST "/settings?units=m&textScale=1.4&warmup=0"`: units (`ft`, `m`, or `unset`), text scale (0.5 to 3; outside is a 400), contour warm-up; `server` (the online tile server, empty for offline only). Cache caps: `onlineCacheMb` (fetched online tiles) and `contourCacheMb`, one LRU byte cap enforced while the app runs over every pack's contour tiles, the cliff-rewritten vector tiles (`cliffs1-<vector id>-<dem id>/`) and the hillshade/slope shade tiles (`shade1-<options>-<dem id>/`); a deleted pack's directories go with it. Map options (T47, also the Map section of the settings sheet): `hillshade` off/single/multi, `hillshadeIntensity`, `slope` on/off (CalTopo bands), `contourInterval` auto or a value from `contourIntervalChoices` (from contour zoom 11, pack and online contours alike), `contourLabels` sparse/normal/dense, `trails`, `water`, `landcover`, `pois`, `boundaries`, `night`; the default style is unchanged unless an option needs shade tiles (`/shade/{z}/{x}/{y}.png`, `/stats` `shadeGeneration`). Units are a preference (docs/PLANNING.md › Units): unset on install, seeded once from the first pack's centre or the first fix, then only the user changes them; contour tiles, the style, track stats, the profile and search results follow them. `POST /settings/ui?open=1` opens the settings sheet (also the Settings chip on the map).
- `POST /reload` (reopen packs after a push), `POST /cache/clear` (drop cached contour tiles).
- `GET /features` (alias `/labels`): rendered feature count per style layer in the viewport (queryRenderedFeatures) plus placed symbols per symbol layer; `GET /features/text`: pixels that change when text is hidden (0 with labels placed = labels not drawn).
- `GET /contour-labels[?minRunPx=200]`: index contours in view and which carry a placed label; unlabelled ones with their visible length and longest on-screen run (`labelledLong`/`indexLong` count lines with a run of at least `minRunPx`).
- `GET /packs`: `active` (the primary pack), `inUse` (every pack on the map with `primary`, `demRank`/`osmRank` in precedence order, `osmProfile`), `roots`, and per pack `name`, `active`, `usable`, `bytes`, `bounds`, `minZoom`/`maxZoom`, `attribution`, `dem`/`vector` (file, bytes, tileType, zooms, bounds, tiles, attribution, title, `complete`), `files`, `errors`, `inUse`; plus `downloads`, `search` (per-pack index state) and `routing` (the primary pack's trail graph). Precedence per tile (`PackPrecedence`): outdoors profile over plain OpenMapTiles, then the primary pack (`POST /packs/activate?name=`), then the deeper archive, then the smaller box. `DELETE /packs/{name}` removes the archives, the search index, the routing graph and (on the next collection) the pack's contour, cliff and shade tiles. `GET /attribution`: full credits plus `mapLine`, what the on-map credit line shows for the packs overlapping `viewBounds` (and the online sources when the view is online).
- **Routes** (T45, `RouteRoutes.kt`): `POST "/route?from=46.7864,-121.7366&to=46.8024,-121.7289&mode=hike"` plans on the primary pack's trail graph (built on first use into `<vector archive>-graph.idx` next to the pack; progress in `GET /route/status`) and shows it, fitting the camera to it; results carry `via`, the named trails in travel order (outdoors packs; plain OpenMapTiles lines have no names). `GET /route` (card state, `ui.lastFit`, `ui.layout` with the route card and track panel edges and `overlap`), `POST /route/mode?mode=bike` (answers with the replanned route), `/route/longpress`, `/route/save`, `/route/gpx`, `/route/export`, `/route/clear` (T65: also closes the route editor, so a kept route's line goes too; the route stays stored, `closedTrip`). T65: a route has one set of numbers everywhere: the card, `route` in `POST|GET /route`, the kept route, the trip card, the Routes list and navigation all show `RouteSummary` of its points (T24's 3 m hysteresis climb, the T45 hike model); the router's graph-based climb and time are under `route.graph`. `POST /route/import/pick` opens the Routes list and the system file picker (its Import button; pick a GPX, it is imported as routes and the last one opens), `GET /route/import` has the result. Trips (planned routes, `/routes`) are documented in `trips/TripRoutes.kt`; the trip card has Go.
- **Navigation** (T61, T65; `NavRoutes.kt` documents every route): `POST /nav/start?route=current|<kept route id or prefix>|<saved route>` (or `track=`, `file=`, a GPX body), `GET /nav`, `GET /nav/status`, `POST /nav/stop`, `/nav/camera`, `/nav/heading`. Starting closes the route editor and hides the route card; the navigation line draws above the planned, kept and track lines (`layer.overlaysAbove` empty). `POST /nav/snooze?min=10|until=back|off=1` silences the off-route alert (events are still listed; `snooze.suppressed`); the banner has Snooze 10 min and Quiet until back. Stale fixes: a GPS fix or the last known location more than 30 s old is dropped (`fix.droppedTooOld`), the last known location more than 2 km from the line does not start navigation (`droppedTooFar`), and with no usable fix for 30 s the bar says "No GPS fix for N s" (`fix.lost`). `etaVsPlan` is a pace ratio, (fix time since the first fix + the model's time still to go) / the planned time (the route's `RouteSummary` time; the line's model time for tracks): 1.0 at the start, above 1 behind plan; `pace` has the parts. `layout` says where the Tracks and Routes chips sit: they stack below the stats card (`TopChips`), and the Routes chip sits below the open tracks list. Off the device: `./gradlew :devtool:run --args="nav replay --path shared/src/commonTest/resources/gpx/skyline-loop.gpx --path-track --fixes shared/src/commonTest/resources/gpx/skyline-offroute.gpx --expect-off 1 --expect-arrive"` runs the same off-route logic on the JVM (events, max distance, progress, `etaVsPlan` as JSON; exit 1 when an expectation fails).
- **Sync**: the `/sync/*` and `/share/*` routes are in the Sync and Phone-to-phone sync paragraphs below; the share listener is a separate server with its own share code (T72: 16 characters, the link encrypted under it), not the loopback token.
- `tools/android-probe.py --port <port> --serial <serial>` sends malformed and oversized requests and checks the server answers 400/408/413/414/431 and stays up, that requests without the token (or with a wrong one) get 401, and (T57) that `/health` without the token is 401 on the debug port and that device port 8686 serves map routes only (debug routes 404).
- T57 also: `/stats` tile counters are cumulative since the app started (`counters.tileServiceOpens`), not reset when a pack install, a synced setting or `/reload` reopens the tile service (T65: `shadeGeneration` and `cliffs` too); `POST /settings?routeSnapM=50..1000` (default 300; the settings sheet offers 300 m, 500 m, 1 km) is how far a route's ends may be from a trail, and an off-network failure names the nearest trail, its distance and direction (`nearestName`, `nearestDirection`); `/route/status` has `decoder`; `POST /packs/catalog/refresh[?server=]` fetches the catalog again (T65: a server's vector-only single-file pack is listed and downloads as a map-only pack, `<name>-outdoors.pmtiles`, drawn over another pack's or the online DEM and never primary); `POST /location/replay?record=` is a 409 while a track is recording (replay without `record=` adds to it).

**Tracks** (T31, T40; `shared/.../store/`, `androidApp/.../tracking/`, routes in `TrackRoutes.kt`, which documents every one). Recording goes through `TrackRecorder` into the SQLDelight `TrackStore` (`tracks.db`), one fix per insert. Pause holds fixes, resume starts a new segment, and a gap of more than `gapS` seconds between fixes (default 300, `POST /tracks/settings?gapS=`, 0 = never) starts one too when the walker also moved more than 50 m across it (T65: a long stop with no fixes, such as the Skyline fixture's 15 minutes at Panorama Point, keeps one segment). Stats are cached in the store and invalidated on append (`GET /tracks` reports `statsComputed`, the misses). GPX export writes our ids in a `dystopo:id` extension (namespace `GpxExtensions.NS_DYSTOPO`), and import (`POST /tracks/import`, GPX body or `?file=` from `files/tracks/`, or Import in the tracks list) keeps them and skips ids already stored. Test with a replay: `curl -X POST --data-binary @shared/src/commonTest/resources/gpx/skyline-loop.gpx "localhost:8686/location/replay?rate=100&record=Skyline"`, then `GET /tracks`, `POST /tracks/<id>/profile` (profile panel), `POST /tracks/waypoints/<wid>/select` (rename/delete sheet) and a `mode=window` screenshot. Replays keep the file's intervals; when the recording already holds a newer fix (recording started a moment before the replay), the replay is shifted onto the recording's timeline (`shiftedMs` in the response) so no point is dropped.

**Phone-to-phone sync** (T54; `androidApp/.../share/`, routes in `ShareRoutes.kt`). The Share screen ("Share" in the tracks list, or `POST /share/start`) opens a second `LocalServer` bound to `0.0.0.0` (port 8841, else any free port) that answers only `POST /share/sealed` (T72): `/share/hello` and the T44 `/sync/pull|push|status` routes travel inside it, ChaCha20-Poly1305-encrypted under the 16-character share code on screen (`7K3M-QW2D-9XHP-T4CA`; a wrong code is a 403 and five replace the code, a replayed request a 409, the old plain routes a 426), announces `_dystopo._tcp` over NSD, lists other phones, and draws a QR of `dystopo://share?addr=<host:port>&code=<code>`. Closing the screen (Back, Close, `POST /share/stop`) closes the port. `POST /share/connect?addr=<host[:port]|share link>&code=` checks the code, then runs one pull-merge-push; `GET /share/status` has the code, port, refusals, NSD state and everything discovered; `GET /share/qr` the QR matrix. Two emulators on one host share a virtual Wi-Fi network (`wlan0`, 10.0.2.18, 10.0.2.20, ...), so NSD discovery works, but a direct connect to the peer's `10.0.2.x:8841` is not guaranteed (it worked for the implementer and failed for the verifier on the same host). The tested path goes through the host: `adb -s <A> forward tcp:8841 tcp:<A's share port>`, then on B `POST /share/connect?addr=10.0.2.2:8841&code=<A's code>` (10.0.2.2 is the host from an emulator); remove with `adb -s <A> forward --remove tcp:8841`. T57: both sides use `AppSync.replica`, and a connect runs through `AppSync.run` (paged like any HTTP sync, `&page=`; conflicts, synced settings, the clock check). A tapped `dystopo://share?addr=&code=` link (`adb shell am start -a android.intent.action.VIEW -d "'dystopo://share?addr=10.0.2.2:8841&code=7K3MQW2D9XHPT4CA'"`) or the in-app scanner ("Scan QR code" on the Share screen: CameraX frames, our own pure-Kotlin decoder `share/QrDecoder.kt`, no ML Kit) fills the address and code; the user still taps Sync. `POST /share/scan` with a PNG or JPEG body (a screenshot of the other phone's Share screen) runs the same decoder and fills the fields; `GET /share/scan` has the camera scanner's frames and reads. **Via server** (T72, `share/RelaySession.kt`, `ShareRelayRoutes.kt`; design and threat model in docs/PLANNING.md › Sync): phones on different networks sync through the server's encrypted relay (`/sync/relay`, docs/SERVER.md › The relay): `POST /share/relay/start[?server=][&code=]` (no code: a new one; the other phone passes it as `code=`) posts this phone's whole log sealed under the code, merges what the other phone posted, then polls every 5 s while the blob lives (15 min) and syncs again when something new arrives; `POST /share/relay/sync`, `POST /share/relay/stop[?forget=1]`, `GET /share/relay` (code, server, polls, syncs, blobs received and rejected, last result). On the screen: New code, or type the other phone's code and Join. Emulators need no adb forward for this: both reach the server at `http://10.0.2.2:<port>`.

**Sync** (T44, T51; design and numbers in `docs/PLANNING.md` › Sync). User data is an operation log (`shared/.../sync/`) that the track store materialises; replicas exchange bundles. The always-on peer is `devtool serve` (and the `server` module) at `/sync/*`, replica in `out/sync/peer.db` (`DYSTOPO_SYNC_DB`). Check convergence with `./gradlew :devtool:run --args="sync-sim --peers 3 --ops 2000 --seed 42 --partitions 5 --reorder --seeds 20 --skew-days 2 --crashes 3"` (`--store sql` for SQLite peers, `--page 50` for paged pulls; exit 1 and a `replay` line on a failure). A JVM replica: `devtool sync status|with|export|import|import-gpx|rename|gpx|gen --db <file>` (`with --peer http://127.0.0.1:8687 --page 2000 [--token T]`; `gen --ops 50000` writes a big synthetic log for paging numbers). Phone (debug): `POST /sync?with=http://10.0.2.2:<port>` (pages of 2000; `&page=0` for one bundle), `GET /sync/status` (digest, `pendingOps`, `conflicts`, `clockSkew`, `settingsSync`), `POST /sync/settings?peer=&token=`, `GET|DELETE /sync/conflicts`, `POST /sync/ui?open=1` (the status sheet, also "Sync status" in the tracks list). Units, text scale and map options set on one device reach the others through the log (`app.*` settings). On API 35 emulators keep wifi enabled, or 10.0.2.2 is unreachable. T57: every sync compares clocks with the peer (the server's HTTP `Date` header, a phone's `now` in `/share/hello`); more than 2 minutes apart beyond the measurement's uncertainty is a warning in the result line and on the sync sheet (`clockCheck` in `/sync/status`). The sync sheet also edits the peer and the bearer token (never shown back). T65 (`sync/RouteOps.kt`): a route's waypoints are written one per field (`wpt:<waypoint id>`, null = removed), so concurrent waypoint edits on two devices merge (the same waypoint: last writer wins); compaction drops route field writes superseded by a newer write of the same field, waypoint writes excepted (the log keeps one `path` per route, `CompactResult.opsDropped`); a `path` value over 256 KiB is refused with `RouteTooLargeException` ("split it into shorter routes").

**Track database migrations.** `Track.sq` is always the current schema; `TrackDb.Schema.version` is the highest `<n>.sqm` plus one. To change it: (1) run `./gradlew :shared:jvmTest --tests "*TrackDbMigrationTest*"` and copy `shared/build/trackdb/<version>.sql` to `shared/src/commonMain/sqldelight/databases/` (the frozen old schema; never edit those afterwards); (2) write `<version>.sqm` beside `Track.sq` with the upgrade (new columns go at the end of a table, in the same order as in `Track.sq`); (3) change `Track.sq`. `TrackDbMigrationTest` (in `check`) builds every frozen version, applies the migrations, compares tables, columns and indexes with a fresh `Track.sq` database, and upgrades a version-1 file with rows in it; the Android driver runs the same generated `migrate` on first open after an update. SQLDelight's own `.db`-based verification cannot run here: it loads sqlite-jdbc in a Gradle worker that Windows starts with an empty environment (details in `shared/build.gradle.kts`).

**Release** (T55). `./gradlew :androidApp:assembleRelease` runs R8 (full mode, rules and their reasons in `androidApp/proguard-rules.pro`) and writes one APK per ABI plus a universal one to `androidApp/build/outputs/apk/release/` (`androidApp-<abi>-release.apk`; ABI splits are on only when the Gradle invocation names a release task, so `assembleDebug` still gives the single `androidApp-debug.apk`). Release builds keep the tile routes (`/style.json`, `/dem`, `/osm`, `/contours`, `/glyphs`, `/shade` tiles) and answer 404 to every debug route; the tile routes need the loopback token like debug builds (401 without it), and release has no `/health` to hand it out. Signing uses a local test key; make it once (both files are gitignored, never commit them):
```
keytool -genkeypair -keystore tools\release.keystore -storetype PKCS12 -alias dystopo -keyalg RSA -keysize 4096 -sigalg SHA512withRSA -validity 36500 -dname "CN=Dystopo release, O=Dystopo"
# tools\release.properties:
storeFile=tools/release.keystore
storePassword=<the password you gave keytool>
keyAlias=dystopo
keyPassword=<same>
```
Without `tools/release.properties` release builds are signed with the debug key. The real release key (RSA 4096, SHA-512, valid 100 years, 48-character password, made 2026-10-10) lives only on the owner's machine and in the `RELEASE_*` Actions secrets; it must never change, because a phone only updates an app whose new APK is signed by the same key. The map opens at a place from a link in every build: `adb shell am start -a android.intent.action.VIEW -d "'dystopo://map?lat=46.853&lon=-121.76&z=12'"` (`z`/`zoom`, `bearing` optional; also as intent extras; `--activity-single-top` moves the open map). `tools/android-release.ps1 -Serial emulator-<port> [-Build] [-Port <host>]` installs the release APK for the device's ABI (uninstalling a build signed with the other key first), pushes the Rainier pack, glyphs and sprites to the app's external files dir (release is not debuggable, so no `run-as`), opens three views through the link, polls `adb exec-out screencap` every 500 ms, and reports `am start -W` times, time to first contours and to a settled screen, the PNGs (`out/release/`, view them), a probe of tile and debug routes without a token (`-Port`: tiles 401, debug routes 404, `probeOk`), and logcat crashes and app errors as JSON. `-Apk <debug apk> -Label debug -Runs 3` gives the debug numbers to compare.

The emulator needs CPU virtualization, which an administrator enables once: Windows Hypervisor Platform (`Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All`, reboot) or the Android Emulator hypervisor driver. Without it, x86_64 images never start under `-accel off` and ARM images are refused on x86_64 hosts, so `android-emu.ps1` stops with these instructions; `-NoEmulator` uses a phone connected with USB debugging instead.

**No device?** `./gradlew :devtool:run --args="serve"` serves the same routes from the same shared code (style, DEM with ancestor fallback, generated contours, glyphs from `cache/glyphs`) on http://127.0.0.1:8687/ with a MapLibre GL JS page, so the phone style can be checked with `python -I tools/demo-check.py --url http://localhost:8687/ --views 12.5/46.853/-121.76` (MapLibre GL JS, not Native: it catches style and tile bugs, not Android ones). `GET /stats` there gives desktop contour timings.

## Debug before you push
The implementer debugs the change; the reviewer confirms. Before opening a PR:
1. `./gradlew check` green (unit tests, goldens, license check).
2. Exercise the change end to end with the real tooling: render the affected areas at the zooms that matter and look at the PNGs; run `tiles --verify` for anything touching tiles; run `tools/demo-check.py` for anything touching the viewer; run `tilebuild` for anything touching the profile. Fix what you find, then re-run.
3. The PR body lists exactly what was run and what was seen. A verifier agent then repeats the key runs; "the reviewer will catch it" is not a plan.
4. **Documentation is part of done.** A task updates the docs its change touches in the same PR: the command or endpoint lines here (`CLAUDE.md`), `docs/SERVER.md` for server behaviour and config, the design section of `docs/PLANNING.md` for a design that changed (Sync, Units, Licensing), `tilebuild/PROFILE.md` for layers, the registry (`sources.json`) for data sources, the KDoc at the top of a `*Routes.kt` file for its routes, and `docs/ARCHITECTURE.md` when a module or format is added. Measurements and findings go in the PR body; the integrator carries them into the dated log.

## Working in parallel (several agents at once)
- The main checkout is `C:\Users\Dorje\Documents\src\android-app` (the folder name is historical; the project is Dystopo). While other agents are active, nobody commits to `main` directly.

- Set `DYSTOPO_CACHE=C:\Users\Dorje\Documents\src\android-app\cache` in your environment so worktrees share downloaded data instead of re-fetching it from USGS and AWS.
- Before pushing: `./gradlew check`, then `git fetch && git rebase origin/main`. Push the branch and open a PR: `gh pr create --fill`. Put measurements, timings, and what you saw in the PNGs in the PR description. Don't commit PNGs.
- Don't edit the Phase 0 log in `docs/PLANNING.md` from a task branch; the integrator adds the log entry when merging. Edit other docs only where the task says so.

- When the task is merged the integrator removes the worktree and deletes the branch (Gradle build dirs exceed Windows path limits for `git worktree remove`; delete with `Remove-Item -LiteralPath \?\<path> -Recurse -Force`, then `git worktree prune`).

Never match processes by a command-line substring such as `devtool`, `demo-server.py` or `dystopo-avd`: one agent doing that killed every other agent's emulator and the coordinator's live server at once.

Removing the worktree follows the link and deletes the target's contents; this wiped the main `out/` once. Read shared data by absolute path (`C:\Users\Dorje\Documents\src\android-app\out\...`), or copy the few files you need, or generate into your own `out/`.
- Model per kind of work (for whoever launches agents): the most capable model for planning, docs, review decisions and merges; a strong coding model (Opus-class) for implementing a task and its tests; a mid-tier model (Sonnet-class) for verifying a PR (run `check`, view PNGs, check done criteria) and small fix-ups; the cheapest model (Haiku-class) for mechanical git work (rebase, push, open the PR from a given summary, cleanup). Set the model explicitly on every launch; the default inherits the launcher's, usually the most expensive.

## Coordinating a wave (for the session that launches agents)
What worked across waves 1 to 5 (24 tasks, 24 PRs, one coordinator). Keep it unless there is a reason to change.
- **Unit of work is a task, not a folder.** A task's **Owns:** line in `docs/TASKS.md` partitions the files so agents never collide; a feature usually spans `shared`, `devtool` and tests, so a folder-owner would need a handoff for every feature. Two tasks that must touch the same file go in different waves, or one task owns the file and the other records a follow-up.
- **Roles and models.** Coordinator (most capable model): writes the wave in TASKS.md, launches, decides, merges, writes the Phase 0 log, runs post-wave sweeps. Implementer (Opus-class) per task: builds, tests, debugs end to end, opens the PR. Verifier (Sonnet-class) per PR: rebases if `main` moved, runs `check`, repeats the PR's key runs, views the PNGs, returns MERGE / MERGE WITH NOTES / FIX with specifics. Chores (Haiku-class) for mechanical git work. Always set the model explicitly.
- **Communication is hub and spoke.** Agents report to the coordinator; the coordinator relays. A verifier may message its implementer directly for a small fix-up, but anything that changes scope or ownership goes through the coordinator. Nobody edits another task's files.
- **Wave size.** 5 to 8 implementers at once has been fine; verifiers run as PRs arrive. Stop launching new work when the usage recorder (`~/.claude/usage.json`, written by the status line) shows 75% of either the 5-hour or the 7-day budget; let running agents finish.
- **Resuming a session.** Read `docs/TASKS.md` from the bottom: the first wave whose tasks lack a **Status:** line is the open wave; `gh pr list` shows tasks with open PRs. Start the live server from the main checkout (`./gradlew :tilebuild:installDist` once, then `./gradlew :devtool:run --args="serve --live --port 8765"`) so agents and the owner have the viewer; AVDs go under `E:\dystopo-avd`; read the usage recorder before launching (`~/.claude/usage.json`). Owner actions the project is waiting on are listed at the top of `docs/TASKS.md`.
- **Merge sequence** (coordinator, main checkout): read the verifier report; `gh pr merge <n> --squash` with a quote-free body (PowerShell 5.1 splits arguments on double quotes); only on success delete the remote branch, fast-forward `main`, remove the worktree, delete local branches; write the dated log entry and the **Status:** line to two files and run `python -I tools/merge-log.py Tnn <entry> <status>` (it updates `docs/PLANNING.md`, `docs/TASKS.md` and `CHANGELOG.md` together); commit to `main`. After a wave, update the README status paragraph and `docs/ARCHITECTURE.md` if the module map or formats changed. Deleting a branch before the merge succeeded once closed a PR; recover with `gh pr reopen` after recreating the branch at the recorded SHA.
- **Post-wave sweeps** after the last merge of a wave: `./gradlew check`, `tour --zooms 9,12`, `python -I tools/demo-check.py --views-file tools/demo-tour.txt`, the Android stand-in (`devtool serve` + `demo-check.py --url http://localhost:8687/`), live views for every national source (`|src=live-swissalti` and friends), `sync-sim` with skew and paging, `:server:installDist`, `python -I tools/notices.py --check` (regenerate `NOTICES.md` when a wave added dependencies or data sources), the release script on a fresh emulator, and the device tour on the coordinator's own emulator (`android-emu.ps1 -Build`, then `python -I tools/android-check.py --views-file tools/android-tour.txt`; view the contact sheet). Findings become the next wave's sweep task (T11a, T19, T23 were these).
- **Privacy at the coordinator too.** Log entries and PR bodies describe personal areas generically; the hooks catch names and coordinates, not paraphrases. The git hooks never see PR text, so before merging run the PR title and body through the scanner (`gh pr view <n> --json title,body --jq '.title + "
" + .body' | java tools/PrivacyCheck.java scan`); a hit means edit the description first, and remember GitHub keeps PR-description edit history visible. A place the owner asks about in chat (a screenshot, a demo) may be a private term even if it is a famous summit; use only `areas.json` names in anything written down.

## Rules
- **Never commit personal locations.** No home/travel areas, real GPS tracks, or coordinates that reveal where the developer lives or travels, in code, tests, fixtures, docs, planning logs, PR descriptions, or commit messages. That includes indirect hints: nearby place names, lidar project names, DEM cell/tile names. When logging results from a personal area, describe it generically. Use public places (Rainier, Mont Blanc, Glacier/Waterton, Bonneville) or synthetic data in anything committed.
  - Git hooks in `tools/git-hooks` enforce this against `devtool.local.json` (area names, `privateTerms`, bbox coordinates, DEM cell names). Enable once per clone: `git config core.hooksPath tools/git-hooks`. They need Java (`JAVA_HOME` or `java` on PATH).
  - **Never bypass with `--no-verify`.** If the check fires, fix the content.
- **Every feature must be agent-testable:** unit tests in `shared`, plus a devtool command (later: debug server endpoint) that triggers it and reports results as JSON or PNG.
- **Dependencies must be permissively licensed** (MIT, BSD, Apache-2.0, EPL/EDL). No GPL or AGPL dependencies anywhere; they'd block relicensing. LGPL is tolerated only in build-side tooling modules (`tilebuild`), never in `shared`, `devtool`, or app modules. `./gradlew check` enforces this (`licenseCheck`; config in `gradle/licenses/`, reports in `<module>/build/reports/licenses/`). An artifact whose POM has no license needs a line in `gradle/licenses/artifact-overrides.txt` with its real license. Don't copy code from other projects.
- **Data sources need license and attribution recorded** in `shared/src/commonMain/resources/sources.json` (the registry; see `docs/PLANNING.md` › Licensing). A new source gets a registry entry first; devtool sources declare `registryIds` and set `provenance` on results so reports and tile metadata credit exactly what contributed.
- Commit as you go with descriptive messages. Don't amend pushed commits. Solo work goes straight to `main`; parallel work goes through branches and PRs (above).
